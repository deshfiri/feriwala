Testing and checks

How the Pest and Vitest suites are laid out, how they stay away from your development data, the traps that make a healthy suite look broken, and the four checks every change must pass.

Rule. Every code change adds or updates a test, and the narrowest relevant slice is run after each change. Do not delete tests or test files without approval. Run one Pest process at a time against a given schema.

Layout

The testing schema

Tests run inside a testing schema in the same database as development, not in a separate database. phpunit.xml sets DB_SEARCH_PATH=testing and config/database.php passes it to the pgsql connection's search_path. The application role owns its database and can create schemas but has no CREATEDB privilege, so a schema gives the same isolation without elevated rights on every developer machine and CI runner (decision D5). scripts/setup-dev-environment.sh creates the schema; CI creates it with CREATE SCHEMA IF NOT EXISTS testing.

phpunit.xml also fixes these environment values for the test process only:

Rule. Those test values live in phpunit.xml and are scoped to the test process. They do not relax the project rule: never switch session, cache or queue to file, sync or database in .env or application config, not even temporarily and not to make a test pass. The application must stay stateless and horizontally scalable (§40, D10).

Note. A runner that sources .env into the shell before starting Pest makes CACHE_STORE=redis win over phpunit.xml, so DistributedLock then uses real Redis (.ai/rules/concurrency.md). Concurrency tests rely on that being safe, see below.

One suite at a time

Every run shares one schema and RefreshDatabase opens by dropping every table in it. Two concurrent runs against the same schema therefore deadlock on the drop and fail in ways that look exactly like code defects: SQLSTATE[40P01] scattered across whichever files happened to be running. A second symptom appears once the schema is large: concurrent drops exhaust PostgreSQL's lock table (max_locks_per_transaction) and fail with SQLSTATE[53200] out of shared memory, so even two runs in different schemas can fail. Run one Pest process at a time. Long slices (Wallet plus Inventory takes ten minutes or more) belong in the background.

If you genuinely need a second run, give it a schema of its own:

psql -h 127.0.0.1 -U feriwala -d feriwala -c 'CREATE SCHEMA IF NOT EXISTS testing_mine'
DB_SEARCH_PATH=testing_mine vendor/bin/pest tests/Feature/Wallet

Use the DB_* credentials from your .env for psql. A missing schema makes every test fail immediately, which is harmless: development data is untouched. If a run reads REDIS_PREFIX-scoped keys (Redis-backed concurrency tests), give each run its own prefix too, for example REDIS_PREFIX=mine_ (config/database.php reads it). Automating a per-run schema is task P0-57.

The cached-config trap

Gotcha. A cached configuration (bootstrap/cache/config.php, written by php artisan optimize or config:cache) pins search_path to public. php artisan test and Pest then ignore DB_SEARCH_PATH, and RefreshDatabase drops and re-migrates your development schema. This has emptied a development database more than once.

Symptoms, none of which look like configuration: deadlocks (SQLSTATE[40P01]) naming public tables; bulk HTTP 419 responses (the cached APP_ENV=local turns CSRF back on); development tables suddenly empty. Bulk 419s are never a test-code symptom. Before any run, verify the override applies:

DB_SEARCH_PATH=testing_mine php artisan tinker --execute 'echo config("database.connections.pgsql.search_path");'
# must print testing_mine, not public

If it prints public, run php artisan config:clear first. composer test does this as its first step (php artisan config:clear --ansi).

Never rebuild assets while the suite runs

Every Inertia response test renders the page shell, which resolves the entry through Vite: public/hot when the dev server is up, public/build/manifest.json otherwise. Deleting public/hot or running npm run build mid-run makes dozens of tests fail at once with ViteException: Unable to locate file in Vite manifest and a 500, across modules nobody touched (.ai/rules/tests.md). Build before starting the suite, and build again after adding a page if the dev server is not running.

Pest conventions

  • Most tests are feature tests. Create with php artisan make:test --pest SomeFeatureTest (do not include Feature/ in the name); --unit for a unit test.
  • Use factories for models and check the factory for a state before hand-building. Faker via fake() or $this->faker, following the surrounding file.
  • Test the behaviour and its important failure modes, not every branch. Read the testing-best-practices skill before writing tests.
  • Prove rejection, not only success for the non-negotiables: self-scoping (a non-admin cannot reach another user's data), product-creation restrictions (§12), immutable ledger rows, illegal status transitions.
  • Do not tinker or write one-off verification scripts where a test proves the behaviour.

Helper naming: one global function namespace

Gotcha. Pest loads every test file into one global function namespace. A bare function resolver() in one file collides with the same name in another, and with Laravel's own helpers (session(), cache(), report()). The failure is a fatal "Cannot redeclare" that takes the whole suite down, not one test.

So prefix every helper with what it belongs to (dataScopeResolver(), localeTestSession(), lockOverArrayStore()) or define it inside the test closure. A helper defined in one file and called from another only works while both happen to be loaded, so a helper used by several files belongs in tests/Pest.php or tests/Support/, where a narrow run of one directory still sees it.

Concurrency tests

tests/Feature/Concurrency (group concurrency) proves that races resolve to one winner: wallet, payment, stock, return, damage, referral, withdrawal, supplier stock and order-allocation tests all live there. They fork worker processes. .ai/rules/concurrency.md records the trap: a forked worker that inherits the parent's open Redis socket reads other workers' replies, never sees its lock granted, and the lock stays held until its TTL (a 130-second hang). Before pcntl_fork, call Redis::purge() for every connection in config('database.redis') (except client, options, clusters), alongside DB::purge().

The four required checks

All four must pass before work is considered done (CLAUDE.md). CI runs them as composer ci:check (npm run check, npm run types:check, then composer test, which itself runs config:clear, Pint in check mode, PHPStan and php artisan test).

CheckCommandNotes
PHP formattingvendor/bin/pint --parallel (composer lint)Fixes in place. The Boost guidance form is vendor/bin/pint --dirty --format agent. --dirty formats every uncommitted file in the tree, including files another session or your editor changed, so check git diff --stat afterwards and stage explicit paths. composer lint:check is the non-writing variant used by CI.
Static analysiscomposer types:checkPHPStan level 8 through Larastan over app/, bootstrap/app.php, config/, database/, routes/. The baseline in phpstan-baseline.neon holds starter-kit debt only; it should shrink over time and must never grow, and all new code is held to level 8.
Testsvendor/bin/pestNarrow slice while working, full suite by the maintainer. See the schema rules above.
Frontendnpm run checkvp check: format, lint (type-aware, warnings denied) and types. npm run check:fix repairs. Also npm run types:check (tsc --noEmit) and npm run test:js (Vitest).

Gotcha. Run PHPStan through composer types:check, never vendor/bin/phpstan directly. A stale result cache in build/phpstan can put the run on a path where the bootstrap files never execute, and Larastan then dies with Undefined constant "Larastan\Larastan\LARAVEL_VERSION", a message that points nowhere near the cause and persists until the cache is cleared. scripts/phpstan.sh (what the composer script runs) clears the cache and retries once only on that exact message; every other failure, including real type errors, passes straight through unretried. It is not an error-suppression script.

Note. vp owns TypeScript, CSS and Markdown formatting. A bare npx vp check --fix rewrites .md files across the repo (.ai/rules/general.md); pass explicit paths to vp check --fix (.ai/rules/js.md). If your editor also formats on save, the two disagree about ternary continuations and a file open in the editor reappears in vp check; point the editor at vp check --fix or turn it off for this project. The whitespace churn blocks nothing and is not worth a commit. This documentation's HTML under docs/ is excluded from vp fmt in vite.config.ts.

Generated route helpers: resources/js/actions and resources/js/routes are gitignored. A fresh checkout needs them before tsc or Vitest page tests can resolve @/actions and @/routes. Generate with php artisan wayfinder:generate --with-form (never without --with-form, see Commands) or run npm run build, which CI does before the checks.

Rules that apply to tests

  • .ai/rules/tests.md: never rebuild frontend assets while the suite is running.
  • .ai/rules/concurrency.md: purge Redis connections before forking race workers.
  • .ai/rules/index.md: the file-to-rule map you must read before editing a path.
