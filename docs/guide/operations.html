Operations

Running Feriwala in production: the processes that must be alive, what each Redis database is for, queues, the scheduler, inbound webhooks and their throttles, logging, storage, deployment steps and a symptom-to-fix table.

Rule. The application is stateless and horizontally scalable (§40, D10). Sessions, cache, queues, rate limiting and locks live in Redis; files live in S3-compatible storage; nothing persistent lives on the app server. Never switch session, cache or queue to file, sync or database drivers, even temporarily to work around a problem.

Queue names come from config, not from the worker command. A worker started without --queue processes only default.

Listeners that react to domain events live in app/Listeners and app/Domain/Notification/Listeners (for example CollectPartnerReceivableOnVerifiedPayment, ReleasePartnerReceivablesOnWalletCredit, BroadcastStoredNotification); whether each is queued was not verified here.

Gotcha: a worker must name its queues. A bare queue:work processes only default, so jobs on payments, sms and webhooks would sit unprocessed. DEPLOY.md and compose.yaml now both pass --queue=payments,webhooks,sms,default (compose.yaml also keeps sync, notifications, reports and maintenance, which match no job found under app/**/Jobs). Keep payments first so it is drained first, and add any new named queue to both files. The queue names come from config/payment.php (PAYMENT_QUEUE), config/sms.php (SMS_QUEUE), config/website.php (WEBSITE_WEBHOOK_QUEUE) and config/stores.php (STORES_QUEUE, default default); if you rename one in .env, rename it in the worker command.

Horizon was approved (D3, gated behind system.monitoring) but laravel/horizon is not in composer.json; today failed jobs are inspected with queue:failed and the failed_jobs table.

The scheduler

Everything is in routes/console.php. Every task uses onOneServer() and withoutOverlapping() (§41), backed by the isolated Redis lock database: a sweep that restricts accounts or sends messages must not run twice concurrently on two application servers. Daily tasks are pinned to app.timezone (Asia/Dhaka) so "overdue today" means the day of the person affected. Each Action is also idempotent on its own: every move is re-read under a row lock and made only from a state that permits it.

Task nameCadenceActionWhat and why
subscription-lifecycle-sweepdaily 01:30SweepSubscriptionLifecyclePackage renewal due, grace, expiry (§8.4). Early and before the KYC sweep so a term that expires today is expired before anything reasons about entitlement.
kyc-deadline-sweepdaily 02:00SweepKycDeadlinesWarn and enforce KYC deadlines (§7.4). Does nothing until an administrator sets kyc.deadline_days.
website-lifecycle-sweepdaily 02:15SweepWebsiteLifecycleWebsite grace, expiry, renewal and low balance (§16.4, §24.3). After the subscription sweep.
wallet-balance-checkdaily 02:30SweepWalletBalancesChecks every wallet against what its account must hold (§24.3); restricts and notifies. Runs before the reconciliation so an account that paid overnight gets services back first.
ledger-integrity-checkdaily 03:00VerifyLedgerIntegrityRe-derives every wallet from its ledger entries and alerts on mismatch (§28.1). Reads only and repairs nothing: silently correcting a balance would destroy the evidence of what caused the drift; corrections are new ledger rows (§23.2).
audit-log-retentiondaily 03:30PurgeAuditLogs::purgeExpiredRemoves audit entries older than audit.log_retention_days (D33). Off by default; every run that deletes anything leaves a permanent audit.logs_purged entry.
storefront-request-prunedaily 03:40 (no timezone pin)PruneStorefrontRequestsForgets stored answers to storefront writes well past the 24-hour replay window (P5-21). The orders they created are untouched.
payment-deadline-sweephourlyExpireUnpaidPaymentsCloses unpaid checkouts past billing.payment_deadline_hours (§9) and gives coupon slots back. Hourly because the deadline is in hours. Does nothing until the setting is configured; a Paid payment has no move to Cancelled.
supplier-fulfilment-confirmation-sweephourlyExpireOverdueFulfilmentCommitmentsReturns supplier fulfilment commitments past their confirmation deadline to staff review.
courier:steadfast-syncevery 5 minutescommandBackstop for a Steadfast callback that never came; bounded batch, per-parcel wait.
cod-confirmation-code-retryevery 5 minutesRetryCodConfirmationCodesResends confirmation codes the SMS provider did not take (§6.2); never resends one that reached the provider.
website-inventory-syncevery 5 minutesSyncWebsiteInventoryTells storefronts about stock that changed, sending only the change (§17.2).
referral-commission-releaseevery 5 minutesReleaseDueReferralCommissionsPays commissions whose holding period has passed and retries reversals a wallet could not carry (D24).
external-store-syncevery 10 minutesDispatchExternalStoreSyncsQueues an order sync for each live external store connection, the safety net under its webhooks (D29). Calls no store itself.
refund-settlement-sweepevery 15 minutesSettleRefund::pending() loopAsks gateways what became of refunds they accepted (§26.3). A refund that failed outright is never re-sent from here: sending money is a person's decision.
website-catalogue-syncevery 15 minutesSyncWebsiteCatalogue::sweepRe-announces storefront products that are out of date.
website-best-sellersevery 15 minutesRefreshWebsiteBestSellersRebuilds the 30-day sales summary in one transaction so sort=best_selling never aggregates orders per request (C3, D31 H5).
gateway-reconciliationevery 2 minutesReconcileGatewayPaymentsAsks each provider with a status lookup what happened to payments old enough to have finished (§28.1). Never downgrades a settled payment (a mismatch is reported, not applied); an unreachable provider leaves everything as it was.
partner-receivable-collection-sweepevery minuteReleaseCollectableReceivables::sweepCollects Banij's receivable on Partner-gateway orders a missed event left waiting, and ends holds past their deadline (D36).
stock-reservation-expiryevery minuteReleaseExpiredReservationsGives back stock held by expired reservations. Every minute because the shortest window is fifteen minutes and expiry is the scheduler's job, not lazy.
wholesale-order-payment-sweepevery minuteExpireUnpaidOrdersConfirms an ERP wholesale order whose payment settled without it, cancels (releasing stock) one whose payment failed or timed out.
cod-confirmation-sweepevery minuteExpireUnconfirmedCodOrdersCloses cash-on-delivery orders nobody confirmed and returns their stock, under the same locks a late confirmation takes.
website-webhook-retriesevery minuteDispatchDueWebhookRetriesQueues webhook deliveries whose next attempt is due (contract §7.3).
website-promotion-windowsevery minuteAnnouncePromotionWindowsAnnounces storefront promotions that opened or closed; each edge once.

Check it with php artisan schedule:list and, on the host, crontab -u www-data -l. Two comments in console.php disagree with the code and are worth knowing: the gateway-reconciliation block says "Hourly" but is registered with everyTwoMinutes(), and the referral outbox comment sits above storefront-request-prune instead of the task it describes.

Logging

LOG_CHANNEL=stack with LOG_STACK (default single). Dedicated channels (config/logging.php, §42) keep an investigation from reading every request and let retention differ. Nothing written to them may contain passwords, tokens, API secrets, gateway secrets or unmasked personal data.

The audit trail is a database table (audit_logs), append-only except for the guarded purge described in D33, not a log file. See Audit. Provider traffic is recorded in payment_logs and api_logs/webhook_logs with secrets redacted.

Backups

The spec requires weekly automatic encrypted database backups with retention and alerts, plus permission-gated manual backups (§35, roadmap phase 11). app/Domain/Backup/ contains only a .gitkeep and no scheduled task creates a backup, so no application-level backup exists today. A backup_manager platform role exists. Until the module is built, take PostgreSQL dumps and object-storage snapshots at the infrastructure level, and test a restore. The deployment-time verify commands (catalog:verify-wholesale-pricing, wallets:verify-typed-balances) are snapshots of selected values, not backups.

Inbound webhooks and throttles

Gateways and couriers cannot carry a CSRF token, so these paths are exempt in bootstrap/app.php (webhooks/payment/*, webhooks/stores/*, webhooks/courier/*) and each authenticates itself before doing any work.

POST /webhooks/payment/{gateway}/{payment}webhooks.partner-paymentSignature checked with the Partner's frozen credentials version (D36); the payment public id picks it.Same limiter.
POST /webhooks/stores/{store}webhooks.storesHMAC over the raw body under that store's own secret; store event id required and recorded once.store-webhooks: STORES_WEBHOOK_RATE_LIMIT (default 240) per minute per store and address.

They settle nothing; a return is verified with the gateway on a valid signature or an identifier we hold, then sent on with a 303.payment-returns: payment.return_rate_limit (default 30) per minute per address.

Other limits: the Storefront API is limited per credential per minute (read 600, write 120, other 300, config/website.php); the mobile API is MOBILE_API_RATE_LIMIT (default 120) per person or address, with a separate 5-per-minute limiter on second-factor guesses; the contract's clock skew (300 s) and nonce lifetime (600 s) are frozen with it. Webhooks are never processed inline: verify the signature, record, queue, answer fast (Integrations).

Security posture

  • ERP pages are no-indexed with the noindex middleware applied per route group; the public site and partner storefronts stay indexable (§34).
  • APP_DEBUG=false and APP_ENV=production; the session cookie's Secure flag derives from the environment in production.
  • Administration requires a second factor for sensitive roles; the Horizon-style queue dashboard, if added, must never be publicly reachable (D3).
  • No global security-headers middleware (HSTS, CSP, frame options) was found in app/; the matches are on file-download responses in the KYC and case-evidence controllers. If you need those headers, set them at the proxy (not verified whether production does).
  • Only .env.example is tracked. A developer's whole environment file once sat in a public repository for two weeks; TrackedEnvironmentFilesTest now guards it. Rotate any secret that has ever appeared in a commit.

Deployment

From DEPLOY.md (a VPS on Ubuntu; note that file is listed in .gitignore, so it may be absent from a fresh clone). Services: PHP (fpm, pgsql, redis, mbstring, bcmath, intl, xml, curl, zip), Nginx, PostgreSQL 18, Redis 8, Node 22, Composer, Supervisor. DEPLOY.md names PHP 8.3 (php8.3-fpm); development and CI use 8.5 and composer.json allows ^8.3.

First install

cp .env.example .env     # APP_ENV=production APP_DEBUG=false APP_URL=https://... DB_* REDIS_* (separate DBs)
composer install --no-dev --optimize-autoloader
php artisan key:generate
npm ci && npm run build:ssr
php artisan migrate --force
php artisan db:seed --class=SafeSeeder --force   # never DatabaseSeeder / DemoSeeder
php artisan storage:link
chown -R www-data:www-data storage bootstrap/cache

Every release

php artisan down
git pull --ff-only
composer install --no-dev --optimize-autoloader
npm ci && npm run build:ssr
php artisan migrate --force
php artisan optimize:clear && php artisan optimize
php artisan queue:restart
sudo supervisorctl restart feriwala-ssr
sudo systemctl reload php8.3-fpm
php artisan up
  • queue:restart makes workers pick up new code; a worker with --max-time=3600 also recycles hourly.
  • Before a migration that touches money, take a snapshot with catalog:verify-wholesale-pricing --snapshot= or wallets:verify-typed-balances --snapshot= to a protected directory outside the release, then compare with --against= after. See Commands.
  • Migrations only add or correct; a committed migration is never rewritten. See Database.
  • optimize:clear flushes the cache database only. Locks and sessions survive by design.
  • After deploy: php artisan about, php artisan schedule:list, sudo supervisorctl status, and hit /up.
  • Supervisor: stopwaitsecs=3600 lets a worker finish its job before it is killed; run two feriwala-queue processes at least. Fix the --queue list as described above.

What must never be done

  • Switch session, cache or queue drivers to file, sync or database. Not temporarily, not for a "quick" local fix.
  • Run DemoSeeder, FakeDataSeeder, FakeOrderSeeder or DatabaseSeeder against production data. (DemoSeeder and StandardKycBatchSeeder throw in production; FakeDataSeeder has no such guard.)
  • Edit or delete a ledger entry or an audit log by SQL. The database refuses ledger updates and deletes with a trigger; correct with a new adjustment, reversal or corrective row.
  • Let a cached config sit on a machine that runs tests, or run two test suites against one schema.
  • Put a second copy of a scheduled task in cron or Supervisor "to be safe". onOneServer() protects against two servers, not against you re-implementing a sweep.
  • Rotate APP_KEY casually: encrypted columns (gateway credentials, KYC, store secrets) depend on it. Use APP_PREVIOUS_KEYS for rotation.
  • Commit any .env* file other than .env.example.
