Getting started

From a fresh WSL Ubuntu shell to a running Feriwala ERP you can log into: prerequisites, installation, environment, Redis layout, seeding, local media, the dev processes and the errors people hit on the first run.

Rule. Local development is native: PHP, PostgreSQL, Redis and Node run directly in WSL Ubuntu and the app is served by php artisan serve (decision D5, amended twice). Docker and Sail are not a development path and nothing may come to require them. compose.yaml is a production-parity reference only.

Install the services

scripts/setup-dev-environment.sh installs PostgreSQL and Redis from Ubuntu apt, enables both services, creates the feriwala role and database, and creates the testing schema the test suite uses. It is safe to re-run. It asks for your sudo password once.

bash scripts/setup-dev-environment.sh

The script's database password defaults to a placeholder and can be overridden with DB_PASS=... bash scripts/setup-dev-environment.sh. Whatever it is, DB_PASSWORD in your .env must match it. The role owns the database, so it can create schemas without CREATEDB.

Clone and install

git clone <repo> ~/projects/feriwala
cd ~/projects/feriwala
composer setup

composer setup is a script in composer.json. In order it runs:

  1. composer install
  2. copies .env.example to .env if .env does not exist
  3. php artisan key:generate
  4. php artisan migrate --force
  5. npm install
  6. npm run build (vp build)

Gotcha. Step 4 needs PostgreSQL running and the DB_* values in the freshly copied .env to be right. .env.example already points at 127.0.0.1:5432, database and user feriwala, so it works as-is after the setup script if the password matches. If step 4 fails, fix .env and run the remaining steps by hand; the script is not resumable.

.env is gitignored along with every .env.* except .env.example; a test (TrackedEnvironmentFilesTest) fails the build if another environment file is ever tracked. Never commit one.

Redis databases

One Redis server, five logical databases, defined in config/database.php:

ConnectionEnv variableDefault DBCarries
defaultREDIS_DB0Anything that uses the unnamed connection.
cacheREDIS_CACHE_DB1The cache store and, through CACHE_LIMITER=redis, the rate limiter.
queueREDIS_QUEUE_DB2Queued jobs.
locksREDIS_LOCK_DB3Distributed locks and idempotency guards (DistributedLock, onOneServer, withoutOverlapping).
sessionREDIS_SESSION_DB4Sessions.

Why separate. cache:clear flushes a whole Redis database. Locks have their own database so a cache flush cannot drop a lock guarding a financial operation or a duplicate-payment guard. Sessions have their own so a routine cache flush on deploy does not sign every user out. The rate limiter sits on Redis, not the local node, so adding web servers does not multiply the attempts an attacker gets (§6, §40).

Gotcha. The connection names are chosen by env variables whose code defaults are default: REDIS_CACHE_LOCK_CONNECTION (config/cache.php) and REDIS_QUEUE_CONNECTION (config/queue.php). .env.example sets them to locks and queue. An environment that omits those two lines quietly puts cache locks and the queue on database 0. Copy them from .env.example into every environment. SESSION_CONNECTION=session is likewise set in the template.

Rule. Never switch session, cache or queue to file, sync or database drivers, even temporarily to dodge a local problem. The application must stay stateless and horizontally scalable (§40, D10). Diagnose the real problem (Redis not running, wrong port) instead.

Local media: storage:link and APP_URL

With R2 not configured, product images go to the local public disk and their URLs are {APP_URL}/storage/catalog/products/.... Three things must hold for those URLs to load:

  1. php artisan storage:link has created public/storage (the link is gitignored, so every checkout needs it).
  2. APP_URL is the origin the app is actually served on, port included: http://127.0.0.1:8000 for php artisan serve, not a bare http://localhost. The public disk builds its URL from APP_URL (config/filesystems.php).
  3. Anything outside your machine, such as a preview storefront, can load them only if that origin is reachable from it over HTTPS.

Each product_media row records its own disk, so a later move to R2 changes new uploads only; the storefront payload resolves every URL from the row's disk. KYC, supplier-media and generic private files use private disks with serve off and are only ever read through a controller that checks permission.

Run it

composer dev        # same as: php artisan dev

composer dev runs php artisan dev, the framework's multiplexer (Illuminate\Foundation\Console\DevCommand). It starts these processes, each with its own tab (on Windows it falls back to concurrently):

NameCommandNotes
serverphp artisan servehttp://127.0.0.1:8000 by default.
queuephp artisan queue:listen --tries=1 --timeout=0Listens on the default queue only. Jobs that use the payments, sms or webhooks queues are not processed by it. See below.
logsphp artisan pail --timeout=0Only when pcntl and Pail are present.
vitenpm run dev (vp dev)Vite dev server; it also runs the Wayfinder plugin (with form variants) and writes public/hot.
reverbphp artisan reverb:startRegistered by laravel/reverb; port 8080.

Flags: -s stream mode, -t tabs, -i inline, --timestamps, --no-restart, --json. php artisan dev:list shows what would start. The scheduler is not part of dev; run php artisan schedule:work in another terminal when you need a sweep to fire.

Gotcha. Online-payment settlement, SMS and website webhooks are queued on named queues. To exercise them locally run a worker for those queues in a spare terminal: php artisan queue:work --queue=payments,default,sms,webhooks. See Operations for the queue list.

Creating a Super Admin outside the demo data

No console command creates one. SafeSeeder creates no users and DemoSeeder refuses to run in production. The mechanism the demo seeder itself uses is a plain Spatie role assignment: create or pick a verified User with no business account (Account, decision D23) and call $user->assignRole('super_admin') after RolesAndPermissionsSeeder has run. How the first production Super Admin is provisioned is not documented in the repository (not verified).
