Conventions

The non-negotiables explained: why each exists, which class enforces it, and what a correct change looks like. Followed by the everyday coding conventions, where files go, and the lang rules. If a rule here seems wrong for your task, raise it; do not route around it.

1. Money is flat Taka, never a float

Why. A ledger that must reconcile to the last paisa cannot tolerate float drift (0.10 has no exact binary form). Feriwala previously used a minor-unit (poisha) convention; D26 withdrew it. 100 now means BDT 100 at every layer and nothing multiplies or divides by 100 to cross a boundary.

PieceClass / fileRole
Value objectApp\Support\Money\MoneyImmutable. Holds an exact decimal Taka string plus a Currency; all arithmetic through bcmath. API: fromDecimal(), zero(), plus(), minus(), multipliedBy(), percentage(), allocate(), negated(), absolute(), comparisons (equals, greaterThan, lessThan...), toDecimal(), format(), jsonSerialize(). Currency mismatches are rejected; every percentage and multiplication takes an explicit RoundingMode (default HalfAwayFromZero).
CurrencyApp\Support\Money\CurrencyEnum: BDT, USD, EUR, GBP. Currency::base() is BDT; scale() and symbol().

// Controller: parse once at the HTTP boundary
$validated = $request->validate(['amount' => ['required', new DecimalAmountRule]]);
$amount = DecimalAmount::parse($validated['amount']);   // Money, or InvalidDecimalAmount

// Action: receives a Money, never a string or float
$total = $line->unit_price->multipliedBy($quantity)->minus($discount);
[$shareA, $shareB] = $total->allocate([60, 40]);        // reconciles to the exact total

// Inertia: the server's own rendering

Rule. Prohibited for financial values: float, double, round(), number_format(), _minor names, minor_units, poisha conversion helpers, a ×100 or ÷100 on money, float/double money columns. Allocating tax, discount, commission or a refund across lines uses allocate() so parts sum to the whole.

How the repository guard tests enforce it

Two Pest files fail the build when the rules are broken:

  • tests/Unit/Support/Money/MoneySourceGuardTest.php scans production source (app, database/factories, database/seeders, lang, and resources/js excluding .test. files) line by line. It fails on: a call to the removed Money::of(; a ->minorUnits read; any identifier ending _minor; the key minor_units outside an allow-list; a .decimal read in React; a (float)/(double) cast near an amount-like word, and floatval()/doubleval(). It also contains a self-test proving each pattern can fail, and asserts it scanned a real body of files so an empty scan cannot pass.
  • tests/Feature/Payment/MoneyColumnConventionTest.php guards the schema: every inventoried money column is exactly NUMERIC(19,2), has a currency relationship (documented exemptions aside), every money-shaped column in the schema is classified, no column keeps the minor-unit name, and defaults are zero.

Allow-list. minor_units is allowed only in the frozen Storefront API compatibility adapter (Api/Storefront/V1/OrderController.php, StorefrontController.php, Website/Api/StorefrontProductPayload.php, plus a docblock in Money.php), per requirements/05-storefront-api-contract.md §4.1. Each allow-list entry must name its reason. New internal code may not read or write it. Note the guard is a text scan: it does not catch every possible ×100, so review money arithmetic by eye as well.

2. Ledger entries are immutable

Why. A record that can be edited afterwards is not evidence. The wrong figure and its correction must both be visible (§23.2).

  • Model guard. App\Domain\Wallet\Models\LedgerEntry::booted() throws a RuntimeException on updating and deleting.
  • Database guard. Migration 2026_09_16_120000_protect_ledger_entries.php creates the trigger function feriwala_ledger_is_append_only(), so a raw SQL update from anywhere fails too. Supplier ledger: feriwala_supplier_ledger_entries_immutable() (2026_10_04_100000_take_supplier_wallets.php). Status history: feriwala_status_history_is_append_only().
  • Corrections are new rows. Wallet\Actions\CorrectLedgerEntry offers reverse() (mirror entry pointing at the original) and adjustments, each idempotent, each audited. corrects_ledger_entry_id links the correction.
  • Detection. Wallet\Actions\VerifyLedgerIntegrity re-derives every wallet from its ledger and checks each entry's balance_before + movement = balance_after and the chain between entries.
  • Debit and credit are both stored positive in separate columns; a misplaced minus can never become a credit. internal_note is staff-only and is $hidden; member statements select LedgerEntry::MEMBER_VISIBLE.
  • Audit logs follow the same rule (AuditLog, AuditLogIsImmutable), with exactly one exception: the guarded purge in D33 (PurgeAuditLogs), Super Admin only, which always leaves a permanent audit.logs_purged record. Ledger entries have no exception.
  • Status history rows use App\Concerns\AppendOnlyStatusHistory: updating and deleting throw a LogicException.

3. The financial mutation recipe

Every financial mutation (a) runs inside a database transaction, (b) takes a row lock, (c) is idempotent when externally triggered, and (d) writes a ledger entry in the same transaction. App\Domain\Wallet\WalletService is "the only thing that moves money in a wallet"; Actions call it rather than writing wallet columns.

  1. Build a posting context. Wallet\Data\PostingContext carries source, description, an idempotencyKey derived from something stable ('payment:'.$payment->reference), and links (paymentId...).
  2. Fast path. findByKey(): if the command already ran, return what it produced. A retry costs nothing.
  3. Transaction + lock. $this->database->transaction(...) then Wallet::query()->lockForUpdate()->findOrFail(...). Insufficient-balance checks happen inside the lock, because only the re-check under the lock knows whether another debit got there first.
  4. Write balance and entry together. Update the wallet, write the LedgerEntry rows (with balance_before/balance_after), append a WalletTransactionEvent. Two kinds of money (platform credit and withdrawable) each get their own entry when a posting spans both.
  5. Unique index as the final guard. The idempotency key is unique; a racing duplicate raises UniqueConstraintViolationException, the whole transaction rolls back, and the winner's transaction is returned to both callers.
  6. Announce after commit. Events such as WalletCredited fire after the posting is durable, so a listener sees the new balance and cannot hold the posting open.
  7. Audit. Sensitive actions record through Audit\Actions\RecordAuditLog (see below).

4. Statuses move through transitionTo()

Why. Feriwala has very large status sets (22 account, 28+ order, 14 website...). Declaring legal moves beside the states stops a Refunded order being dragged back to Processing.

  • App\Support\StateMachine\TransitionableState is the interface status enums implement: transitionsTo(): array, label(): string, isTerminal(): bool.
  • App\Concerns\HasStateMachine gives the model currentState(), canTransitionTo(), transitionTo() and availableTransitions(). An illegal move throws IllegalStateTransition. transitionTo() does not persist; the caller saves it inside the same transaction as the ledger entries and history. A model with several independent lifecycles (an order's status and its fulfilment status) passes the $attribute explicitly.
  • App\Concerns\RecordsStatusHistory adds transitionWithHistory(): move + history row in one transaction (previous, new, changed_by, changed_at, reason, internal_note, public_note), using Support\StatusHistory\StatusChange. Locking the subject row first is the caller's job. recordStatusChange() writes the first status of a new row.
  • App\Support\Status\HasTranslatedLabel gives label() by looking up status.<group>.<value> in lang/{en,bn}/status.php; the enum supplies statusLabelGroup(). Never hard-code English in label().
enum WalletTransactionStatus: string implements TransitionableState
{
    public function transitionsTo(): array
    {
        return match ($this) {
            self::Initiated => [self::Pending, self::OnHold, /* ... */ self::Cancelled],
            self::Pending   => [self::OnHold, /* ... */ self::Settled, self::Failed, self::Cancelled],
            // terminal states return []
        };
    }
}

// In an Action, inside DB::transaction(), after lockForUpdate():
$order->transitionWithHistory(OrderStatus::Confirmed, new StatusChange(actorId: $user->id, reason: $reason));
// or StatusChange::bySystem($reason) when no person made the move

Rule. Never write $model->status = .... The specification also allows admin-defined order statuses (§18.2); check the Order module page before adding a status.

5. Self-scoping is a query concern

Why. Hiding a row in a template still ships it to the browser and returns it from an export. §31.3 forbids reaching another user's data through a URL, an API call, an export or a modified parameter.

  • Resolver. App\Domain\Access\DataScopeResolver::for($user, PermissionModule) returns DataScope::All only if the viewer holds <module>.view; otherwise Own for a user, None for a guest. canExport() and canSeeSensitive() check <module>.export and .view_sensitive_data separately.
  • Trait. App\Concerns\ScopedToViewer adds scopeVisibleTo($viewer) (Order::visibleTo($user)->paginate()); a viewer without entitlement gets whereRaw('1 = 0'), an empty list rather than a leaked error. A model declares scopeModule() and optionally ownerColumn() (default user_id).
  • In practice (verified by grep): at the time of writing no model in app/ uses the ScopedToViewer trait. Self-scoping is done by resolving the account from the membership (ResolvesBusinessAccount::businessAccountFor()) and constraining queries by business_account_id, with Queries/ classes owning the read models. Either way the rule is the same: scope in the query, resolve public ids inside the caller's scope (see WalletController::transaction(), which filters wallet_id before using the public id, so a borrowed id answers 404).
  • No account identifier appears in ERP URLs; there is nothing to swap for someone else's.
  • Every model has a Policy. They are registered in AuthorizationServiceProvider. A Gate::before grants the Super Admin override and refuses a non-User authenticatable outright.

Gotcha (account-access rule). BusinessAccountPolicy::view is true for a member; it must never guard an admin screen. Administrative screens about an account authorize viewDossier, which treats membership as a refusal and requires the platform account.view permission. See .ai/rules/account-access.md.

6. Only admins create products

Why. The catalog is the platform's (§11, §12, product ownership is architecture-locked). Regular users select from it; suppliers submit listings and offers but never own catalog products (D25).

7. Merchant of record and payment direction

  • For dropshipping, Feriwala verifies payment, controls inventory, fulfilment, courier and COD reconciliation, and credits the partner's earning to the wallet (D12). Retail margin is a commission calculation base, not a separate money path.
  • Webhooks never decide money. PaymentWebhookController records the message, queues SettleGatewayNotification, acknowledges identically for every non-signature outcome, and the job asks the gateway directly. Billing\Actions\SettlePayment is the only thing that decides a payment was made.
  • D36 caveat. Where Admin allows it, a partner-owned gateway (Model B) may receive the customer's payment; the partner's credentials are a separate, versioned, encrypted store, and a payment points at the exact version it started with. This is a recorded amendment, not a loophole: do not add partner-gateway paths outside the D36 design. Credentials of any gateway never appear in logs (RecordAuditLog::REDACTED and per-driver redaction).

9. Audit

Sensitive actions write through App\Domain\Audit\Actions\RecordAuditLog::handle(AuditEntry), the single way audit rows are created. It redacts at any nesting depth any key containing password, secret, token, api_key, private_key, credential, authorization, signature, cvv, card_number, pin, otp, remember_token (§42). Rows carry actor, action, before/after, reason, IP, account and module. Viewing needs audit.view_audit_logs.

Coding conventions

PHP

  • Always use curly braces for control structures, even one-line bodies.
  • PHP 8 constructor property promotion (public function __construct(protected WalletService $wallet) {}); no empty zero-parameter constructors unless private.
  • Explicit return types and parameter types on every method.
  • PHPDoc over inline comments; inline comments only for exceptionally complex logic. Use array-shape types in PHPDoc (@return array{token: string, expires_at: CarbonInterface|null}).
  • Descriptive names: isRegisteredForDiscounts, not discount(). Follow the naming of sibling files, including Enum naming.
  • Create files with php artisan make:… --no-interaction; a new model comes with a factory and seeder. Prefer named routes and route().
  • Do not change dependencies without approval; do not create new base folders.
  • Pint (preset laravel in pint.json): run vendor/bin/pint --parallel. Another session may share your tree and --dirty formats every uncommitted file, so prefer explicit file arguments when unsure.
  • PHPStan level 8 with Larastan; run it through composer types:check (it calls scripts/phpstan.sh), never vendor/bin/phpstan directly. The baseline phpstan-baseline.neon holds starter-kit debt only and must never grow.

Tests

  • Pest. Every code change adds or updates a test; run the narrowest slice. Groups are declared in tests/Pest.php (pest --group=wallet).
  • Pest loads all test files into one global function namespace, so prefix every helper with what it belongs to (moneyGuardHits(), dataScopeResolver()) or define it inside the test closure. A bare function session() redeclares a Laravel helper and takes the whole suite down.
  • Use model factories and their states. Full guidance on the Testing page.

Language files (en / bn)

  • User-facing strings in PHP go through __(); in React through useTranslation().t('group.key'). Lines live in lang/en/*.php and lang/bn/*.php (about 50 files, e.g. common.php, nav.php, status.php, wallet.php).
  • Status enum labels use HasTranslatedLabel and status.<group>.<value>; a missing Bangla line falls back to a humanized value, not a raw key.
  • Case workflow refusal codes need cases.errors.<code> in both en and bn; tests/Feature/Cases/CaseTranslationsTest.php fails on a missing Bangla line (.ai/rules/lang.md).
  • The front end receives the active locale's tree as the shared translations prop, with English as fallback (HandleInertiaRequests::translations()). See Frontend.
  • Known debt: page breadcrumb titles are hard-coded English (.ai/rules/ui-surfaces.md); do not patch piecemeal.

Working rules worth remembering

  • Read .ai/rules/index.md and every rule file whose globs cover the path before editing; record new durable rules with the Boost record-rule tool rather than a personal note.
  • Markdown files have their own rule: a bare vp check --fix reformats .md files repo-wide; pass explicit paths.
  • Never document or commit secrets; name environment variables only.
