Decision log

A condensed restatement of every decision in requirements/04-decisions.md (D1 to D36), what is still open in 99-open-questions.md, and the roadmap phases in 03-roadmap.md. The source file is authoritative; read it before relying on a detail here.

Rule. Decisions marked locked in the source (merchant of record, financial ledger, payment direction, storefront separation, single account structure, product ownership, wallet settlement, referral rewards) must be raised for approval before implementation. Nothing here changes without explicit written instruction, and the Storefront API contract is frozen at v1.

Numbering traps. The source has two decisions headed D30: the shared multi-tenant storefront (2026-10-12, superseded by D32) and KYC verification batches as versioned templates (2026-10-14). The activity-log decision is D33; it was recorded as D29 on main and renumbered, so about eight code comments still cite "D29" for the audit purge. D34 appears in the file after D30 (KYC) and D36 is dated before D35. Code comments also cite a "D-new" for the Non-Conditional rule that D34 later replaced. When a comment cites a D-number, check which decision it means.

Amendment chains at a glance

  • Money: D4 (decimal or minor units) is amended by D26 (flat Taka) and by the exchange-rate amendment; D24's integer-poisha arithmetic is superseded in representation by D26.
  • Accounts: D1 is amended by D23; D22 by D27; D25 adds a second, separate domain.
  • Storefront: D10 and D11 are amended by D30 (storefront) then D32; D12 step 4 by D30; D12 Model B by D36; D29 by D30.
  • Audit: the append-only audit rule is amended by D33.
  • Wholesale: D34 replaces the undocumented "D-new" rule.

Roadmap phases (03-roadmap.md)

Thirteen phases in dependency order, each ending in working, tested software, with progress tracked in requirements/TODO.md rather than as a percentage. Storefront API contract design was moved from phase 5 up into phase 0 (task P0-53) so the contract is frozen before anything depends on it.

PhaseScopeWhy in this position / done when
P0Foundation and infrastructurePostgreSQL, Redis, Money, RBAC, audit log, settings registry, queues and a multi-server-safe scheduler, CI, the ERP shell and DataTable, design tokens. Retrofitting any of these is a rewrite.
P1Identity, KYC, packages, activationThe funnel every feature sits behind. Done when a user registers, verifies, submits KYC, picks a package, pays and is activated automatically (D27) with correct pre-activation restrictions (§5.4).
P2Money coreWallet, ledger, deposit rules, all eight gateways behind the driver contract, concurrency proof of no double-spend or duplicate payment.
P3Central catalog and inventoryCatalogue, statuses, stock buckets, transaction-safe reservations, and the product-restrictions test group (§12).
P4ERP wholesale browse, cart, checkoutFirst revenue path; exercises catalog, inventory, payments and orders end to end.
P5Dropshipping selection and dedicated websitesThe largest phase (about 50 tasks): selection, publishing within bounds, website lifecycle, API and webhook layer, isolation test. Flagged for possible splitting.
P6Order management, fulfilment, courierComplete the unified OMS against real inputs: statuses and transition map, invoices, fulfilment, pluggable couriers.
P7Commission, referral, withdrawal, COD settlementAll compute from delivered orders and write to the wallet, so correct only after P2 and P6. Includes the multi-level referral programme (D24).
P8Notifications and SMSThe events it reacts to now exist; four SMS providers behind one contract, bilingual templates, controls at several levels.
P9Reports and analytics56 admin and 21 self-scoped reports with filters, exports and the access-isolation tests.
P10CMS, landing page, SEOIndependent of ERP domains; can run in parallel with P4 to P9.
P11Security, performance, scalability, backup, monitoringHardening against the finished system: weekly encrypted backups, audit coverage, stateless verification, health endpoints.
P12Final QA, accessibility, documentation, launch readinessEvery §43 test item covered, accessibility and responsive checks, §44 and §45 walked through, runbook and recovery documentation.

The roadmap marks P0 to P2 as foundations, treats SMS (needed at registration) and payments (needed at activation) as minimal slices built early and completed later, and keeps P8 and P10 off the strict linear path. What has actually been built is far ahead of the file's text: for example app/Domain/Backup is still empty (phase 11), and Horizon is not installed. Check requirements/TODO.md for current status.
