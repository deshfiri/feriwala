Database

PostgreSQL 18 is the only supported database. This page covers what the schema relies on, the migration history grouped by area, the conventions every table follows, the guards the database enforces on its own, a map from table families to module pages, and how to write a migration here without breaking any of it.

PostgreSQL specifics

  • PostgreSQL only. .env.example says "Do not switch to SQLite/MySQL" (requirements.txt §2, §37). The schema uses plpgsql trigger functions, partial unique indexes, CHECK constraints, jsonb and numeric(19,2); none of that ports.
  • Search path. config/database.php reads DB_SEARCH_PATH (default public). Development and production use public; tests use a testing schema in the same database. A cached config pins the search path, which is why config:clear matters before tests (Testing).
  • Role. The application role owns its database and can create schemas but has no CREATEDB privilege.
  • Row locking (lockForUpdate(), SELECT ... FOR UPDATE) is how every financial mutation and every stock change serialises. Transactions that take many table locks, such as RefreshDatabase dropping every table, can exhaust max_locks_per_transaction, so one test run at a time.
  • JSON columns are jsonb, never json.
  • Local file. database/database.sqlite is a starter-kit remnant (post-create-project-cmd); the application does not use it.

What the database enforces by itself

Application guards (model events, policies) do not fire for DB::table(...)->update(), tinker, a seeder or a psql prompt. For rules that must hold for every writer the rule is a trigger or constraint. Names follow feriwala_* for functions.

Seeders and factories

Seeders are in database/seeders and are documented, with what is safe in production, in Getting started: RolesAndPermissionsSeeder, SafeSeeder, DemoSeeder, StandardKycBatchSeeder, FakeDataSeeder, FakeOrderSeeder, CategorySeeder and the starter kit's DatabaseSeeder. Seeders that must be re-runnable use updateOrCreate or an importer that upserts by natural key. Only SafeSeeder is production-safe by design.

Most other fixtures are built through the real Actions by the helpers in tests/Pest.php, on purpose; see Testing. New models get a factory and a seeder (project guideline).

The money column convention test

tests/Feature/Payment/MoneyColumnConventionTest.php keeps an explicit MONEY_COLUMN_INVENTORY (table to money columns) matching D26's conversion map. It checks every listed column is numeric(19,2), that the table has a currency_code (unless in MONEY_COLUMN_CURRENCY_EXEMPTIONS with a reason), and that no money-shaped column exists that is not registered. The old design found money columns by the %_minor name, which would have passed vacuously once the suffix was gone; the inventory fails closed instead. Adding a money column to a table without registering it is a failing test. The inventory does not yet cover every money column; a note in the file says the older order_proceeds_settlements columns are a known gap.

Writing a safe migration here

  1. Create with Artisan. php artisan make:migration create_x_table --no-interaction. Name the file after the latest existing migration so it runs last (the D36 chronology note).
  2. Never edit a committed migration. Add a new one. If an old one is wrong and cannot be fixed, ignore it narrowly in phpstan.neon with a comment, as was done once.
  3. Money: $table->decimal('amount', 19, 2) plus $table->string('currency_code', 3)->default('BDT'). Register the column in MONEY_COLUMN_INVENTORY. Cast it with MoneyCast on the model. Never bigint, float or a _minor name; MoneySourceGuardTest scans app, factories and seeders (not historical migrations).
  4. Public identity: add $table->ulid('public_id')->unique() and use HasPublicId; use the id nowhere in URLs.
  5. Statuses: a string column, a CHECK (status IN (...)) named *_status_known, a status enum implementing TransitionableState, and a history table with feriwala_status_history_is_append_only() attached for UPDATE and DELETE when the spec wants history.
  6. Immutable data: put the guard in the database, not only the model: a BEFORE UPDATE/DELETE trigger through DB::unprepared(...) (see protect_ledger_entries for the template). Ledger-style rows get both an update and a delete trigger and have no exception. Use feriwala_catalogue_columns_are_locked('col', ...) for identity columns.
  7. One live owner / one default: a partial unique index (CREATE UNIQUE INDEX ... WHERE ...), not application checks alone.
  8. Altering a money or locked column. ALTER COLUMN ... TYPE is refused on any column named in a BEFORE UPDATE OF trigger, so drop and recreate those triggers around it. Trigger functions resolve locked column names from string arguments that PostgreSQL does not rewrite on rename, so a guard left pointing at an old name fails open silently: recreate every guard with the new names. A multi-column CHECK is validated after each ALTER COLUMN clause, so alter all of a table's related columns in one ALTER TABLE. ALTER TABLE does not fire row triggers, so no immutability exception is ever needed. Convert numeric scale by multiplication, not division (value::numeric / 100 can silently drop decimals for 19-digit values). See the header of 2026_10_05_100000_convert_monetary_storage_to_flat_taka.
  9. Backfills must be exact, idempotent (check before acting) and must not guess. D28 rules out name-matching free-text addresses to bd_locations.
  10. Reversible and additive where possible: implement down(), drop triggers before functions. Existing rows must stay valid; new columns are nullable or defaulted, then tightened in a later migration once backfilled (the users.public_id history is the cautionary tale).
  11. Test it. Add or update a test (group database for schema guards) and run the narrow slice in your own schema. For money-changing migrations on populated databases, use the --snapshot/--against verify commands in Commands around the release.
  12. Run it with php artisan migrate locally; production uses migrate --force in the release steps (Operations).

Rule. Ledger entries (ledger_entries, supplier_ledger_entries) are immutable with no exception, and every financial mutation runs in a transaction with row locking and writes a ledger entry. A migration that needs to "fix" a ledger value adds a corrective row through the application's Actions; it never updates one.
