Route name conventions

  • ERP: <area>.<resource>.<action> with no prefix: wallet.show, wallet.top-up.create, kyc.create, wholesale.orders.*, websites.*, cases.returns.*, subscription.renew.pay. Area names are the gate's allow-list keys.
  • Admin: every route is admin.<area>.<action> (admin.activity-log.index, admin.roles.store, admin.catalog.*, admin.inventory.*). The admin. prefix is load-bearing: DefaultReasonUnlessSecurity and config/reasons.php match on it, and the catalog/inventory 403 pages in bootstrap/app.php match admin.catalog.* and admin.inventory.*.
  • Supplier: supplier.<area>.<action>. bootstrap/app.php uses routeIs('supplier.*') to send a guest to supplier.login and a signed-in Supplier to supplier.dashboard.
  • Mobile: mobile.v1.<module>.<action> (suppliers mobile.v1.supplier.<module>...). The name also decides the Swagger tag.
  • Storefront: storefront.v1.<resource>.<action>.
  • Webhooks: webhooks.payment, webhooks.partner-payment, webhooks.stores, webhooks.courier.steadfast.
  • Standard resource verbs: index, show, create, store, edit, update, destroy. Register literal segments (roles/create, products/facets) before wildcard ones (roles/{role}) so the literal wins.
  • Parameters are public ULIDs or slugs, never database ids (HasPublicId, HasSlug). ERP URLs carry no account segment.

Form requests, policies and Gates

Form Requests

Under app/Http/Requests, grouped by area: Account, Catalog, ContentLibrary, Kyc, Package, Settings, Mobile/**. The codebase is mixed: many controllers validate inline with $request->validate() (for example Erp\WalletTopUpController), the newer or larger forms use Form Requests. Follow the sibling controller. In either style, money fields use DecimalAmountRule and are parsed once with DecimalAmount::parse().

Policies and permissions

  • Policies live with their domain (app/Domain/<Module>/Policies) and are registered in App\Providers\AuthorizationServiceProvider with Gate::policy(Model::class, Policy::class).
  • Permissions are named <module>.<action> from App\Domain\Access\PermissionCatalogue (PermissionModule x PermissionAction). PermissionCatalogue::name($module, $action) throws for a pair that is not in the catalogue matrix, so add it there first. Custom, database-backed roles and permissions are managed by ManageCustomRole and ManageCustomPermission.
  • Gate::before in AuthorizationServiceProvider implements the Super Admin override, and refuses anything that is not a User (a Supplier holds no platform permission).
  • Some policies expose static helpers (CatalogPolicy::canCreate($user), CatalogPolicy::authorize()) used by controllers and form requests alike.
  • Sensitive actions (§32.2) go through App\Domain\Access\SensitiveActionGuard with SensitiveActionRequest.
  • Reasons. DefaultReasonUnlessSecurity fills "No reason given." on admin.* (and a few partner) routes except those in config/reasons.php's required_for (who can do what, sign-ins, suspensions, manual money moves). The mobile counterpart is mobile.reason.

API documentation (Scramble)

App\Providers\ApiServiceProvider configures two OpenAPI documents generated from the routes, Form Requests, API Resources and controller PHPDoc, so they cannot drift from the code:

  • The intro text of each document is docs/api/mobile.md and docs/api/storefront.md.
  • Access: the viewApiDocs Gate. Open when config('scramble.public') (env API_DOCS_PUBLIC) is true; otherwise only a Super Admin or System Administrator (RestrictedDocsAccess). Per the config comment it is also open locally.
  • Tags come from the route name: mobile.v1.wallet.transactions.show is "Wallet"; mobile.v1.admin.orders.index is "Admin · Orders"; mobile.v1.supplier.* and mobile.v1.wholesale.* (Cart, Checkout, Orders) likewise. Naming a route is how it is filed (ApiServiceProvider::tagFor()).
  • config/scramble.php api_path is api/mobile/v1 for the default document; the storefront document is registered with Scramble::registerApi('storefront', ...).

Wayfinder-generated route helpers

Wayfinder turns Laravel routes into typed TypeScript. The output directories resources/js/actions (per controller), resources/js/routes (per named route) and resources/js/wayfinder are generated and git-ignored; the Vite plugin (wayfinder({ formVariants: true }) in vite.config.ts) regenerates them during npm run dev.

php artisan wayfinder:generate --with-form

Gotcha. Always pass --with-form. A bare wayfinder:generate omits the .form helpers that dozens of pages call (login().form) and breaks tsc --noEmit in ~40 unrelated files with Property 'form' does not exist (.ai/rules/actions.md). A new route is invisible to the front end until you regenerate. If the dev server is not running and a page imports a route that is not generated, TypeScript fails, not PHP.

Usage: import { show } from '@/routes/wallet' or import WalletTopUpController from '@/actions/App/Http/Controllers/Erp/WalletTopUpController'. Controller actions are also generated, so renaming or moving a controller changes its import path. See Frontend.

Inertia shared props (HandleInertiaRequests)

Every Inertia response carries these props. They resolve the one identity the route asked for: on a supplier route auth.user is null and only the supplier is shared; otherwise only the web user. A browser can hold both sessions, but a page never carries the other person's profile.

PropValue
nameconfig('app.name')
brandingLogo and icon addresses, accent colours (Branding::toArray()), never a storage path.
auth.userThe signed-in User (null on supplier routes).
supplierAccountBusiness name, reference, status, status label, operational, unread count, only for a Supplier.
impersonation{kind, name} while an admin views a partner or supplier dashboard.
sidebarOpenFrom the sidebar_state cookie.
accountThe viewer's own business account (AccountContext::forUser); null for staff without one. Not a list, so no one builds a switcher.
locale{current, direction, available}.
translationsLazy closure; the active locale's lang/<locale>/*.php tree merged over English.
permissionsA short { 'module.action': bool } map for navigation, from NAVIGATION_ABILITIES.
notifications, unreadNotificationCountHeader bell, lazy.
realtimeChannelThe private channel name this person may listen on.

Closures are lazy: they run once per full page load and are skipped on partial reloads that do not ask for them.

Gotcha: a page prop must not shadow a shared prop. Page props are merged over shared ones, so a page that returns its own account silently overwrites the viewer's account for the whole shell (.ai/rules/account-access.md). The admin account detail screen returns its subject as business for exactly this reason; when it was account, the sidebar named the business being looked at and the "My business" group appeared for platform staff. Nothing failed; it just lied. Before naming a page prop, check HandleInertiaRequests::share() (name, branding, auth, supplierAccount, impersonation, sidebarOpen, account, locale, translations, permissions, notifications, unreadNotificationCount, realtimeChannel, and Inertia's own errors/flash).

Gotcha: a navigation link needs its ability shipped. permissions is an explicit list, not the user's whole permission set (161 entries would ship the access model to every browser). A link gated on a key that is not in NAVIGATION_ABILITIES reads undefined and silently never appears, even for a Super Admin who can open the page by URL. Add the entry when you add the nav link; tests/Feature/Ui/NavigationPermissionsTest.php fails if one is missing.

How to add a page-backed route

  1. Add the Action in app/Domain/<Module>/Actions, and a Policy method or permission.
  2. Add the controller method in the right folder (Erp, Admin, Supplier), validating (parse money with DecimalAmount), authorizing and delegating.
  3. Register the route in the right group in routes/web.php, named by the conventions above. ERP route that must work before activation: name it under an allowed prefix.
  4. Regenerate Wayfinder (php artisan wayfinder:generate --with-form or npm run dev).
  5. Add the page under resources/js/pages/<area>/, import the typed route, add lang/en and lang/bn lines, and the nav entry plus its NAVIGATION_ABILITIES row if it is a menu item.
  6. Add a feature test (authorization failure included) and run vendor/bin/pest <file> in its own schema.
