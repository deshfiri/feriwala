Mobile API

The JSON API behind the Feriwala mobile app, served at /api/mobile/v1. It acts for a signed-in person with a Sanctum bearer token, is self-scoped exactly like the web ERP, and reuses the same Actions, Queries and policies. This page explains how it works and how to add an endpoint; the endpoint-by-endpoint reference is generated live at /docs/mobile.

Authentication

Partner, staff and business logins (User)

  1. POST /api/mobile/v1/auth/login (mobile.v1.auth.login, LoginController) with email, password and device_name (max 100 characters, shown in "my devices"). Unauthenticated.
  2. Same rules as the web login: the same failure throttle (LoginThrottle through Fortify's LoginRateLimiter; only failed attempts count: 5 per minute per email and 30 per quarter-hour per address, answering 429 with Retry-After), the same identity gate (hasPlatformAccess()), the same second factor.
  3. No 2FA: 200 with {two_factor_required: false, token, token_type: "Bearer", expires_at, user}.
  4. 2FA on: 202 with {two_factor_required: true, challenge_token, expires_in} (5 minutes, held in cache). Finish with POST /auth/two-factor-challenge (mobile-two-factor limiter, 5 per minute keyed on the challenge) sending challenge_token plus a six-digit code or one recovery_code (spent on use). The success body is the same as above.
  5. Send Authorization: Bearer <token> on every other call. IssueMobileAccessToken issues one token per device name: signing in again on a device replaces its token.
  6. A suspended login gets 403 {code: "account_unavailable"} and its token is revoked on the next request (a bearer token outlives its issue, so the gate bites immediately).

Suppliers (Supplier, D25)

Suppliers are a separate account domain with their own tokens (Supplier uses HasApiTokens). POST /supplier/auth/login (mobile.v1.supplier.auth.login, SupplierSessionController::store, SupplierLoginRequest) returns {token, token_type, expires_at, supplier}; it is throttled like the main login. A suspended supplier may sign in to read its own status; only a closed one loses access. Token routes: GET /supplier/auth/me, POST /supplier/auth/logout.

Rule. A token for one audience is refused on the other's routes. mobile.access:user and mobile.access:supplier (EnsureMobileIdentityHasAccess) answer 403 {code: "wrong_audience"}, so a controller written for a User is never handed a Supplier.

Request headers

Authorization: Bearer <token>Required on every route except login, 2FA challenge, health, registration and password reset.

Accept-Language: en | bnPicks the response language. SetMobileLocale resolves: explicit Accept-Language (only en/bn accepted), then the person's saved locale, then config('app.locale'). Every response carries Content-Language. A person's saved language is changed with PUT /locale.
Content-Type: application/jsonFor bodies; file uploads use multipart.

Rate limits

  • throttle:mobile on every mobile route: 120 per minute (configurable) per person, per IP before sign-in. Over the limit: 429 with Retry-After.
  • Login failures: see above. 2FA challenge: mobile-two-factor, 5 per minute per challenge.
  • Per-route inline limits on guest and sensitive routes, for example registration throttle:10,1,mobile-register, registration options 30,1, password forgot/reset 5,1, 2FA settings 10,1, account deletion request 5,1.

Response conventions

Success shape

  • A single resource: Laravel's JsonResource default, { "data": { ... } }. A few endpoints return a hand-built object (login, usable balance, auth/devices returns {data: [...]}). The generated document states each shape through @response annotations.
  • A collection: { "data": [...], "links": {...}, "meta": {...} }. Many list endpoints add extra top-level keys such as filters (what was actually applied; meaningless filters are ignored) and options (the values each filter accepts, already translated). 204 with no body for revoke/logout.
  • Identifiers: resources are addressed by a public ULID or slug exposed as id, never a database id. Anything not belonging to the signed-in person answers 404, not 403, so existence is not leaked (the wallet transaction endpoint scopes the query to the caller's wallet before using the public id).
  • Times are ISO 8601 strings (toIso8601String()).

Money

Money is flat Taka, never poisha, and always the server's own object (App\Http\Resources\Mobile\MoneyResource, equal to Money::jsonSerialize()):

{ "amount": "100.50", "currency": "BDT", "formatted": "৳100.50" }

The app displays it and never computes with it. Amounts the app submits are decimal strings exactly as typed ("100.50"); they are parsed with DecimalAmount::parse(), and more than two decimal places is rejected, never rounded. See Conventions.

Pagination

List endpoints are Laravel length-aware paginators: query page, and per_page where the endpoint accepts it (for example OrderListRequest: integer, min:1, max:100); the response carries data, links and meta (current_page, last_page, per_page, total, and Laravel's other meta keys). The default page size is set by each controller (orders 25, wallet statement 20, website orders 20); the endpoint's PHPDoc says which. Some endpoints return a hand-built meta with only the four keys (for instance referrals). Exports are CSV downloads capped per controller (orders: 10,000 rows, spreadsheet formula cells neutralised).

Identity and onboarding gating

The web funnel gate is an allow-list keyed on route names with redirects. A mobile client cannot follow a redirect, so the mobile API inverts the allow-list into structure (routes/mobile.php comment):

  • auth:sanctum + mobile.access:user wrap every signed-in route (EnsureMobileIdentityHasAccess: right audience, platform access, revokes the token of a suspended login).
  • The §5.4 areas an unactivated account may reach are registered outside mobile.activated: onboarding status, KYC, packages and subscription, activation checkout, profile/verification/security/2FA/notifications/locale/account-deletion, staff invitation accept.
  • Everything else is registered inside Route::middleware('mobile.activated') (EnsureMobileBusinessActivated), so a route added in that group is closed to an unactivated account by default. Forgetting the group in a new module file exposes the route; always wrap business routes.
  • entitled:staff_limit applies to staff management exactly as on the web.
  • Administration: routes/mobile.php reserves /admin with auth:sanctum, mobile.access:user, mobile.two-factor (second factor, else 403 two_factor_required) and mobile.reason (default reason on staff screens), plus per-route mobile.password (current_password in the body) where the web uses RequirePassword. Route names there must equal the web route (roles.store inside the admin. group) so config/reasons.php and the policies recognise them. No files currently exist in routes/mobile/admin/, so there are no mobile admin endpoints yet (MobileAdminGatesTest covers the gates).

How Scramble documents an endpoint

Scramble reads the code; you add PHPDoc only where it cannot infer. Conventions in use throughout Api/Mobile/V1:

SourceBecomes
First line of the method docblockOperation summary (Sign in, Usable balance).
Following paragraphsOperation description. State filters, page size, error cases (403 without the right to view orders).
@unauthenticatedMarks the operation as needing no token (login, challenge, registration, password reset).
@response array{...} / @response 202 array{...}Response schema when it cannot be inferred (hand-built JsonResponse, collection with extra keys). Reference resources by class name: list<WalletTransactionResource>, MoneyResource. Multiple annotations with status codes for multiple outcomes.
Return type (JsonResource, AnonymousResourceCollection)Inferred from the Resource's toArray() return shape.
Form Request rules()Request body / query parameters. A /** comment */ above a key becomes the parameter description (/** The login email address. */).
Resource toArray() keys with /** ... */Field descriptions (MoneyResource: "Exact decimal Taka as a string").
Route nameSwagger tag, via ApiServiceProvider::tagFor(): mobile.v1.wallet.transactions.show is "Wallet"; mobile.v1.supplier.listings.index is "Supplier · Listings"; mobile.v1.wholesale.cart.items.store is "Wholesale · Cart" (admin, supplier and wholesale are split by their second segment); mobile.v1.health is "System". Name every route.

The generated document is cached in the file store (config/scramble.php cache); use scramble:cache / scramble:clear if the live document looks stale (Scramble commands, not verified here).

How to add an endpoint

  1. Find the Action or Query. The mobile app reuses the web app's Actions and Queries. If the logic exists for the web, call it. If not, write it in app/Domain/<Module>/Actions (money through WalletService/the recipe in Conventions) and have the web controller call it too. No business logic in the controller.
  2. Pick the module file routes/mobile/<module>.php (create one if the module is new; it is picked up by glob() automatically). Decide the gate: if an unactivated account must reach it (§5.4), register it outside Route::middleware('mobile.activated'); otherwise inside. Add entitled:<feature> if the web does.
  3. Register the route with a name (mobile.v1.<module>.<action>, written without the prefix in the file: ->name('wallet.usable') inside the file becomes mobile.v1.wallet.usable) and public-id parameters ({transaction} resolved by public_id, never an auto-increment id). Literal segments before wildcard ones.
  4. Create the Form Request in app/Http/Requests/Mobile/<Module>/: rules, /** description */ comments on each key. Money fields use DecimalAmountRule and are parsed with DecimalAmount::parse(). Reuse the web rules where possible.
  5. Create the Resource in app/Http/Resources/Mobile/<Module>/. Money is new MoneyResource($money) (or MoneyResource::nullable()), never a float or a hand-formatted string; ids are public_id/slug; never expose internal notes, secrets or database ids.
  6. Create the controller in app/Http/Controllers/Api/Mobile/V1/<Module>/ extending MobileController. Resolve the account (ResolvesBusinessAccount) and start every query from it; authorize with a policy or permission; delegate to the Action; return the Resource. Write the Scramble docblock (summary, description, @response where needed).
  7. Self-scoping. Scope by the caller's account/wallet/website before using a public id from the URL, so a borrowed id finds nothing and answers 404.
  8. Test in tests/Feature/Mobile/Mobile<Module>Test.php (group mobile): use Sanctum::actingAs() or $this->withToken(), postJson(route('mobile.v1...')); assert success, 401 without a token, 403 account_not_activated for an unactivated account (if gated), 404 for another account's id, and 422 for bad input. Run vendor/bin/pest tests/Feature/Mobile in its own schema (see Testing).
  9. Check the docs. Open /docs/mobile: the operation should appear under the right tag with the expected parameters and response. Fix docblocks until it does. Update docs/api/mobile.md only if a client-wide rule changed.
  10. Pint, PHPStan (vendor/bin/pint --parallel, composer types:check).

Note. The mobile API is versioned in the path but, unlike the storefront API, is not documented as frozen. Still, the app in users' hands is slow to update: add fields rather than renaming or removing them, and introduce v2 for a breaking change.

Testing the API by hand

# sign in
curl -sX POST "$APP_URL/api/mobile/v1/auth/login" \
  -H "Accept: application/json" -H "Content-Type: application/json" \
  -d '{"email":"owner@example.test","password":"...","device_name":"curl"}'

# call something
curl -s "$APP_URL/api/mobile/v1/wallet/usable" \
  -H "Accept: application/json" -H "Accept-Language: bn" \
  -H "Authorization: Bearer $TOKEN"

Do not paste real tokens or passwords into tickets or docs. Use APP_URL as served by php artisan serve.
