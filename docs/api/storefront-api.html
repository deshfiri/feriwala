Storefront API (v1)

The signed HTTP API a partner's storefront uses to read its catalogue, quote carts, place orders and register customers and returns, plus the signed webhooks the ERP sends back. It is frozen at v1: fields and endpoints may be added, nothing is removed or renamed without an approved v2. Read this before touching routes/api.php, the storefront.* middleware or any payload.

Authoritative sources: requirements/05-storefront-api-contract.md (the frozen contract), docs/api/storefront.md (the text that becomes the OpenAPI description), and the code named below. Live OpenAPI generated from the routes is served at /docs/storefront (Swagger UI) and /docs/storefront.json (raw document). Access to those pages is gated: public only when scramble.public is set, otherwise Super Admin and System Administrator (ApiServiceProvider, gate viewApiDocs; the RestrictedDocsAccess middleware also applies).

Rule. The storefront never computes a price and never holds a gateway credential. Feriwala is merchant of record (D12; Partner gateways under D36 change no field of this contract). There is no wallet, ledger, KYC, commission or user endpoint, scope or parameter: the surface does not exist. No route names a website; the credential does.

Base URL and versioning

https://<erp-host>/api/storefront/v1. Route names are prefixed storefront.v1.. Breaking changes (removing or renaming a field, narrowing a type, adding a required request field, changing an error code's meaning) need v2 and approval; the storefront boundary is architecture-locked (Decisions).

Authentication and signing

There are no bearer tokens. Each request is signed with the website's credential (a WebsiteCredential, issued by staff when the store is connected; see Website). Implemented in App\Domain\Website\Api\RequestSignature and verified by App\Http\Middleware\Storefront\AuthenticateStorefrontRequest.

Authorization: Feriwala-HMAC-SHA256 Credential=<key_id>, Signature=<hex>
X-Feriwala-Timestamp: <unix seconds>
X-Feriwala-Nonce: <uuid v4>

canonical_request =
    METHOD                       \n
    path + sorted query string   \n
    X-Feriwala-Timestamp         \n
    X-Feriwala-Nonce             \n
    hex sha256 of the raw body   (empty string hashed when there is none)

signature = hex(HMAC-SHA256(secret, canonical_request))
  • key_id is wsk_ plus 26 uppercase alphanumerics (the "store id"). The header must match Credential=(wsk_[0-9A-Z]{26}), Signature=([0-9a-fA-F]{64}) exactly.
  • "Sorted query string": the raw query split on &, pairs sorted byte-wise, rejoined with a leading ?, exactly as encoded on the wire. Never decode and re-encode (that is where %20 and + implementations disagree). The path is getPathInfo(), so a storefront whose ERP URL has a path prefix must sign the full path.
  • The nonce must be a version-4 UUID.
  • Checks, in order: HTTPS; credential exists; not revoked; timestamp within 300 s (website.api.clock_skew_seconds); nonce well-formed; signature matches the current secret or a rotated one still inside its grace window (constant-time, every secret tried); nonce not seen for this credential in 600 s (nonce_ttl_seconds, held as a cache lock, checked after the signature so garbage cannot burn nonces); website is being served.
  • Every failure is the same 401 unauthenticated to the caller; the precise reason (missing_or_malformed_authorization, unknown_credential, credential_revoked, stale_timestamp, malformed_nonce, invalid_signature, replayed_nonce) goes to api_logs.error_code only.
  • HTTPS only. Plain HTTP is refused with 400 https_required, never redirected (a redirect would leak the signed request), unless website.allow_local_addresses is on (development only).
  • Website not served: 403 website_unavailable. Allowed statuses: live ones plus development, api_connection_pending and maintenance.
  • Each retry must be a fresh request with a fresh nonce and timestamp.

A call outside the credential's scopes is 403 insufficient_scope with details.required_scope. Tenancy: every query is scoped to the credential's website before any caller filter; a resource of another website is 404 not_found, so the API cannot be used to probe other partners.

Host binding

Optional header X-Feriwala-Storefront-Host: shop.example.com. When present, VerifyStorefrontHost resolves the host itself through ResolveWebsiteHost (the website's subdomain, or a verified and active custom domain on a website that is not closed) and answers 403 host_mismatch unless it belongs to the credential's website. It can only narrow a request, never select a website. The storefront app sends it when ERP_STOREFRONT_HOST is set.

Rate limits

LimitStorefrontRate, counted per credential and per website (a second credential does not double the allowance), per minute, three classes from website.api.rate_limits:

Responses carry X-RateLimit-Limit, X-RateLimit-Remaining, X-RateLimit-Reset (whichever budget has less left). Over the limit: 429 rate_limited with Retry-After and details.retry_after. The limiter store must be shared (Redis in production). /health is not limited.

Idempotency

Every write route (everything under storefront.idempotent) needs Idempotency-Key, at most 64 characters (else 400 idempotency_key_required). The key is scoped to the website. First use runs the request and stores the answer; the same key with the same method, path and body replays the stored response byte for byte with Idempotent-Replay: true; the same key with a different request is 409 idempotency_key_reused; a concurrent duplicate waits on a lock and replays (or 409 request_in_progress if it times out). 5xx, 401, 403 and 429 answers are not stored. The fingerprint is an HMAC keyed with app.key. Records are in storefront_requests, pruned daily at 03:40 well after the contract's 24-hour replay window. storefront_order_reference is a second duplicate guard (409 duplicate_storefront_order). POST /checkout/quote is advisory, writes nothing and takes no key.

Behaviour worth knowing

  • Pagination is cursor-based: {"data":[...],"meta":{"next_cursor":"...","has_more":true}}; ?limit= default 50, maximum 200 (website.api.default_page_size, max_page_size). There are no page numbers.
  • Products (§5.1): ?updated_since=&cursor=&limit=&category=&q=&sort=&price_min=&price_max=&brand=&attributes[slug]=&in_stock=&featured=&flash_deal=&status=. sort is one of featured, newest, price_asc, price_desc, name, best_selling. Only products published on the website, eligible for its owner to sell, and bought by the owner are listed (StorefrontSelections). price is the website's own selling price; wholesale price, cost and margin are never present. best_selling is rebuilt every 15 minutes.
  • Orders: the ERP recalculates every price, discount, tax and total; a difference of 0.01 is 422 price_mismatch carrying only selling-side figures, and the storefront must obtain the customer's reconfirmation and resubmit with a new idempotency key. Acceptance reserves stock in the same transaction (15 minutes online, 24 hours COD by default). payment.return_url must be https, standard port, no credentials, and on a host that belongs to the website now, else 422 return_url_not_allowed.
  • COD: a COD order starts customer_verification_pending; the six-digit code goes only to the customer's SMS and is never in any response. A wrong, spent or never-issued code all answer 422 confirmation_refused; a closed window 409 confirmation_expired; resends are cooled down (429 confirmation_code_too_soon) and capped at five (429 confirmation_code_limit_reached).
  • Customers: keyed on (website_id, normalised mobile); mobile in E.164 (the ERP normalises, converts a leading 0, and rejects the unresolvable with 422 invalid_mobile_number). Knowing a number grants no access to history.
  • Returns: only for delivered or completed orders inside the return window (7 days default). Refusals include order_not_returnable, return_window_closed, quantity_not_returnable, line_not_on_order, nothing_returnable (per contract §6.3).
  • Connection returns the website's public id, status and host, the credential's key id, scopes, rotated_at and previous_secret_expires_at, the rate limits, last_synced_at and connection_health. The storefront's storefront:doctor uses it.

Money: amount and legacy minor_units

Money is always an object mirroring Money::jsonSerialize(): {"amount":"1234.56","currency":"BDT","formatted":"৳1,234.56"}. amount is flat Taka as a decimal string; nothing on either side multiplies or divides by 100.

Compatibility rule (contract §4.1). Before 2026-09-23 money was {"minor_units":123456,"currency":"BDT","decimal":"1234.56"} in poisha. For the compatibility period outbound objects carry amount and also the legacy minor_units and decimal; inbound, an object may supply either amount (preferred) or minor_units, but exactly one: both is 422, because a payload that disagrees with itself is the one way a 100-times error could enter. The legacy value is converted once at the edge by the documented adapter. In the code the only place that writes minor_units is the API payload layer (for example StorefrontController builds it with bcmul($amount, '100', 0)); this is the repository guard test's one exemption. No new internal code may read or write minor_units, and new endpoints and fields are amount-only. The legacy keys are removed only in v2.

Price comparisons are exact decimals at two places. Money in requests goes through the strict parser (DecimalAmount); excess precision is rejected, not rounded.

Webhooks to the storefront

The ERP POSTs to the website's one endpoint (website_webhook_endpoints.url; the storefront app expects /webhooks/feriwala). Payload: {"event","occurred_at","website_id" (public id),"data"}. Headers:

Content-Type: application/json
X-Feriwala-Event: product.updated
X-Feriwala-Delivery: <ULID, stable across retries>
X-Feriwala-Timestamp: <unix seconds>
X-Feriwala-Signature: sha256=<hex>

signature = "sha256=" + hex(HMAC-SHA256(webhook_secret, timestamp + "." + raw_body))
  • Verify in constant time over the raw body, reject a timestamp older (or newer) than 300 s, accept a rotated secret while its window is open, and deduplicate on X-Feriwala-Delivery. The reference implementation is WebhookSignature::verify().
  • Delivery is asynchronous (queue webhooks), at least once, unordered. Answer 2xx within 10 s and process later. Retries on any non-2xx or timeout: after attempts at +10 s, 30 s, 2 min, 10 min, 30 min, 2 h, 6 h, 12 h; then the delivery is failed (dead letter) for a person to retry with the same delivery id. A redirect is never followed and counts as a failure. Endpoint addresses must be https on port 443 and resolve only to public addresses, checked when saved and before every attempt.
  • Events (WebhookEvent): product.published, product.updated, product.unpublished, product.price_changed, inventory.updated, inventory.out_of_stock, category.updated, order.status_changed, order.cancelled, cod.confirmation_required, cod.confirmed, cod.expired, shipment.updated, return.status_changed, refund.completed, website.suspended, website.restored, website.updated (carries only the website and time; re-read GET /site). Low wallet balance and grace period are not suspension and send no website.suspended.
  • A webhook is a hint, not the source of truth: re-read the API for anything that matters. Full mechanics: Website.

Storefront obligations (contract §8)

  1. Ignore unknown JSON fields and tolerate unknown enum values and event types.
  2. Treat every list as paginated.
  3. Retry 429 and 5xx with backoff and jitter; never retry other 4xx.
  4. Send an Idempotency-Key on every write.
  5. Verify webhook signatures and deduplicate on the delivery id.
  6. Never cache catalogue data past its updated_at without revalidating at checkout.

The reference client is the Storefront app (storefront/app/Erp/Client.php).

Extending without breaking v1

  1. Allowed (additive): a new optional request field, a new response field, a new endpoint, a new enum value or event the client is documented to tolerate. Not allowed: removing, renaming or narrowing anything; a new required request field; changing an error code's meaning.
  2. New endpoint: add the route inside the storefront/v1 group with the right storefront.rate:* class and storefront.scope:*, and storefront.idempotent if it writes. Take the website from the request attribute set by authentication (StorefrontController::website()), never from input. Build errors with StorefrontError::respond().
  3. Name the route storefront.v1.<group>.<action>: ApiServiceProvider::tagFor() files it under a Swagger tag from the name.
  4. New fields use amount money only. Never expose cost, margin, wholesale price, wallet or another website's data.
  5. New scope: see "Add a credential scope" on the Website page. New webhook event: see "Add a webhook event" there.
  6. Update requirements/05-storefront-api-contract.md (note an additive change with its decision reference) and, if consumers must know, docs/api/storefront.md. Add tests in tests/Feature/WebsiteApi/ (authentication and isolation tests exist as models: StorefrontAuthenticationTest, StorefrontIsolationTest).
  7. Anything breaking: stop and raise it for approval; it needs v2.
