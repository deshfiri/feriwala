Storefront app

The customer-facing shop for one partner website: a separate Laravel application in storefront/ with its own repository, database (MySQL) and deployment. It talks to the ERP only through the frozen Storefront API and never decides a price. Read this to install, configure, run or change it.

Rule. The storefront has no access to the ERP database, never computes money, never holds a gateway credential, and never stores a price in the basket. Every figure shown was worked out by the ERP; an order is submitted with exactly those figures, and a 0.01 difference makes the customer confirm the new total again (D11, D12, D32).

What it is

Per D32 each partner website is served by its own installation of this app. It is Laravel 13 on PHP 8.3 or newer (storefront/composer.json), needs pdo_mysql, curl and mbstring, has no Node build (plain CSS and JS in public/assets), and supports English and Bangla (lang/en.json, lang/bn.json). Features: home, catalogue, category and search with the ERP's filters; product pages; a basket that remembers SKUs and quantities; guest checkout (COD or online payment) with a review step and price-change reconfirmation; an order page (pay, cancel, confirm a COD code, request a return); order lookup by reference and mobile number; a webhook receiver. Its own README is storefront/README.md.

The ERP side of the relationship (credentials, webhook endpoint, "Connect the store") is documented in Website module.

Structure

Builds the canonical request, signs, retries 429/5xx/connection failures with backoff, never follows redirects, gives every non-GET an Idempotency-Key. Client::fromConfig() throws if ERP_BASE_URL, STORE_ID or STORE_TOKEN is empty, and if the base URL is not https (http is allowed only when APP_ENV=local). Bound as a singleton in AppServiceProvider.

app/Erp/ErpException.phpCarries status, errorCode (the contract's stable code), details, requestId, retryAfter. isUnavailable() is true for status 0, 429 or 5xx. Nothing branches on the message. It is not reported; bootstrap/app.php renders it as the "unavailable" page (503) or 404 and logs the request id.
app/Services/Catalog.phpProducts, facets, categories, inventory via the ERP, cached through ApiCache with tag catalog. Only the filters the API understands are forwarded.
app/Services/Site.phpGET /site through a cache (tag site); falls back to a conservative site that says it cannot take orders when the ERP is unreachable. Also vets the banner link and colours before they reach HTML or CSS.

On price_mismatch it stores the ERP's authoritative figures, issues a new idempotency key and returns repriced. Claims a checkout (draft to placing); a claim older than two minutes counts as abandoned. returnUrl() is APP_URL/payment/return only when APP_URL is https.
app/Services/Orders.phpLocal order rows so a customer can find an order again; status is always read back from the ERP. Access: the order's unguessable access_token, the placing session, or reference plus mobile (rate limited). A miss and a wrong number are indistinguishable.
app/Services/Webhooks.phpVerifies and applies the ERP's webhooks (below).
app/Services/ApiCache.phpShort-lived tagged cache of ERP reads in the api_cache table: remember, forgetTag, forgetKey, flush, prune. A TTL bounds staleness if a webhook is lost. Quotes and orders are never cached.
app/Http/Controllers/CatalogController, CartController, CheckoutController, OrderController, SystemController (areas proxy, locale, about, contact, robots, health, migrate), WebhookController.
app/Http/Middleware/LoadStorefront (language, the site's status, layout data; an unavailable shop answers every page with a 503 "closed" view and Retry-After: 120), SecurityHeaders (nosniff, frame deny, referrer policy, a CSP that allows images from https and from the ERP's origin).
app/Models/, app/Support/Cart, CartItem, Checkout, Order; helpers and Money (decimal-string handling).

From storefront/.env.example and the config files. Names only; never commit values. .env.example ships an APP_KEY line: replace it with your own via key:generate.

How it authenticates to the ERP

  1. Staff with website.manage_integrations open the website in the ERP's admin and use "Connect the store" with the storefront's address. The ERP shows ERP_BASE_URL, STORE_ID, STORE_TOKEN (and WEBHOOK_SECRET when it could register a webhook) once; copy them into .env.
  2. Every call is signed: Authorization: Feriwala-HMAC-SHA256 Credential=<STORE_ID>, Signature=<hex> with X-Feriwala-Timestamp and a fresh X-Feriwala-Nonce, where the signature is HMAC-SHA256 of the canonical request keyed with STORE_TOKEN. Each retry re-signs with a new nonce and timestamp because a nonce is accepted once. Details: Storefront API.
  3. Scopes are decided by the credential. A connected store gets all six, so storefront:doctor should list them.
  4. The token is never sent to the browser: the delivery-area directory is proxied so the browser holds no credentials.
  5. A rotated token keeps the old one valid for the ERP's grace window (STOREFRONT_ROTATION_GRACE_MINUTES, default 1440 minutes); update STORE_TOKEN within it.

Credentials made by hand in the ERP (admin.websites.credentials.store) return an .env block that uses the same names this app reads: ERP_BASE_URL, STORE_ID and STORE_TOKEN. Paste it as it is. Older ERP versions emitted BANIJ_* names, which this app never read.

Caching

ApiCache stores JSON in api_cache with a tag and an expiry (key truncated to 190 characters). TTLs come from config('storefront.cache_ttl') (variables above). Tags: site and catalog. Quotes, orders and anything priced at checkout are never cached; the ERP prices the cart again at POST /orders. storefront:prune removes expired entries.

Webhook receiver

POST /webhooks/feriwala (route name webhooks.feriwala, in routes/system.php: no session, no CSRF, no shop lookup) calls Services\Webhooks::receive() with the raw body and the x-feriwala-signature, -timestamp, -delivery and -event headers.

  1. Verify. The timestamp must be all digits and within 300 s. The signature (with or without a sha256= prefix) is compared with hash_equals against HMAC-SHA256(timestamp + "." + rawBody) for each of WEBHOOK_SECRET and WEBHOOK_SECRET_PREVIOUS; every configured secret is tried whatever the first answered. No secret configured: always 401 invalid_signature.
  2. Parse. Not JSON: 400 malformed. The delivery id must match ^[A-Za-z0-9_-]{8,64}$, else 400 missing_delivery_id.
  3. Deduplicate. insertOrIgnore into webhook_deliveries by delivery_id; a repeat answers 200 {"status":"duplicate"} and is not processed.
  4. Apply. product.*, inventory.* and category.updated drop the catalog tag; website.* drops site and catalog; an event whose data.order has an id and status updates the local order's status (Orders::noteStatus). Unknown events are acknowledged and ignored. Answer 200 {"status":"ok"}.

A webhook only invalidates cache; a lost, late or duplicate one costs freshness, never correctness. Delivery ids are pruned after 14 days.

Rotating the secret. In the ERP, rotate (or "Generate webhook secret"). Put the new value in WEBHOOK_SECRET and the old one in WEBHOOK_SECRET_PREVIOUS, redeploy within the ERP's grace window, then clear the previous one.

Installation and deploy

  1. composer install --no-dev --optimize-autoloader
  2. Point the web server's document root at public/ only.
  3. Create a MySQL database and user.
  4. Connect the store in the ERP (above).
  5. cp .env.example .env, fill in the database, APP_URL and the ERP lines, then php artisan key:generate.
  6. php artisan migrate --force: safe to repeat, and upgrades an earlier plain-PHP installation in place.
  7. php artisan storefront:doctor
  8. Cron every minute: php /path/to/storefront/artisan schedule:run (the schedule runs storefront:prune hourly), or run php artisan storefront:prune hourly directly.
  9. Production: php artisan config:cache route:cache view:cache. Behind a proxy you control set TRUSTED_PROXY=1.

No shell: the /migrate route

On hosting with no shell (cPanel), open https://your-domain/migrate?token=<MIGRATE_TOKEN> once after upload. SystemController::migrate() runs migrate --force and prints the output as plain text. With MIGRATE_TOKEN set, a wrong or missing token answers 404. With it unset anyone can open the route (harmless as it only applies the shipped migrations, but set it). On failure it answers 500 with detail only to a caller holding the token or when APP_DEBUG is on; the exception is always reported. The route lives in routes/system.php, so it works before any table exists.

The doctor command

php artisan storefront:doctor (exit code 1 if anything needs attention) checks: PHP pdo_mysql, curl, mbstring; database connection; that carts, checkouts, orders and sessions exist; that APP_URL is https (or the environment is local); the webhook secret (optional, at least 16 characters if set); then against the ERP: GET /site accepts the credentials, website status is open, it is accepting orders, payment methods are available, and GET /connection lists the credential's scopes. storefront:prune removes expired sessions and cached reads, abandoned baskets (30 days), unplaced checkouts (14 days) and old webhook delivery ids (14 days).

Local development against the ERP

  1. Run the ERP with APP_ENV=local (or WEBSITE_ALLOW_LOCAL_ADDRESSES=true) so it accepts plain http and a local address (php artisan serve, http://127.0.0.1:8000).
  2. Run the storefront on another port: php artisan serve --port=8001, with APP_ENV=local in its .env.
  3. In the ERP admin, "Connect the store" with http://127.0.0.1:8001. A local address registers no webhook; the shown .env block adds APP_ENV=local.
  4. Paste ERP_BASE_URL=http://127.0.0.1:8000, STORE_ID and STORE_TOKEN, run php artisan migrate and storefront:doctor.
  5. Product images are served by the ERP; APP_URL and the ERP's APP_URL must match the origin each is really served on (port included), and the ERP needs php artisan storage:link. The storefront's CSP already allows the ERP's origin for images.
  6. Without a payment return URL (the storefront's APP_URL not https) the ERP gets no return_url and the customer lands on the shop home after paying. Tests: vendor/bin/pest inside storefront/ (no ERP needed).

Gotchas

  • routes/web.php contains a route GET /cc/{token} that runs optimize:clear, key:generate --force, migrate and storage:link when the token equals config('services.cc_token'). That config key does not exist in config/services.php and no env variable for it is documented, so the route always answers 403 as shipped. Do not enable it casually: key:generate --force would invalidate sessions and encrypted data. Not in the README; flagged for review.
  • A basket survives price changes because it holds no price. A stale checkout is re-quoted before it is placed.
  • An order is reachable only through its own token, the session that placed it, or reference plus mobile; never by id or mobile alone.
  • The reference in POST /orders is SF-<year>-<id>-<random>; the random tail keeps a database restored from backup from reusing a reference the ERP already saw.
  • If the ERP is unreachable the shop renders from a fallback site and says it cannot take orders; ERP failures show the "try again shortly" page, never a trace.
