KYC module

Identity and business verification for Client/Partner accounts (and, through the same batch engine, Suppliers). It owns the document catalogue, versioned batch templates, rounds, evidence, the private encrypted document store, reviews, re-verification requests and deadlines.

Purpose

KYC approval is one of three conditions for activating a business account (§5.1, §44); approving KYC never activates by itself. The module implements §7.2 (administrator-configured requirements, scoped by package and country), §7.3 (rounds, review outcomes, append-only review record), §7.4 (deadlines and consequences), §7.5 (private, authenticated, access-logged documents) and D30 (batches as versioned templates, with groups, options, slots and a live selfie).

Users: the applicant (partner owner or staff of that account) fills in rounds; KYC Manager and Admin staff review; the system sweeps deadlines. Supplier KYC lives in the Supplier domain (separate tables, D25) but reuses the batch engine through the KycRound interface.

Key terms

Document type / requirement
KycDocumentType: one thing the applicant is asked for ("National ID"). Called a "criterion" in older comments. Active, inactive (paused) or archived; never deleted once referenced.
Slot
KycRequirementSlot: one piece of evidence a requirement is made of: a file, image, PDF, typed value or declaration. "National ID" is two image slots (front, back); "TIN" is a value slot (D30).
Batch
KycBatch: a template of groups an administrator asks for together ("Identity", "Business"). Has an audience, optional selfie, scope rules, a default flag.
Group
KycBatchGroup: holds options and a completion rule: all, any (one of) or min (at least N).
Option
A requirement's place in a group (KycBatchGroupRequirement), shown as a choice in any/min groups.
Version
KycBatchVersion: the batch frozen at publish time; append-only. A round reads only its version, never the live batch.
Round
One KycSubmission (`round` is a counter per account). A correction or resubmission is a new round, never an edit of the reviewed one.
Round purpose
onboarding, correction, reverification (a trading business asked again, §7.2). Only re-verification can carry consequences.
Evidence
An uploaded KycDocument or a typed KycSubmissionField in a slot, judged per slot by a verdict.
Live selfie
A batch-level setting, not a requirement. It appears under fixed keys __selfie / capture (KycRoundDefinition::SELFIE_REQUIREMENT, SELFIE_SLOT); stored with captured_live and capture_meta; JPEG/PNG up to 3072 KB.
Legacy (flat) round
A round with no batch version, judged against a snapshot of document types (KycSubmissionRequirement). Still supported.
Audience
KycAudience: account, supplier, both.

States & lifecycle

Submission (KycStatus)

StatusLegal nextNotes
draftsubmittedThe only editable state (isEditable())
submittedunder_review, resubmission_requiredAwaits review (awaitsReview())
under_reviewapproved, rejected, resubmission_requiredAwaits review
approvedresubmission_requiredApproval can be withdrawn (§7.2)
rejectedresubmission_required
resubmission_requirednone (isTerminal())The round is closed; the applicant starts a new round

A review straight from submitted is stepped through under_review explicitly by ReviewKyc; the map is not loosened. isOpen() on a submission means not cancelled and not approved/rejected, matching the partial unique index.

Effect on the account status

ReviewKyc::applyToAccount maps approved to kyc_approved (then immediately package_selection_pending), rejected to kyc_rejected, resubmission to kyc_resubmission_required, stepping kyc_submitted through kyc_under_review first. SubmitKyc moves the account to kyc_submitted only when the machine allows it (a re-submission is already further on). See the table in Account.

Batch lifecycle

Draft structure (live, editable) → publish creates version N+1 (or returns the existing version if the checksum is unchanged) → rounds pin the newest published version when opened. A batch used by anything is archived, not deleted. Active, default and archived are flags, not a state enum.

Flow: applicant to approval

  1. The applicant opens /kyc; OpenKycDraft returns (or creates) the draft, pinned to a batch version if a default applies.
  2. Each file, value or choice is saved on its own (one request each) through RecordKycEvidence; a rejected upload never costs the others. Files go through KycDocumentStore: private kyc disk, random name, encrypted at rest.
  3. SubmitKyc: completeness is checked server-side; the progress bars are a courtesy.
  4. A reviewer at /admin/kyc/{submission} opens documents (access recorded), reveals sensitive values on demand, records per-slot verdicts, then decides (decide).
  5. Approve: the batch round must be fully accepted. Account becomes kyc_approved then package_selection_pending; automatic activation is re-evaluated.
  6. Send back: at least one rejected slot. The applicant gets round N+1 with accepted slots locked and satisfied, and only the failed or missing ones open.

Flow: document access (§7.5)

  1. Routes kyc.documents.show / .download (web), mobile equivalents, and admin.suppliers.kyc.documents.show are the only way to a file.
  2. The policy decides: the applicant (any member of the submitting account) may open their own; others need kyc.view_kyc_documents.
  3. KycDocumentStore::read writes the kyc_document_accesses row before returning the bytes; if that insert fails nobody gets the file. Then reads from the recorded disk and decrypts.

Rule. There is no public URL for a KYC document, deliberately: no getUrl() on the model or the store. Do not add one. Storage disk and path are hidden from every array and JSON form.

Flow: re-verification

  1. Staff with kyc.verify call RequestKycUpdate from the account dossier (admin.kyc.request-update). A round with purpose reverification opens; the account's status is untouched.
  2. Consequences are chosen per case (KycConsequence): warning_only (default), block_new_orders, block_publishing, block_withdrawals (these three bite as soon as the round is open), suspend_after_deadline (only after the deadline). Each blocks new activity only; nothing cancels an order, unpublishes a site, reverses a ledger entry or blocks payment settlement, refunds or reconciliation.
  3. Server-side Actions ask KycRestrictions::blocksNewOrders/blocksPublishing/blocksWithdrawals (one open case per account). A hidden button is not a restriction.
  4. The daily sweep warns once before the deadline and enforces once after. Approval of the round lifts a deadline restriction.

Rules, invariants & gotchas

  • A round never reads live configuration. Batch rounds read their version's definition; flat rounds read their requirement snapshot. An administrator editing a type or batch this morning must not change what an applicant was shown yesterday. File acceptance in KycDocumentStore::store uses the round's snapshot rules first.
  • A correction is a new round. Never edit a reviewed round; resubmission_required is terminal.
  • Approval does not activate. It clears one gate; payment and the owner's verification remain (ActivationRequirements).
  • Approving a batch round needs every accepted slot reviewed. A complete-looking round whose files were never opened is not verified. CompleteAccountManually will not approve a batch round with unaccepted evidence.
  • Rejection needs a note (it is the instruction the applicant reads). Staff-only notes (internal_note, request_reason) never reach the applicant (§7.2); admin screens use viewDossier.
  • Typed values are encrypted and masked; the full value is revealed per request through kyc.evidence-value (kyc_batch.view_sensitive_data).
  • Draft file deletion is conditional. A carried-forward file is the same stored file as the earlier round's; deleteDraftFile removes bytes only when no other row points at them, and refuses on a non-editable submission.
  • Batches with begun rounds cannot be re-pinned (kyc.batch.refused.round_begun).
  • Publishing unchanged returns the same version (a version number means "this changed").
  • Deadlines are opt-in and only restrict when an administrator turned that on. Idempotency is a unique-index claim, not a flag.
  • kyc_document_types.accepted_mime_types default for a slot with none comes from KycEvidenceType::defaultMimeTypes() (JPEG/PNG for image, PDF for pdf, all three for file).
  • Language: older comments say "criterion"; the rename of consequence values is covered by KycConsequenceRenameMigrationTest.

How to…

Add a document type or batch (data, not code)

  1. Admin → KYC → document types, or the batch builder (/admin/kyc-batches). Define requirements and slots, group them, preview, then publish. Only published versions reach new rounds.
  2. Switch the batch on and, if wanted, make it the default for its audience. Existing open rounds stay on their version.

Add a new evidence kind

  1. Add a case to KycEvidenceType, with takesFile() / takesValue() / defaultMimeTypes().
  2. Handle it in RecordKycEvidence (file / value branches), KycCompletion::holds, the presenter and the React form; keep PartnerKycRound and SupplierKycRound in step through the KycRound interface.

Add a re-verification consequence

  1. Add a case to KycConsequence; decide appliesBeforeDeadline(); add label keys under kyc_consequence (lang/en|bn/status.php).
  2. Add a blocks… method to KycRestrictions and call it from the Action that performs the activity, never only the UI.
  3. Never make it cancel, reverse or unpublish anything.

Add a mobile evidence field

  1. New request in app/Http/Requests/Mobile/Kyc/ using AcceptsDocumentType if it names a requirement; add the route in routes/mobile/kyc.php (and the Supplier file if it applies); keep the validation docblocks, which feed the API docs.

Add a review outcome side effect

  1. Extend ReviewKyc::applyToAccount inside the existing transaction; do side effects like notifications after commit.
