External store module

A read-only mirror of orders from stores a partner runs on another platform. Feriwala pulls the orders (scheduled sync) and accepts signed webhooks, records them exactly as the store reported them, and shows them beside the partner's Feriwala orders. It changes nothing at the store and moves no money.

Read this first. The brief for this module mentions WooCommerce, but StorePlatform has exactly one case, dfcommerce (DFCOMMERCE). Another platform is added with its driver, not before. Also, D30 retired the partner's self-service connection: today a partner can only view stores that were connected earlier (stores.index, stores.show). The connect, update, rotate and disconnect Actions, the jobs, the webhook endpoint and the scheduler all still exist and are tested, but no route currently calls the connect, test, update, rotate or disconnect Actions (I grepped app/; only the Actions' own classes, SyncExternalStore and tests reference them).

Purpose

Partners may run their own shop on a platform other than Feriwala's storefront and want its orders next to their Feriwala orders in the Owner Panel (D29). Four decisions settle the design:

  1. A separate, read-only mirror. External orders live in their own tables (external_orders, external_order_items, external_order_events, external_customers), never in orders, which is bound to Feriwala's catalogue, status machine, stock, payment and earnings workflows.
  2. The store is the source of truth. Feriwala records what the store reports and changes nothing there. Feriwala's own status vocabulary is never applied to these orders.
  3. Partner-merchant, no Feriwala money path. The partner collects payment and fulfils. Amounts are stored for display; no payment, wallet, ledger, commission, settlement, refund or fulfilment row is ever written.
  4. A package feature with a per-package limit. PackageFeature::ExternalStoreAccess (external_store_access) and PackageFeature::ExternalStoreLimit (external_store_limit), off and zero by default.

Who uses it: the partner (account holder with AccountPermission::ManageStores, value store:manage) views stores; the system syncs and receives webhooks; platform staff have no ability here by design, since they have no reason to hold a partner's store keys. Decisions: D29, amended by D30 (self-service connection retired). D11 still holds: an external store is never given ERP credentials; Feriwala calls it. D12 still holds for every Feriwala order source.

Rule. No Feriwala money path for an external order. It never creates a payment, wallet or ledger row, never touches stock, and is never deleted (a database trigger refuses it). Its history is append-only and an older copy never overwrites a newer one.

Key terms

External store
A partner's own shop on another platform, connected to their business account. One live connection per store address across all accounts.
Platform / driver
StorePlatform names the platform; its StorePlatformDriver knows how to verify credentials, fetch orders and read webhooks.
Mirror
The set of external_* tables: a copy of what the store said, not a Feriwala order.
Sync
A pull of orders in two passes, each with its own cursor: new orders (by increasing id) and changed orders (by updated_since).
Deferred notification
A signed webhook too thin to create its order (missing store id, amount or items). Kept with its payload; the pull brings the order in whole.
Live
Not disconnected (ExternalStoreStatus::isLive()).

isTerminal() is always false. Moves happen through transitionWithHistory(), never by assigning status. Who moves it: the partner (connect, reconnect, disconnect: source account), a sync or connection test (system), the scheduled round (scheduler). A sync that fails stores.failing_after (3) times in a row, or fails with a non-retryable error, moves the store to failing; the next successful sync from pending or failing moves it to connected.

Connecting a store (ConnectExternalStore::handle)

  1. Package must include external stores with room for another (ExternalStoreAllowance: account can transact and holds ExternalStoreAccess; live stores count against ExternalStoreLimit).
  2. The address must be HTTPS (StoreAddress::parse() refuses plain HTTP and embedded credentials) and not held by any live connection on the same platform, this account's or anybody else's. Whose is not said.
  3. The driver's verify() reads one order, which proves the address, the key and the orders.read scope in one call.
  4. In a transaction, lock the business_accounts row, repeat the capacity check, create the store (pending, credentials encrypted, api_key_hint = last four of the key) with the webhook secret the partner provided or a generated one, and write the first history row. A unique-index race settles as ExternalStoreRefused::alreadyConnected().
  5. Audit external_store.connected and queue the first import with SyncExternalStore::dispatch(...)->afterCommit(), never inside the request.
  6. A generated webhook secret is returned in plain text once for the setup screen; a provided one is never handed back.

Syncing (ImportExternalOrders)

  1. Takes a distributed lock external-store-sync:{id} (TTL 600 s); a sync already running means this one returns null. Does nothing if the store is not live or the package no longer includes stores.
  2. New orders pass. Walk the store's ids upward from order_cursor, advancing the cursor only past what was recorded. Stops at stores.max_pages_per_pass (20) or when the store returns a cursor that does not move forward.
  3. Changed orders pass. Everything the store says changed since orders_updated_through (first run: initial_change_window_hours, 24) minus change_overlap_minutes (10), walked from the start. The window is advanced only when the whole window was read; a pass that hits the page limit re-reads it next time.
  4. Each order goes through RecordExternalOrder, which locks by the store's own id and only creates an order that is absent (a unique index settles races). A newer copy updates the order and records each change to source_status or payment_status as an event dated by the store's updated at; a same-or-older copy leaves it untouched. An order short of what is needed, or whose id and number belong to two different orders, throws ExternalOrderNotRecorded and is counted as unreadable, never guessed at or merged.
  5. On success: consecutive_failures = 0, last_error set only if some orders were unreadable, pending/failing moves to connected, and ApplyExternalStoreWebhook::settleDeferred() closes deferred notifications whose orders have now arrived. On a StorePlatformException: failure counters and last_error (255 characters, a message written in our code, never copied from the store), possible move to failing, and the exception is rethrown to the job.

Receiving a webhook (ReceiveExternalStoreWebhook::handle)

Unauthenticated by necessity, so the order of checks is the security:

  1. The store must exist, be live and hold a webhook secret; otherwise unknown_store (an unknown and a disconnected store answer the same, so it cannot be used to find which stores exist).
  2. The driver checks the signature: for DFCOMMERCE, X-Webhook-Signature: sha256=<hex hmac of the raw body>, compared with hash_equals. Bad: unauthorised.
  3. The body is decoded without floats; the store's event id (X-Webhook-Event-Id) is required, with no made-up fallback. Missing or unparseable: malformed.
  4. An ExternalStoreWebhookEvent is created in state received. A unique-violation (same store and event id) is a duplicate: counted, acknowledged, and re-queued only if the first attempt ended failed or deferred.
  5. last_webhook_at is stamped and ProcessExternalStoreWebhook is dispatched: a store waiting on our database times out and resends.

ApplyExternalStoreWebhook then reads the notification through the driver: an order event goes through RecordExternalOrder (the same idempotent path a sync uses, so a webhook and a sync can never write an order twice); a payment confirmation is recorded as a payment_received event and updates paid_total and payment_status to paid (the store's own account of its payment); anything else is ignored. After success the stored payload is cleared because it held customer details. A deferred event is never applied late: once the order exists it is closed as processed.

Unified orders

"All orders" for a partner lists website, external and wholesale orders in one place (orders.index), and an external row opens orders.external.show, which renders the mirror with ExternalOrderStatusDisplay::label() (the store's word, translated where Feriwala recognises it, otherwise shown as written) and an OrderTimeline built from the order's events. External customers appear in the customer directory (CustomerDirectory). Nothing maps the store's status onto Feriwala's order statuses.

Permissions & scoping

  • ExternalStorePolicy: viewAny and create need the account permission AccountPermission::ManageStores (store:manage; the owner by default); view and manage also need the store to belong to the signed-in person's own business account. Platform staff are granted nothing.
  • Self-scoping is a query concern: ExternalStore::scopeForAccount(), and the overview is built only from the account's own stores. A partner reads orders with order:view through the unified orders screens.
  • Credentials never leave the server: the key is shown by its last four characters, the secrets not at all; they are encrypted, hidden from serialisation, and never in a page prop, log or error.

Money, ledger & audit effects

No ledger, wallet or payment effect, by design. Money columns are display-only Money values parsed from the store's decimal text. Audit actions (module external_store): external_store.connected (with webhook_signing_origin), external_store.webhook_secret_rotated, external_store.disconnected, plus external_store.updated and external_store.reconnected from UpdateExternalStoreConnection.

Rules, invariants & gotchas

  • Outbound calls are SSRF-guarded. The address is typed by a partner, so every call goes through OutboundAddressGuard: the host is resolved, every address must be public, the request is pinned to the checked address with CURLOPT_RESOLVE, redirects are off, and timeouts are short (the DFCOMMERCE driver uses 15 s). Carrier-grade NAT space (100.64.0.0/10) and IPv4-mapped IPv6 are handled explicitly.
  • One sync per store at a time. A lock, not a queue property: a manual sync and the scheduled round cannot overlap.
  • Two cursors. The OMS this mirrors could lose a status change because its passes shared one watermark; here new orders and changed orders each have their own.
  • Webhooks are a hint, the pull is the truth. A thin event is deferred rather than filled in; an older notification arriving late never rolls an order back.
  • The address is the identity. It cannot be edited, because pointing a connection at another shop would graft one store's history onto another. A different store is a new connection.
  • Disconnect keeps orders. Credentials and the webhook secret are forgotten, so a notification signed with the old secret is refused from then on; reconnecting starts again from pending and resumes from where the cursors left off.
  • RotateExternalStoreWebhookSecret has no grace window (unlike the Website module): the old secret stops working immediately.
  • Entitlement lapse does not delete anything: syncing simply stops until the package includes stores again, and the scheduled round skips such accounts.
  • Unlike a partner website (Website), an external store holds no Feriwala credential and has no storefront API surface.

How to…

Add a platform

  1. Add a case to StorePlatform with a label(). The external_stores_platform_known and external_orders_platform_known CHECK constraints list the platforms, so add a migration that replaces them.
  2. Write app/Integrations/Store/Drivers/<Name>Driver.php implementing StorePlatformDriver (verify, fetchOrders, signatureIsValid, webhookEventId, readWebhook, webhookEvents). Use OutboundAddressGuard for every call and ExactJson for amounts.
  3. Add the arm to the match in StorePlatformManager::driver() (PHP's exhaustive match will fail loudly on the new case until you do).
  4. Add tests faking HTTP with Http::fake() and DNS with externalStoreFakeDns().

Add a webhook event

  1. Add it to the driver's WEBHOOK_EVENTS (and its order or payment event list) so readWebhook() classifies it.
  2. If it carries a new kind of change, add an ExternalOrderEventType case and the migration for its CHECK, then handle it in ApplyExternalStoreWebhook.

Re-expose connecting to partners

This is a decision (D29 as amended by D30), not a code change: raise it for approval first. The Actions are ready; you would add routes and a controller guarded by ExternalStorePolicy, rate-limited with store-actions, and Inertia pages next to pages/stores/.
