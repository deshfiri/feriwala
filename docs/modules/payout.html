Payout methods

Where a Supplier or a Client/Partner business is paid out: a bank account, bKash or Nagad. One shared, owner-polymorphic table with encrypted details. A withdrawal snapshots a method at request time.

Purpose

D25 (P13-24, the Shared Payout Methods batch) generalised the Supplier-only payout method into one table used by both owner kinds. Business accounts manage their own methods on the ERP side; Suppliers on the Supplier portal. There is no staff screen for them. Spec §27, §31.3.

Key terms

Owner
owner_type (business_account or supplier) plus owner_id. The owner cannot change after creation.
Details
Sensitive fields, encrypted at rest and hidden from serialisation. Bank account: account holder name, account number, account type; bKash and Nagad: holder name and number. The bank and branch are real foreign keys, not inside the blob.
Last four, masked number
The only form of the number that reaches a screen (the bullets glyph plus the last four digits).
Fingerprint
A keyed HMAC-SHA256 (app key) of owner, type and the whitespace-stripped number. Used only to refuse the same account twice for one owner.

Guarantees from the migration: checks payout_methods_type_known, _status_known, _owner_type_known, _bank_fields_match_type; unique index payout_methods_fingerprint_unique_per_owner; trigger payout_methods_locked_owner (owner columns immutable); trigger payout_methods_never_deleted. Methods are archived, never deleted. Account and Supplier withdrawals reference this table by foreign key.

States & lifecycle

PayoutMethodStatus: active may move to archived; archived is terminal. Archiving also clears is_default. A default can only be an active method.

Actions & workflows

ClassPurpose
SavePayoutMethod::handle(ownerType, ownerId, type, label, details, bankId, branchId, makeDefault, ?existing)Create or update. Ownership is a parameter: the controller resolves the owner from its own guard. Derives last four and fingerprint, refuses a duplicate active account for the owner (checked, and caught again from the unique index), saves in a transaction under lock for updates, audits payout_method.created or .updated (sensitive; stores type and last four only). An update clears verification. Optionally sets default.
SetDefaultPayoutMethodLocks the method, refuses an archived one, clears the owner's other defaults, sets this one.
ArchivePayoutMethodTransition to archived through transitionTo(), audit payout_method.archived.
PayoutMethodsForOwner (query)forOwner() and findForOwner() filter by owner type, id and public id, default first.

The account-side controller validates type (enum), label (max 80), details as an array of strings (max 120), bank code and routing number required for bank accounts, and requires current_password to save and archive. Bank and branch come from the bank directory lookups (banks.index, banks.branches; see Bank).

A withdrawal calls PayoutMethod::toSnapshot() once, at request time (PayoutMethodSnapshot: public id, type, label, masked number, bank, branch, district, routing number). It never stores the raw details.

Permissions & scoping

PayoutMethodPolicy (business side): any user with a business account may view their own; create, update, archive and set default need "runs the business" (AccountPermission::UpdateAccount); a method is reachable only if owned by the user's account. The Supplier side is not routed through a policy: every query is scoped to the signed-in Supplier's own guard, which already isolates suppliers. Self-scoping is in the query (findForOwner), so a borrowed public id finds nothing (§31.3).

Money, ledger & audit effects

None directly. Audit actions: payout_method.created, .updated, .archived, all sensitive, with accountId set to the owner id.

Configuration

None. The fingerprint uses the application encryption key (Crypt::getKey()); rotating that key invalidates duplicate detection for existing methods.

Rules, invariants & gotchas

  • Never log, return or render details; use maskedNumber(). Never decrypt the fingerprint.
  • Editing a method does not change withdrawals already made against it (snapshot).
  • A changed number clears verification because it is no longer the verified number.
  • The duplicate rule is among active methods of the same owner and type; archive then re-add is allowed.
  • In accountId: of the audit entry the code passes $ownerId for either owner kind, so for a Supplier that is a supplier id, not a business account id.

How to…

Add a payout method type

  1. Add the case to PayoutMethodType with label(), detailFields(), requiresBankBranch().
  2. Widen the payout_methods_type_known check (and bank-fields check if relevant) in a new migration.
  3. Update the controller validation (both owner sides and mobile), the dialog in payout-method-dialog.tsx, lang strings, and the snapshot if it needs new fields.
