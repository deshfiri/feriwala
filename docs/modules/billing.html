Billing and payments

Billing prices what Feriwala charges (fees, coupons, tax, delivery), records a payment with its itemised components and invoice, settles it against a gateway, and refunds it. It also covers manual settlement, the exchange-rate layer for international gateways, webhook receipt, and the Partner-owned gateway model (D36). The Money API reference is at the end of the page.

Rule. SettlePayment is the only place a payment becomes paid. Every route in (browser return, IPN, reconciliation sweep, manual settlement) lands there or in applyPurpose(). A browser return or webhook body is never evidence: the gateway is asked server to server, every time. Payment status moves only through transitionTo().

Purpose

Everything a customer or partner pays Feriwala goes through one payments table with child allocations (registration fee, package fee, discount, tax, gateway charge, wallet deposit, goods, delivery and so on, §5.1, §9). The split is the data model: it is what makes a refund of just the package fee, or a report of registration revenue in March, possible.

  • Applicant / partner pays an activation, renewal, package change, top-up or wholesale order and reads invoices and receipts.
  • Admin staff price fees, coupons, tax and delivery; enable gateways and enter credentials; settle by hand; decide and send refunds.
  • Partner (D36) may configure its own gateway for its Storefront, where Admin allows it.
  • System verifies notifications, reconciles with providers, expires unpaid checkouts, settles refunds.

Specification: §5.1, §8.2 to §8.4, §9, §26.3, §26.4, §28.1, §36, §42. Decisions: D4 (currency, amended for exchange rates), D12 (merchant of record, Model A), D17 (refundability), D19 (tax, see Tax), D26 (flat Taka), D36 (Partner-owned gateways, Model B).

Merchant of record. For dropshipping, Feriwala is merchant of record and partner websites never use their own gateway credentials (D12). D36 adds a second, separately approved payment direction (Model B) for eligible Storefront orders only. Retail margin remains a commission calculation base, not a money path.

Key terms

Quote
A priced breakdown (ActivationQuote implements PaymentQuote): a list of QuoteLines plus the tax breakdown. Calculated entirely on the server.
Allocation
One component of a payment (AllocationType). Discount is stored positive and flagged as a deduction.
Purpose
What a payment is for (PaymentPurpose, §26.3). Decides what settlement unlocks.
Revenue
The part of a payment that is Feriwala's earning. Excludes wallet deposit, tax, gateway charge and discount. A top-up has revenue zero.
Settled
paid or partially_refunded (PaymentStatus::isSettled()). Only settled money releases anything.
IPN
The gateway's server-to-server notification. It says which payment to look at, nothing more.
Reconciliation required
Money confirmed after the checkout had closed. Real money, purchase not reopened, waits for a person.
Charge amount / FX rate
What an international gateway is asked for when Taka is converted; stored beside, never instead of, the Taka amount.
Platform / Partner ownership
GatewayOwnership: whose gateway took the money. Frozen on the payment.
Platform receivable
Under Model B, Feriwala's share of a Storefront order, collected from the Partner's wallet (D36).

States & lifecycle

PaymentStatus (§26.4)

FromMay move toTriggered by
draftinitiated, cancelledGateway session opened; deadline sweep
initiatedpending, paid, failed, cancelledGateway answers

paidrefunded, partially_refundedProcessRefund::settleStatus

failed, cancelledreconciliation_requiredLate confirmed success
refunded, reconciliation_requirednoneTerminal (reconciliation waits for a person)

Terminal in isTerminal(): failed, cancelled, refunded, reconciliation_required. Failed and cancelled are retried as a new attempt, never revived. The one exception is Payment::transitionToPaidManually(), which reads PaymentStatus::manuallySettleable() (initiated, pending, failed, cancelled, reconciliation_required; not draft) and is called only by SettlePaymentManually. Paid has no move to cancelled, so a sweep cannot cancel money that arrived.

RefundStatus (D17)

FromMay move to
requestedapproved, rejected
approvedprocessed, failed
failedprocessed (retry without re-approval)
rejected, processednone

Approval is a decision; processing is money leaving. They are separate states so a refund that fails at the gateway does not look like money that went back. A rejected request may be asked for again with new grounds.

Flow 1: activation payment, end to end

  1. CheckoutController::show builds the quote with CalculateActivationQuote (order below), lists PaymentGatewayManager::availableFor(Currency::base()), and revalidates any session coupon (nothing is reserved on a render).
  2. CheckoutController::pay validates the gateway is in that list, recalculates the quote (never trusts the form), closes anything overdue, refuses if the payment is being reconciled, and records via RecordPaymentFromQuote.
  3. A gateway session opens (StartGatewayPayment): gateway and gateway_mode are stamped, PaymentIntent::forPayment carries the success, fail, cancel and IPN URLs, and the status moves to initiated. If the gateway is unavailable the payment stays a draft so another gateway can be tried.
  4. The payer pays. Two things come back: the browser (/checkout/return and friends) and the IPN (/webhooks/payment/{gateway}).
  5. Either way SettleGatewayNotification runs. It uses dispatchSync first and falls back to the payments queue with five tries and backoff 30, 120, 600, 1800 seconds. It exits if already settled, and uses WithoutOverlapping per payment.
  6. SettlePayment::handle takes the distributed lock payment:settle:{id} (ttl 30s, wait 10s), re-reads the payment, and returns early if settled.
  7. A closed payment is still verified: a confirmed success lands in reconciliation_required, nothing activates. An overdue order is cancelled first.
  8. Verification: PartnerGatewayResolver::driverFor picks the driver (Feriwala's, or the frozen Partner version), then verify(); the answer is logged to payment_logs.
  9. Checks, in order: belongsToPayment (the gateway's reference matches ours; no other payment already holds this gateway or settlement reference), then matchesAmount(expectedGatewayAmount()). A mismatch is logged critical and marks a live payment failed.
  10. Inside a transaction, re-read with lockForUpdate, go draft to initiated if needed, then paid, storing reference, settlement reference, settled_amount, gateway_fee, completed_at.
  11. After commit, applyPurpose() (below). It never fails the settlement: each consequence is wrapped, logged and left for a sweep or an admin.

For every non-Partner payment, first a coupon held against it becomes a use (SettleCouponRedemption::redeem) and the owner gets a PaymentReceived notification (not for website_order, whose money is the shop customer's). A Partner-owned payment skips all of this (see D36).

Flow 2: quote order of operations (CalculateActivationQuote)

  1. Gather fees. Registration fee by dated rule: a rule naming the package, then the package's own registration_fee, then the global rule, then the legacy setting billing.registration_fee. Always resolved against the moment of charge, so a reissued quote reproduces the original. Unconfigured means zero.
  2. Discount comes off the fees, capped at the taxable base, and is apportioned across the taxable lines with Money::allocate() using integer ratios (smallest-unit counts). Shares always sum to the discount exactly.
  3. Tax is charged per fee on what remains, at that fee's own rate and mode (Tax). Only added (exclusive) tax joins the total.
  4. The wallet deposit is added, untaxed.
  5. The gateway charge, if the setting billing.gateway_charge_percent is above zero, is a percentage of the total at that point, added last.

Renewal quotes have no registration fee and no deposit; the fee is the terms' renewal fee, else the package fee. Package-change quotes treat the credit for unused time as a discount line, so it reduces the taxable base before tax.

Flow 3: manual settlement (SettlePaymentManually)

  1. SensitiveActionGuard requires payment.settle_manually, a reason, a freshly confirmed password and two-factor.
  2. Take the same lock as SettlePayment (payment:settle:{id}). Already settled: return "already settled", change nothing.
  3. Refuse a Partner-owned payment, a status that is not manually settleable, or a gateway reference already held by another payment.
  4. Ask the gateway about the reference the person gave. A confirmed, matching answer settles like an IPN (basis gateway_verified). A gateway that contradicts the claim (another payment's transaction, another amount) is never overridable. If the gateway cannot answer, does not support verify, or says "not paid", an explicit override flag allows basis manual_override.
  5. In a transaction: transitionToPaidManually(), store reference, completion time, settled amount (the gateway's, or the payment's own on override), append a note to reconciliation_reason, and write audit billing.payment_settled_manually (sensitive, with before and after).
  6. Write a manual_settle payment log, then run SettlePayment::applyPurpose() so a deposit credits the ledger and an order confirms exactly as for a gateway-confirmed payment.

Flow 4: webhook receipt (PaymentWebhookController)

  1. Unknown gateway: 404. On the Partner address (/webhooks/payment/{gateway}/{payment}) the payment must exist, be Partner-owned and of this gateway, or 404; the signature is checked with that payment's frozen version.
  2. A driver that cannot verify (EPS, Nagad) is answered 404: no notification from it means anything.
  3. If the driver signs notifications and the signature is bad: 401 and an inbound log row (refused_signature). Three providers do not sign; they are accepted because a notification only names a payment, and the job asks the gateway.
  4. Parse with handleCallback; an unreadable body is logged (unreadable) and acknowledged. Resolve the payment (ResolveNotifiedPayment); unknown, a Partner payment on the platform endpoint, or no transaction id: logged and acknowledged.
  5. Otherwise log queued and call SettleGatewayNotification::now(). Every non-signature outcome returns the same {"message":"Acknowledged."}, so the endpoint cannot be used to ask whether a reference exists or is paid.

Flow 5: refund

  1. RequestRefund (locks the payment, refuses a Partner-owned one, evaluates RefundabilityPolicy inside the transaction, copies the rule used onto the row, audit billing.refund_requested, announces to the staff queue). A reason is mandatory. Where the UI calls it from I did not verify.
  2. DecideRefund::approve re-evaluates eligibility inside the lock (an account activated since the request makes a package fee ineligible); reject needs a note. Audit billing.refund_approved / billing.refund_rejected; the requester is notified.
  3. ProcessRefund (route admin.refunds.process, RequirePassword): needs payment.reverse_transaction, a confirmed password, two-factor and the request's reason. Step one, claim, in a transaction: lock the request and payment; status approved or failed; refuse Partner-owned, unsettled, or no gateway; compute RefundableAmount excluding itself (approved, in-flight and processed refunds all count); check the gateway supports full or partial refund; ApplyRefundReversal::assertPossible (the wallet must be able to give the money back, taken from the kind it was credited as); write idempotency key refund:{public id}.
  4. Step two, outside any transaction, ask the provider (amount in the charged currency via gatewayShareOf). A wallet-paid payment goes back to the wallet instead (RefundPaymentToWallet: platform credit up to what the debit took from it, the rest withdrawable, keys order-refund:{id}:{kind}).
  5. Step three, record: success moves to processed, then the wallet reversal (refund_debit, key refund:{public id}), the referral reversal (ReverseQualifyingEvent::forRefund, which reverses the whole event on any refund of the qualifying payment), the payment status (refunded or partially refunded) and audit billing.refund_processed. Pending leaves it approved with the amount still claimed; unavailable leaves it approved; a definite failure moves it to failed and releases the claim. SettleRefund (every 15 minutes) asks providers what became of accepted refunds; a failed refund is never re-sent automatically.
  6. If the wallet reversal cannot post after the provider has already refunded, the refund still stands and the failure is logged critical and written to the request: a discrepancy a person must settle.

Flow 6: Partner-owned gateway (D36, Model B)

  1. Admin turns on payment.partner_gateways.enabled (default off) and lists allowed providers in payment.partner_gateways.providers (default empty) through ConfigurePartnerGatewayAvailability (payment.manage_integrations).
  2. A Partner (the business owning the Storefront, with UpdateAccount account permission; no platform role, Super Admin included) saves a gateway with SavePartnerGateway: a new immutable version holding the whole credential set. A blank field keeps what exists, except sandbox/live changes, which need every credential again. UsePlatformGateway switches back; saved versions and past payments stay. Audit carries field names, never values. I found no controller in app/Http that calls these actions, so I could not verify where the Partner UI is wired.
  3. For a new attempt, PartnerGatewayEligibility::candidate() returns usable or a named fallback reason (switch, allow-list, version, live mode in production, provider capability, credentials, currency). Order-side conditions (Non-Conditional account, central stock, defined line amounts, one payment owner) are checked where the order is placed.
  4. The payment freezes ownership, funds destination, website and the exact configuration version. From then on PartnerGatewayResolver::driverFor resolves that version for verify, notify, reconcile and refund status. Credentials are never copied into payments, logs or audit; provider HTTP errors are replaced by a generic "could not be reached".
  5. Settlement of a Partner payment verifies the same way but then does only applyPartnerPayment(): record the collection fact for the order, log partner_payment_verified, dispatch PartnerGatewayPaymentVerified. It does not confirm the order, commit stock, credit a profit, or debit a wallet.
  6. CollectPartnerReceivable (Order domain) then collects the frozen receivable from the Partner's wallet all-or-nothing under the order, collection, payment and wallet locks: platform credit first, one partner_gateway_receivable_debit entry per kind used. A short wallet is not touched; the order is held with partner_wallet_insufficient and the withdrawal path refuses new withdrawals while a live hold exists. A wallet credit (WalletCredited) or the every-minute sweep partner-receivable-collection-sweep releases waiting collections oldest first.
  7. Feriwala never records the customer's gross payment as received or refunded in Model B. The standard refund refuses a Partner-owned payment; manual settlement does too.

Money, ledger & audit effects

  • Amounts are Money in NUMERIC(19,2). A payment's amount is always the Taka the payer owes; foreign figures sit in charge_amount / settled_amount with their own currency columns.
  • Billing itself writes no ledger entry for a gateway payment into Feriwala's revenue. Ledger effects are: wallet credit for deposit and top-up (key payment:{reference}), the refund wallet reversal (refund_debit) or wallet credit (order_refund_credit), and under Model B the receivable debit (partner_gateway_receivable_debit).
  • Audit actions: billing.payment_settled_manually, billing.refund_requested, billing.refund_approved, billing.refund_rejected, billing.refund_processed, billing.fee_rule_created / _closed, billing.coupon_created / _withdrawn, billing.delivery_charge_rule_created / _closed, billing.payment_deadline_set, payment.gateway_configured, payment.gateway_enabled / _disabled, payment.gateway_connection_tested, payment.exchange_rates_updated, payment.partner_gateway_configured, payment.partner_gateway_disabled, payment.partner_gateways_availability_changed.
  • Idempotency: payments.idempotency_key (unique) for recording; refund:{public id} for refunds; payment:settle:{id} lock and payment:notification:{id} job overlap key for settlement.
  • Logs: payment channel (90 days) for critical events; payment_logs table for the per-payment trail, redacted by PaymentLogRedactor (§42: no passwords, tokens, secrets, full credentials, unmasked personal data).

Exchange rates (D4 amended)

  • An administrator enters rates by hand; nothing fetches one. Stored in setting payment.fx.rates as Taka per one unit of USD, EUR or GBP. A rate must match ^\d{1,8}(\.\d{1,6})?$ and be above zero.
  • A Taka gateway is asked for the Taka amount. A gateway that cannot take Taka is asked for the equivalent in a currency it accepts at the set rate, stamped on the payment before the gateway is called, because the confirmation is checked against it (expectedGatewayAmount()). Quoted once per currency: a retry shows and charges the same figure.
  • Rounding is stated: charging rounds the foreign figure up (PositiveInfinity), a refund share rounds down (NegativeInfinity), so partial refunds can never exceed what was charged. The whole payment refunds as exactly the charge amount.
  • Only Taka converts into a foreign currency. Setting or clearing a rate changes which gateways the Taka checkout offers; existing payments keep their quoted rate. A Partner gateway is never converted (the Partner is paid what the customer was charged).

Rules, invariants & gotchas

Gotcha: coupon value is not flat Taka. For a percentage coupon it is basis points (10 000 = 100%); for a fixed coupon it is still stored in minor units and divided by 100 in Coupon::discountOn(). The code calls this the one deliberate remaining boundary (D24 references it). Do not add a second place that reads coupons.value; go through discountOn(). Percentages round toward zero.

Gotcha: a late callback is not an error. Failed and cancelled payments are still verified; a confirmed success goes to reconciliation_required, the quote and invoice are left alone and nothing activates. Do not "fix" this by reviving the payment.

  • An invoice is created when the payment is recorded (activation, renewal, top-up), not when it settles, except order payments whose invoice is issued once paid (issuesInvoiceWhenRecorded()). Issuing is not granting; nothing reads an invoice to decide entitlement.
  • Unconfigured prices are zero and unconfigured tax is none: an unconfigured system undercharges visibly rather than invent a number (D19).
  • A top-up payment has revenue zero so a revenue report never counts a deposit as income.
  • A one-open-refund-per-request rule is a partial unique index, not a check in code.
  • Gateway fee is recorded separately and never netted off the settled amount.
  • EPS issues its own per-attempt id: PreparePaymentAttempt saves it to gateway_reference and freezes the payer address before the gateway is called, so an early return still matches.
  • Manual settlement is the single route to paid that skips the gateway callback; keep the permission narrow and never add another.
  • Settlement consequences are wrapped. If a deposit credit, activation or order confirmation fails, the payment stays paid and the problem is logged and flagged; sweeps or an admin retry (idempotently).

Money API reference

Verified in app/Support/Money/ and app/Casts/MoneyCast.php. Money is flat Taka everywhere: 100 means BDT 100 in a form, a column, an API payload, a calculation and a display. Nothing multiplies or divides by 100 to cross a boundary (D26). A repository guard test (tests/Unit/Support/Money/MoneySourceGuardTest.php) fails the build if new production code reintroduces _minor naming, poisha conversion or float money.

ClassWhat it does
Currency (enum)BDT, USD, EUR, GBP. All scale 2. base() is BDT. smallestUnit() returns "0.01". symbol() (BDT is the taka sign).
Money (final, immutable)Holds amount as an exact decimal string at the currency scale plus a Currency. All arithmetic is bcmath; float is rejected.
DecimalAmountThe only boundary for human or request input. parse(string, ?Currency, bool $allowNegative = false); parseOrNull() for blank optional fields.

Casts\MoneyCastCasts a NUMERIC(19,2) column to Money, reading currency from a sibling column (default currency_code; MoneyCast::class.':other_column' for another).
Exceptions\InvalidDecimalAmount, CurrencyMismatchParse refusals; mixing currencies in arithmetic or comparison.

Creating and reading

  • Money::fromDecimal(string|int $amount, ?Currency, RoundingMode $rounding = HalfAwayFromZero): accepts ^-?\d+(\.\d+)?$; rounds excess precision to scale (for computed fractions); refuses more than 17 integer digits. Not for what a person typed.
  • Money::zero(?Currency); toDecimal() (the column and wire value); format(bool $withSymbol = true) (grouping done on digits, not number_format); jsonSerialize() returns {amount, currency, formatted}; __toString() is format().
  • DecimalAmount::parse() rules: trimmed, digits with at most one point (no thousands separator, no exponent, no look-alike digits); negative refused unless allowed; a third decimal place is refused, never rounded away; ceiling MAX_AMOUNT = '10000000000' (compared with bccomp). Errors are InvalidDecimalAmount::malformed|negativeNotAllowed|excessivePrecision|overflow.

How to…

Add a payment purpose

  1. Add the case and label() to PaymentPurpose; decide isDeliverable(), paysForOrder(), creditsWallet(), isPaidByAccount(), issuesInvoiceWhenRecorded().
  2. Add the arm to the total match in SettlePayment::applyPurpose() and to CreditSettledPayment::typeFor(); both matches have no default so the compiler will point at them.
  3. Build a quote implementing PaymentQuote, record it with RecordPaymentFromQuote, and add a test under tests/Feature/Payment (see PaymentPurposeTest.php).

Add an allocation type

  1. Add the case and label to AllocationType; set isRevenue(), isTaxable(), isDeduction(). Set a refund default in Refundability::defaultFor().
  2. Check CommissionBase (referral) if it could be a base, and the migration that constrains the column if it has a check.

Add a payment gateway

  1. Implement the PaymentGateway contract under app/Integrations/Payment/Gateways/, declaring honest GatewayCapability values (a gateway with no Verify is never accepted by the webhook endpoint or for Partners).
  2. Register it in config/payment.php with enabled => false (a new provider arrives disabled).
  3. Add a label in lang, a test file in tests/Feature/Payment, and an entry in PartnerGatewayProviderSupport if Partners may use it. Do not put credentials in config.

Change what a fee costs

Do not edit a row. Use Admin, Billing (ManageFeeRules): close the rule and open a new dated one, so past quotes still reproduce.

Add a refund rule for a component

Set the setting billing.refundability.{allocation type} to never, before_activation or always; defaults are in Refundability::defaultFor().
