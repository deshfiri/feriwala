Website module

A partner's dedicated storefront, from the request for it through payment, build, connection to the separate storefront app, daily operation and closure. Also the machinery that keeps that storefront current: signed credentials, outbound webhooks, retries and the failed-sync queue. Read this before touching anything under app/Domain/Website, routes/api.php or the storefront.* middleware.

Purpose

A Partner whose package includes a dedicated website (§8.1, §16) asks for one. The request raises charges, which the Partner pays from the wallet. Platform staff then build the storefront by hand (D9: no registrar or hosting automation), register the domain, and connect the store to the ERP. The storefront itself is a separate Laravel application (Storefront app) that never touches the ERP database; it reads the catalogue and posts orders through the frozen Storefront API, and the ERP tells it about changes by signed webhook (D11, D32).

Who uses it:

  • Partner (business account owner or an account role holding AccountPermission::UpdateAccount): requests websites, pays charges and renewals, edits branding, selects and prices products, reads orders, retries failed deliveries.
  • Platform staff: website.view / website.edit to administer; website.manage_integrations (Super Admin by default) to connect a store, issue credentials and manage the webhook secret; website.manage_settings for platform-wide price rules.
  • The storefront app: the machine caller, authenticated by an HMAC-signed credential.
  • System: the scheduler (lifecycle sweep, webhook retries, inventory and catalogue sync, promotion windows, best sellers).

Implements §15, §15.1, §16.1–§16.4, §17 and §24.3 of requirements.txt; decisions D9, D11, D12, D30 (partly superseded), D31, D32 (credentials and webhooks are staff-managed, Option P1), D34. The contract is requirements/05-storefront-api-contract.md.

Rule. Feriwala is merchant of record (D12). A storefront never holds a gateway credential, never computes a price, and never sees a wholesale price, cost or margin. There is no wallet, ledger, KYC, commission or user scope in the API: the surface does not exist to be granted.

Key terms

Website
One dedicated storefront, owned by exactly one business account. The owning account cannot change; the database refuses it. It is the tenancy boundary of the API.
Store / connecting a store
Staff attaching a deployed storefront app to a website: its address is recorded, one credential is issued, and a webhook is registered when possible. Done in one action, ConnectStore (D32).
Store id, token
The credential's key_id (wsk_ followed by a 26-character ULID) and its secret. The storefront's .env calls them STORE_ID and STORE_TOKEN.
Credential
A WebsiteCredential: a key id, an encrypted secret and an explicit list of scopes. Shown once; rotatable; revocable.
Scope
A CredentialScope case limiting what a credential may call. Never granted by default.
Preset
A CredentialPreset: a starting point that fills the scope checkboxes. What is issued is exactly what staff submit.
Webhook endpoint
The single HTTPS address per website the ERP posts signed events to, with its own signing secret.
Delivery
One event queued for one website's endpoint, with a stable event_id across retries.
Dead letter
A delivery in state failed, with an unresolved SyncQueueFailure for a person to retry.
Selection
A WebsiteProduct: a central catalogue product a Partner chose for one storefront. Selection is not authorship; partners never create products (§15, §16.3).
Price rule
A WebsiteProductPriceRule: the administrator's bounds on what a Partner may charge (§15.1).
Allocation
A WebsiteAllocation: one slot per website a package purchase entitles, carrying the package-based domain and hosting periods (D30 §9).
Local address
A plain-HTTP address such as http://127.0.0.1:8001, accepted only while website.allow_local_addresses is on.
Connection health
WebsiteConnectionHealth: unknown, healthy, degraded, failing, derived from how recent deliveries went.

Money columns are MoneyCast columns: exact decimal Taka plus a currency_code column. Public identifiers are ULIDs via HasPublicId where noted; no database id appears in a URL.

Flow 1: request, pay, build

  1. The partner submits the request form. SubmitWebsiteRequest interprets the address: a local URL (when allowed) is stored as the domain; a plain label must not be reserved (website.reserved_subdomains) and must be unique; anything else (myshop.com, a URL) is kept in requested_address and the website gets a generated subdomain label. Asking never claims a domain.
  2. RequestWebsite::handle() checks entitlement (account can transact, package includes PackageFeature::DedicatedWebsite, website limit not reached, slots not all lapsed), then inside one transaction locks the business_accounts row, re-checks, creates the website in setup_pending with the fee snapshot, writes the first history row, attaches an allocation slot (AllocatePackageWebsite::attachWebsite; no slot means the whole request rolls back), and creates a due WebsiteCharge per positive fee. A package that includes the domain or the hosting (PackageFeature::DomainIncluded, HostingIncluded) charges nothing for it.
  3. A unique-constraint failure becomes WebsiteRefused::subdomainTaken(). After commit: audit website.created and an announcement on the staff queue (StaffQueue::WebsiteRequest).
  4. The partner pays each charge (websites.charges.pay). SettleWebsiteCharge locks website:charge:{id}, debits the wallet with idempotency key website-charge:{public_id}, marks the charge paid with its wallet_transaction_id, audits website.charge_paid, and when nothing is outstanding moves the website to development. An uncovered wallet moves a setup_pending website to deposit_pending and throws WebsiteRefused::insufficientBalance().
  5. Staff build the storefront and register the domain by hand: admin.websites.domains.store (ProvisionWebsiteService::registerDomain, which also makes it the website's primary domain), admin.websites.hostings.store.

Flow 2: connect the store (D32)

Staff holding website.manage_integrations open the website in Admin, Websites, and use "Connect the store" (admin.websites.connection, WebsiteConnectionController::store). ConnectStore::handle():

  1. Refuses if a non-revoked credential already exists (WebsiteRefused::alreadyConnected()): one store connection per website. To change the token, rotate.
  2. Parses the address. If LocalAddress::parse() accepts it (only while local addresses are allowed) the host and port are taken as typed; otherwise normalise() strips scheme and path and rejects anything with a port, whitespace or no dot.
  3. In one transaction: FreeAddressOfClosedWebsites releases the name if a closed website held it; the address is recorded (a local one straight onto websites.domain, refusing if another website holds it; a real one through ProvisionWebsiteService::registerDomain() unless this website already holds that domain); then ManageWebsiteCredentials::issue() creates a credential named "Storefront" with CredentialPreset::Storefront scopes.
  4. For a real address only, after the transaction: registerWebhook() configures the endpoint at https://<domain>/webhooks/feriwala (ConnectStore::WEBHOOK_PATH). If ManageWebhookEndpoint::configure() refuses it (no DNS yet, private address) the store is connected without a webhook; the storefront refreshes its catalogue by cache expiry. If an endpoint was left from an earlier connection, its secret cannot be read back, so a new one is issued by rotating.
  5. Audit website.store_connected (sensitive), then return a ConnectedStore. The controller answers once with store_id, token, address, local, webhook_url, webhook_secret, erp_base_url and an env block (ERP_BASE_URL, STORE_ID, STORE_TOKEN, optionally WEBHOOK_SECRET, and APP_ENV=local for a local address), with Cache-Control: no-store, private. Nothing secret goes to the session, a flash message, a prop, the audit trail or a log.

rotate() issues a new token and keeps the old one valid for the grace window; disconnect() (a reason of at least five characters is required) revokes every active credential and disables the webhook in one transaction, audits website.store_disconnected, and leaves the address recorded.

CredentialScope::defaults() is catalogue and inventory read. CredentialPreset::Catalogue is catalog:read only (a preview or a site that does not sell yet). CredentialPreset::Storefront is all six scopes and is what ConnectStore issues. A credential with no scope is refused with an InvalidArgumentException; there is no implicit grant (ER-7).

The secret is 32 random bytes as hex, encrypted at rest, returned only by the issue()/rotate() call. Rotation moves the current secret to previous_secret with an expiry of website.api.rotation_grace_minutes (default 1440) and acceptedSecrets() returns both while the window is open. Revocation is immediate and final: it clears the previous secret and needs a reason; a revoked credential is never un-revoked.

Webhook endpoint, signing secret and rotation

ManageWebhookEndpoint owns one WebsiteWebhookEndpoint per website.

  • configure($website, $actor, $url, $acceptUnresolved = false): refuses a closed website; validates the URL (https only, no embedded credentials, port 443 only, not localhost, *.localhost or *.internal, not a private or reserved IP literal); then resolves the name through OutboundAddressGuard, which refuses any private resolution. A name that does not resolve yet is refused, unless $acceptUnresolved is true. A first call creates the endpoint and returns the secret once; later calls only change the URL and reactivate it (the secret is returned as null). Audit website.webhook_configured.
  • rotate($endpoint, $actor): new secret, old one kept as previous_secret for the same grace window as credentials; audit website.webhook_secret_rotated. Returns the new secret.
  • regenerate($website, $actor): a secret is available even when connecting skipped the webhook. If an endpoint exists it rotates it; if none exists (the store was connected before its DNS resolved, or the webhook was never set) it registers one at https://<website host>/webhooks/feriwala and returns the freshly issued secret. This is what the admin page calls through admin.websites.webhook.rotate; the button reads "Rotate" when an endpoint exists and "Generate webhook secret" (website.integration.generate) when it does not (storefront-webhook.tsx).
  • disable($endpoint, $actor): is_active = false; audit website.webhook_disabled. Nothing is queued for an inactive endpoint.

The controller (Admin\WebsiteWebhookController) is the only response that may carry the secret, marked no-store. Hand-typed addresses (admin.websites.webhook.store) pass acceptUnresolved: true, because staff may be ahead of their DNS; every automatic path keeps the strict default.

The storefront verifies with WEBHOOK_SECRET and, during a rotation, WEBHOOK_SECRET_PREVIOUS; see the Storefront app page and the signature scheme in the Storefront API page.

Webhook deliveries, retries and the dead letter

  1. Queue. A domain action calls PublishWebsiteEvent::handle($website, $event, $data, $subjectType, $subjectId). Nothing is queued if the website does not acceptsSync() (except website.suspended and website.restored, which must reach a shop that is not served) or has no active endpoint. The payload is {event, occurred_at, website_id (public id), data}. A pending, never-attempted delivery for the same event and subject is updated in place (a burst of five price nudges becomes one delivery). Otherwise a WebhookDelivery is created with a fresh ULID event_id, and DeliverWebhook is dispatched after the surrounding transaction commits, so a rolled-back change never tells a storefront it happened.
  2. Attempt. DeliverWebhook runs on the webhooks queue (WEBSITE_WEBHOOK_QUEUE), $tries = 1, guarded by WithoutOverlapping('webhook-delivery:{id}'). AttemptWebhookDelivery::handle() locks the delivery row, skips one already finished or not yet due, increments attempt, then resolves the endpoint host again, requires every address public and pins the connection to the checked address with CURLOPT_RESOLVE (no DNS rebinding), sets the four X-Feriwala-* headers, posts with a 10-second timeout and allow_redirects = false. A 3xx is just a non-2xx answer.
  3. Log. Every attempt writes a WebhookLog with redacted headers (PaymentLogRedactor), the status, duration, the first 500 characters of the response, and the transport error.
  4. Outcome. Any 2xx: delivered, the website's webhook_connected_at and last_synced_at are set, the product named by a product event is marked synced (only if it has not changed since the event was queued), and open failures for that delivery are resolved. Otherwise the delay after attempt n is website.webhooks.backoff[n-1]: 10 s, 30 s, 2 min, 10 min, 30 min, 2 h, 6 h, 12 h. The state becomes retrying with next_retry_at. Once the delays are used up (the ninth attempt failing; the database caps attempt at 9) the state becomes failed, a SyncQueueFailure is created or updated, and the product is marked sync_status = failed with the error.
  5. Retry schedule. The schedule lives in the delivery row, not in delayed queue jobs: a worker restart mid-backoff loses nothing. DispatchDueWebhookRetries runs every minute and queues deliveries whose next_retry_at has passed.
  6. Manual retry. RetryWebhookDelivery (websites.deliveries.retry, partner and admin) accepts only a failed delivery, keeps the same event_id so the storefront recognises it, sets state to retrying with attempt = min(attempt, 8) (so one more attempt, and a failure goes straight back to failed), increments the failure's retry_count, and audits website.webhook_retried.
  7. Health. After every attempt connection_health is recomputed: failing if an unresolved failure from the last day exists; else degraded if any of the last 20 deliveries is retrying; else healthy if any is delivered; otherwise unchanged. A first authenticated API call also lifts unknown to healthy (AuthenticateStorefrontRequest::noteUse).

Events (WebhookEvent): product.published, product.updated, product.unpublished, product.price_changed, inventory.updated, inventory.out_of_stock, category.updated, order.status_changed, order.cancelled, cod.confirmation_required, cod.confirmed, cod.expired, shipment.updated, return.status_changed, refund.completed, website.suspended, website.restored, website.updated. I found emitters for every case except shipment.updated (no WebhookEvent::ShipmentUpdated reference outside the enum; not verified whether it is emitted dynamically). Sync queue and catalogue synchronisation

  • Real time. Partner and admin edits call UpdateWebsiteProduct, SetWebsiteProductPublication, ManageWebsiteCategories and so on, each of which marks the selection sync_status = pending and publishes an event.
  • Scheduled. SyncWebsiteCatalogue::sweep() every 15 minutes re-announces products whose catalogue record changed after the shop last synchronised, and selections whose last event never went out. SyncWebsiteInventory every 5 minutes compares each published product's availability with synced_availability and sends only changes (inventory.updated; inventory.out_of_stock when the last unit goes). AnnouncePromotionWindows every minute sends one product.price_changed per promotion opening or closing, recording the new state with promotion_live under a row lock.
  • Manual. "Synchronise now" (websites.sync.store) calls SyncWebsiteCatalogue::handle() for everything.
  • The failed-sync queue is the set of unresolved SyncQueueFailure rows shown on the integration page with a Retry button.

Selections, pricing and publishing

  1. SelectProductForWebsite checks the product is still eligible for the account on the dropshipping channel (ProductEligibility) and creates an unpublished, unpriced selection, pre-filled with the suggested price where one is set. From My Products, SetPurchasedProductOnWebsite selects and publishes in one step.
  2. UpdateWebsiteProduct resolves the pricing terms with ResolveWebsitePriceRule::for() and checks every figure on every save. The resolver walks outward: a rule naming this product and package, then the product only, then the package only, then the global rule; specificity beats recency, and the latest effective_from wins at one scope. Where a rule states no bound, the product's own minimum_selling_price, maximum_selling_price and suggested_selling_price stand. With nothing configured anywhere a partner may price freely above zero. A locked field is refused, not ignored.
  3. SetWebsiteProductPublication publishes only when: a price is set, the product is still eligible, the account has not used its publish limit (counted under a lock across all the account's storefronts), and the owner has units left to sell (D34). Unpublishing is always allowed.
  4. A product is listed by the API only while it is published on that website, eligible for the owner to sell by dropshipping, and bought by the owner (StorefrontSelections). Every catalogue read starts there, so nothing listed is refused at checkout for being ineligible.

Custom domains and the shared TLS check

ManageWebsiteDomainRouting proves a custom domain by DNS TXT. issueVerification() issues banij-verify-<40 random characters> and returns the domain to unverified; verify() reads TXT records at _banij-verify.<domain> through App\Integrations\Dns\Contracts\TxtRecordResolver and moves it to verified only on a match. A failed lookup is a failure with a reason, never a pass and never a demotion. activate() needs a verified or suspended domain whose registration is running on a website that is not closed; suspend() needs an active one and a reason. Steps that change which hosts serve announce website.updated. ResolveWebsiteHost answers "which website does this host belong to": a subdomain of STOREFRONT_DOMAIN, or a verified and active domain whose registration is running, on a website that is not closed. It backs the stated-host check on the API, WebsiteAddresses (whether a customer may be redirected to a return URL), and Caddy's on-demand certificate check (GET /api/internal/tls/authorize, off until STOREFRONT_TLS_ASK_TOKEN is set).

Renewals and the daily sweep

RenewWebsiteService::renewDomain()/renewHosting() raise the charge at today's price, settle it from the wallet, and only then extend the term from the later of the current expiry and today; the reminder stage is reset and a website in the matching renewal-pending status goes back to active. SweepWebsiteLifecycle asks, per open website: still entitled? If not, a live website enters grace_period for website.grace_days (7) and then package_expired; if entitled again it is restored to active. Does the wallet still meet the agreed minimum (DepositGuard)? Flag or clear low_wallet_balance. Has a domain or hosting term run out? Mark the service expired and move a live website to temporarily_disabled. Is a term inside a reminder stage (website.renewal_reminder_days: 30, 14, 7, 1)? Move an active website to the renewal-pending status and notify the owner once per stage (WebsiteRenewalDue). It is idempotent: every move goes through the status map, and the stored reminder stage prevents a second message.

Money, ledger & audit effects

  • Website fees are snapshotted at request time (setup_fee, domain_fee, hosting_fee, required_deposit, minimum_balance) so a later fee-rule change never re-prices an existing website. Renewals are priced at the renewal date.
  • Charges are paid only from the wallet, never by a gateway: WalletService::debit() with a ledger type from WebsiteChargeType::ledgerType(), idempotency key website-charge:{public_id}, inside DB::transaction and a DistributedLock (website:charge:{id}, TTL 15 s, wait 5 s). The charge's unique wallet_transaction_id means one transaction can settle one charge.
  • Prices shown to the storefront are the website's own selling price. Wholesale price, cost and margin never appear in any payload or error.
  • Audit actions (module website): website.created, website.status_changed, website.store_connected, website.store_disconnected, website.credential_issued, website.credential_rotated, website.credential_revoked, website.webhook_configured, website.webhook_secret_rotated, website.webhook_disabled, website.webhook_retried, website.domain_registered, website.hosting_started, website.domain_verification_issued, website.domain_verified, website.domain_activated, website.domain_suspended, website.charge_paid. Secrets are never written to audit rows: only the key id, the hint and the expiry. Credential and webhook entries use PermissionAction::ManageIntegrations->isSensitive(); the connect and disconnect entries are marked sensitive.

Rules, invariants & gotchas

Rule. A secret is shown once and never stored in the clear, put in the session, a prop, a flash, the audit trail or a log. A screen that can show a secret again is a screen that can leak it again. The partner sees only the last four characters.

Gotcha: a webhook secret can exist without a working webhook. ConnectStore skips the webhook when the storefront is not reachable yet, and always skips it for a local address. Do not assume a connected store has an endpoint. Use "Generate webhook secret" (ManageWebhookEndpoint::regenerate) once the address resolves.

One .env vocabulary. Both ConnectedStore::env() (the one-step connect) and StorefrontEnvironmentBlock (the hand-made credential endpoint, admin.websites.credentials.store) emit ERP_BASE_URL, STORE_ID and STORE_TOKEN, which is what storefront/config/erp.php reads. StorefrontEnvironmentBlock used to emit BANIJ_* names that the storefront never read; the constants and the tests that pin them were changed together.

Gotcha: maintenance still authenticates. AuthenticateStorefrontRequest::websiteIsServing() accepts live statuses plus development, api_connection_pending and maintenance. Credentials of a suspended, temporarily_disabled, package_expired or closed website get 403 website_unavailable. But PublishWebsiteEvent treats maintenance and api_connection_pending as sync-accepting while development is not, so a website in development receives no webhooks even though it may call the API.

Intended. A website that is already in the target status is returned unchanged by MoveWebsiteStatus, not refused: the daily sweep would otherwise refuse every website it already fixed.

  • The retry schedule is data in webhook_deliveries, not delayed queue jobs. A manual retry reuses the event_id; consumers deduplicate on it. Delivery is at-least-once and unordered.
  • Webhook address rules are applied twice: when the endpoint is saved and before every attempt. A name that later resolves to a private address is refused at send time with AttemptWebhookDelivery::ADDRESS_REFUSED; the partner reads a translated summary (AttemptWebhookDelivery::describe()), never the transport error, which names internal hosts and stays in webhook_logs.
  • Idempotent replays: a stored answer is returned byte for byte with Idempotent-Replay: true; 5xx, 401, 403 and 429 answers are not stored. The request fingerprint is an HMAC keyed with app.key, so a one-time confirmation code in a body cannot be recovered from the table.
  • Only admins create products. The website Actions have no route into the catalogue (ManageWebsiteBranding says so in its docblock, §16.3).
  • Closing a website cancels its domains and frees the name; the address stays on the closed website as requested_address.
  • A non-resolving webhook host is refused for automatic paths on purpose. Do not relax OutboundAddressGuard to "just register it"; it exists to stop the ERP calling its own network.
  • Legacy columns websites.lists_whole_catalogue and website_products.auto_listed are unused and slated for a cleanup migration.

How to…

Add a webhook event

  1. Add a case to App\Domain\Website\Enums\WebhookEvent. It is additive under contract §8 (a storefront must tolerate unknown events); add it to concernsProduct() only if it decides a selection's sync status.
  2. Call PublishWebsiteEvent::handle($website, WebhookEvent::X, $data, $subjectType, $subjectId) from the Action that makes the change, inside its transaction. Pass a subject so duplicates coalesce. Never put a cost or margin in $data.
  3. Add a row to the events table in requirements/05-storefront-api-contract.md (§7.1) and to the OpenAPI description source docs/api/storefront.md if consumers must know. Make the storefront app tolerate it (its Webhooks::apply() ignores unknown events).
  4. Test with Http::fake() against WebhookDeliveryTest's pattern; fake DNS (see Testing).

Add a credential scope

  1. Add a case to CredentialScope with a label(); decide whether any CredentialPreset includes it.
  2. Guard the new routes with storefront.scope:<value> in routes/api.php. Update the scope table in the contract (§3.4); a new scope is additive, a removed one is breaking (needs v2).
  3. The website_credentials.scopes column is a JSON array that the database only checks to be an array (the scope values are not enumerated in a CHECK), so no migration should be needed; existing credentials simply lack the scope.
  4. Add the lang strings for the label in lang/en/website.php and lang/bn/website.php if it is shown in a screen.

Add a status or a legal move

  1. Edit WebsiteStatus: the case, transitionsTo(), and isLive(), isBeingBuilt(), acceptsSync() as appropriate.
  2. The websites.status and history CHECK constraints are built from WebsiteStatus::values() at migration time, so add a migration that replaces them (look at 2026_09_28_100000_create_websites.php and ..._110000_create_website_status_history.php).
  3. Add the translated label under website.statuses in both language files and a pill tone in the frontend.
  4. Make the move through MoveWebsiteStatus only; add a WebsiteStatusReason case if the sweep or billing makes it.

Make a change visible to storefronts

  1. If it changes how a website is presented (branding, hosts, payment methods) call AnnounceWebsiteUpdated; its payload is intentionally minimal, so also expose the data through GET /site (SiteController).
  2. If it changes a product, mark the selection pending and publish through SyncWebsiteProduct.

Connect a storefront on your own machine

  1. Run the ERP with APP_ENV=local (or set WEBSITE_ALLOW_LOCAL_ADDRESSES=true) and run the storefront with php artisan serve --port=8001.
  2. In Admin, Websites, open the website, "Connect the store", and enter http://127.0.0.1:8001. No webhook is registered for a local address.
  3. Paste the shown ERP_BASE_URL, STORE_ID, STORE_TOKEN into the storefront's .env and run php artisan storefront:doctor. See Storefront app.
