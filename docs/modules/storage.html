Storage module

Managed file storage: one place that decides which disk a file is written to and read from, an admin-configured Cloudflare R2 backend, a metadata table for files that previously had none, and a resumable command that moves existing local files to R2. Read this before adding any upload feature.

Purpose

Files in Feriwala fall into two kinds: public assets that anyone with the address may load (product images, brand and category images, website logos, branding, content-library files) and private files that may only be streamed through a controller that checks permission (KYC documents, supplier listing media, case evidence). The module lets storage move from the local disks to Cloudflare R2 without every caller being told: a caller asks for a StorageVisibility, not a disk name. It was built as the "beta-critical batch" (code comments refer to Commits 3, 4 and 5 of that batch). Users: administrators with the integration.* permissions (configuration) and every upload surface in the application.

Key terms

Managed file
A file written through StoreManagedFile and tracked by a stored_files row.
Visibility
A property of the file (public or private), independent of which backend holds it.
Local disk name
A disk from config/filesystems.php. Surfaces with their own dedicated disk (kyc, supplier-media) keep it when R2 is off.
Stored disk name
The value of a row's own disk column (public, private, kyc, supplier-media or r2). The disk a file is read from is always its own column, never today's active disk.
r2
A stored disk name only. It is not registered in config/filesystems.php; R2Manager builds it on demand from the settings table.
Available vs configured vs enabled
isConfigured(): all five required fields present. isEnabled(): the switch is on. isAvailable(): both. Only available R2 takes over writes.

A trigger (stored_files_locked_columns, function feriwala_catalogue_columns_are_locked) rejects updates to public_id, path, fileable_type, fileable_id. disk was originally locked too; the second migration released it because the R2 migration must flip it once from a local disk to r2.

stored_files does not replace product_media, supplier_listing_media, kyc_documents or supplier_kyc_documents. Those keep their own disk/path/size_bytes columns and compliance history; stored_files is the home for surfaces that previously tracked nothing. Settings rows for R2 live in the settings table (below), not in a table of their own.

States & lifecycle

There is no status enum. The only lifecycle is a file's disk: a local disk until MigrateManagedFileToR2 flips it to r2 (once, one way), plus the R2 switch itself (storage.r2.enabled). Turning R2 off does not move anything back: existing rows keep disk = 'r2' and resolveNamedDisk('r2') still builds the R2 disk from the stored credentials.

Writing a file (StoreManagedFile::handle())

  1. The caller passes the upload, a purpose, a StorageVisibility, its own MIME allow-list and $maxBytes (no defaults), optionally encrypt, a fileable owner, createdBy, retainUntil and an extension-by-MIME override.
  2. The MIME type is read from the file's own bytes via $file->getMimeType(); one outside the allow-list throws UnacceptableFile::mimeNotAccepted; a larger size throws tooLarge. Callers catch it and raise their own domain refusal (e.g. WebsiteRefused).
  3. SHA-256 is computed over the plaintext; the path is {purpose}/{random 32 hex}.{ext}; $disk->put() stores the bytes (or encrypt($bytes)).
  4. A StoredFile is created recording the disk name actually used (diskNameFor), visibility, size (strlen($bytes)), checksum and flags.

Callers I found using StoreManagedFile: platform branding (Settings\Actions\ManageBranding), website logo/banner (Website\WebsiteImageStore), brand/category images (Catalog\CatalogImageStore), product content attachments (Catalog\Actions\PublishProductContent), content library (ContentLibrary\Actions\UploadContentLibraryFile), case evidence (Cases\Actions\StoreCaseEvidence, private).

Configuring R2

  1. Admin opens Settings → Storage (admin.storage-settings.index). The controller returns only booleans and a masked access key (•••• plus the last four characters); secrets are never sent to the browser.
  2. Saving (PATCH) and switching on/off (PUT) sit behind the RequirePassword middleware. ConfigureR2Storage then runs SensitiveActionGuard::authorize() with PermissionModule::Integration / ManageIntegrations, a required reason, password-confirmed and two-factor flags (enforced again inside the action).
  3. R2StorageSettings::candidate() merges submitted fields over stored values: a blank field means "keep what is there", never "clear".
  4. The five required fields (account_id, access_key_id, secret_access_key, bucket, endpoint) must be present, then TestR2Connection runs a live directoryExists('') against the bucket. If it fails, nothing is written; the previous configuration is untouched by construction.
  5. Each field is stored with SettingsRepository::define()/set() under the storage group; access_key_id and secret_access_key are marked encrypted. Audit: storage.r2_configured (sensitive; field names written, bucket and endpoint, never values).
  6. Entering credentials is preparation. setEnabled(true) is the moment uploads start landing on R2 and requires isConfigured(). Audit: storage.r2_enabled / storage.r2_disabled.

R2Manager::diskConfig() produces an s3 driver config with use_path_style_endpoint = true, url = the public domain, visibility = default visibility, throw = true. It builds the disk with Storage::build() instead of registering it, so a credential rotation applies on the next call without a config cache clear. sanitize() redacts AWS4-HMAC-SHA256… and Authorization: text from provider errors and truncates to 500 characters.

Migrating existing files (storage:migrate-to-r2)

php artisan storage:migrate-to-r2 --mode=inventory
php artisan storage:migrate-to-r2 --mode=dry-run
php artisan storage:migrate-to-r2 --mode=migrate --chunk=200 --report=/path/report.json
php artisan storage:migrate-to-r2 --mode=verify
ModeBehaviour
inventory (default)Counts per source: total, already_on_r2, eligible. No disk access.
dry-runInventory plus missing_local_file count (checks Storage::disk($disk)->exists()). No writes, no network to R2; safe before R2 is configured.
migrateFor each row not on R2: read local bytes, upload to R2 unless that object already exists, read it back, compare SHA-256, and only then set the row's disk to r2. The local original is never touched. Outcomes: migrated, already_on_r2, missing_local_file, verification_failed. Rows already on R2 drop out of the next run's query, so it is resumable. Requires R2 available.
verifyRe-checks every row already on R2 against its recorded size and checksum (where the table has one). Outcomes: verified, missing_remote_file, verification_failed. Never writes. Requires R2 available.

The command prints the report as JSON, or writes it to --report. Unknown mode returns failure; RuntimeException (e.g. R2 not available) is reported as an error and returns failure.

Permissions & scoping

No storage-specific permission module exists. StorageSettingsPolicy reuses integration.*: canView needs integration.view, canManage needs integration.manage_integrations (the latter covers saving, switching and the live test, since all touch the secret). The permission names are built via PermissionCatalogue::name(PermissionModule::Integration, ...). The code comment says SystemAdministrator holds all three verbs. Serving a private file is the responsibility of each surface's own controller (supplier ownership or the staff supplier_listing.view permission for listing media, KYC review permissions for KYC); this module only supplies the disk.

Money, ledger & audit effects

No money. Audit entries (module storage, all sensitive): storage.r2_configured, storage.r2_enabled, storage.r2_disabled. No audit row is written per file migrated.

Rules, invariants & gotchas

Rule. Resolve a stored file's disk from its own disk value through ManagedStorage::diskForFile() / resolveNamedDisk(). Storage::disk('r2') does not exist.

Product media in local development (CLAUDE.md). With R2 not configured, product images go to the local public disk and their URLs are {APP_URL}/storage/catalog/products/…. Three things must hold for those URLs to load: (1) php artisan storage:link has created public/storage; (2) APP_URL is the origin the app is actually served on, port included (http://127.0.0.1:8000 for php artisan serve, not bare http://localhost); (3) anything outside this machine, such as a preview storefront, can only load them if that origin is reachable from it over HTTPS. Each product_media row records its own disk, so a later move to R2 changes new uploads only; the storefront payload resolves every URL from the row's disk.

  • Switching R2 on moves writes only. A file written locally before R2 was enabled stays on the local disk until storage:migrate-to-r2 --mode=migrate. Reads follow the row's disk column, so both coexist.
  • When R2 is available it takes over every managed surface, including the private ones (kyc, supplier-media, private). diskFor() returns the same R2 disk regardless of visibility, so confidentiality for private files on R2 depends on the app never exposing a direct URL (url() returns null for private files) and on the bucket's own configuration, not on a separate private bucket in code.
  • Public URLs on R2 come from storage.r2.public_domain; if it is unset, url() on the R2 disk has no base. ManagedStorage::url() and urlForPath() swallow the exception and return null.
  • Bare path surfaces (diskForPath) find their disk by stored_files.path. Because path is unique and random, collisions are not a concern, but a file with no tracked row always resolves to whatever disk today's visibility maps to.
  • Secrets. Never print or log R2 values, never add a prop that returns them, and never write them in an audit payload. Follow the existing "report presence, never the value" pattern.
  • One-way, verified, non-destructive migration. The command never deletes the local copy. Cleanup of local files is manual and out of scope.
  • Encrypted files: the checksum is over plaintext, but MigrateManagedFileToR2 compares ciphertext bytes it copied, so migration verification is self-consistent while verify on an encrypted stored_files row would compare size_bytes (plaintext length) against ciphertext length. See the report: not verified whether any stored_files row is created with encrypt: true today.

How to…

Add a new upload feature

  1. Inject StoreManagedFile; call handle() with your own MIME allow-list and size cap, a purpose and a StorageVisibility. Pass fileable and createdBy where there is an owner.
  2. Catch UnacceptableFile and raise your module's own refusal.
  3. For public files render with ManagedStorage::url($storedFile); for private files stream through a controller that checks permission (diskForFile() + response()), or use temporaryUrl() when it returns non-null.
  4. Delete with DeleteManagedFile::handle() (or forPath() on replace).

Add a table to the R2 migration

  1. The table must have a per-row disk column, a path and a recorded size (and ideally a checksum).
  2. Add a MigrationSourceDefinition to MigrationSources::all() and extend MigrateManagedFilesToR2Test.
  3. Make sure every reader of that table resolves via resolveNamedDisk() with the row's disk.

Test an R2 change without real credentials

  1. Follow tests/Feature/Storage/MigrateManagedFilesToR2Test.php and ManagedStorageTest.php for how R2 and the settings are faked.

Make a product image URL load locally

  1. Run php artisan storage:link.
  2. Set APP_URL to the origin and port you actually serve on, then clear config cache if it is cached.
