Courier module

Shipments, courier providers and the Steadfast integration. A provider-neutral shipment domain (manual first, D8) with one real API provider, Steadfast, behind a shared contract. Used by courier staff in the admin panel, by the system (webhook and scheduled poll) and, read-only, by Partners through order pages and bell notices.

Built locally, never run live. Per requirements/06-steadfast-courier.md and the code comments, the Steadfast contract was taken from Steadfast's maintained package source, not from a live service. No test or script has made a real booking, and a real create_order creates a live, possibly chargeable consignment. Do not run one without explicit approval. The unverified assumptions are listed under "Rules, invariants & gotchas".

Purpose

Orders need to leave the warehouse with a courier and be tracked until delivered or returned (§21, D8). This module holds the shipment record, the provider contract, and the Steadfast driver. D8 sets the order of work: a driver contract and a manual workflow first (courier name, tracking number, delivery charge, COD amount, statuses, return charge, notes, manual reconciliation), then Steadfast, then Pathao; RedX, eCourier, Paperfly and Sundarban later through the same interface.

Booking only asks a courier to take a parcel. It does not dispatch the order, move stock, record cash on delivery, credit profit or mark anything picked up or delivered. Those are separate, existing paths in the Order module.

Key terms

Shipment
One courier-neutral consignment for an order. An order can have several (a failed delivery can be retried through a fresh shipment). Never deleted.
Provider
A seeded courier_providers row. Manual is usable; Steadfast is usable once configured and switched on; Pathao exists as a disabled row with no driver.
Booking attempt
The record of asking a provider to take a parcel, written before the call so a lost reply leaves something to reconcile.
Uncertain
A booking whose outcome Banij does not know. Never retried blind.
Invoice
Banij's own order reference (ORD-...), sent as Steadfast's invoice. It is the one identifier both sides know before any reply, and the key for every lookup.
Provider status
Steadfast's raw status string, kept as received in shipments.provider_status as a diagnostic. The application acts on the typed OrderCourierStatus, never on this string.
Needs review
shipments.needs_review: a person has to look at this parcel.

States & lifecycle

Shipment status = OrderCourierStatus

A shipment has no enum of its own. Its status is OrderCourierStatus (defined in the Order module), and the order's courier_status axis mirrors it. Moves go through transitionWithHistory() from the RecordsStatusHistory concern, never by assigning the attribute.

A reason is required for cancelled and failed_delivery. The mapping onto the order's delivery axis is in RecordManualCourierStatusUpdate::mapToDeliveryStatus() (picked_up → shipped, in_transit → in_transit, delivered → delivered, failed_delivery → failed_delivery, cancelled → cancelled; returned_to_origin has none on purpose: it is a courier depot fact, distinct from a customer return).

Booking sequence (BookSteadfastShipment)

  1. Refuse if Steadfast is not available (CourierManager::isAvailable(): a configured driver and an enabled row) with CourierProviderUnavailable.
  2. Begin, in a transaction under a row lock on the order: refuse if a live attempt exists (needs_reconciliation, already_booked or already_in_progress); refuse a Store Order not yet dispatched (not_dispatched, via StoreOrderStep::hasDispatched()); refuse if a non-cancelled shipment exists or the order cannot move to courier assigned and delivery courier_assigned (order_not_ready), checked before the call because a parcel booked and then unrecordable is the failure this sequence exists to avoid. Build the request, write a pending attempt with idempotency key steadfast:{order public id}:{ulid}, audit courier.booking_requested, commit.
  3. Call Steadfast outside any transaction (SteadfastClient::createOrder()). A network call must never hold a lock, and a rollback must never pretend a parcel was not booked.
  4. A SteadfastException is classified: kinds whose outcome is unknown (timeout, unexpected) make the attempt uncertain; the rest (not_configured, authentication, unreachable, validation) make it failed. Both notify staff after commit.
  5. On success the consignment id, tracking code and raw status are saved onto the attempt's snapshot at once (so reconciliation has them if the next step fails), then RecordSteadfastBooking creates the shipment (delivery charge = the order's delivery; COD amount from the snapshot), sets external_id, provider status and sync times, and marks the attempt booked. If recording fails, the attempt becomes uncertain with code local_failure.

The request is built only from what the order froze (SteadfastOrderRequestBuilder): reference as invoice, recipient name and phone from the customer snapshot, address from the shipping snapshot, and COD amount (order->total if the order is cash on delivery, otherwise zero). It refuses non-Store Orders, non-BDT currency, a missing recipient, a phone that is not Bangladeshi mobile format (01XXXXXXXXX), and a missing street address.

Reconciliation

  • If the attempt already holds a consignment id, finish the local records with no call.
  • Otherwise ask GET /status_by_invoice/{invoice}. Found: create the shipment with needs_review = true (that answer has no consignment id or tracking code). HTTP 404: the attempt becomes failed (not_found_at_provider) and booking may be tried again. Any other failure leaves it uncertain.
  • If the lookup is inconclusive, staff use "not booked" with a reason; if they are wrong, the parcel is booked twice.

Status application (ApplySteadfastStatus)

  1. Under a row lock on the shipment. A raw value equal to the one held changes nothing except refreshing the sync time and clearing the error.
  2. Unknown value or one that requires review sets the review flag. A delivered or cancelled target finds the shortest legal route through the courier map (path(), failure/return/cancel/delivery only ever as the destination) and walks it step by step through RecordManualCourierStatusUpdate in a nested transaction, so the walk is all-or-nothing. If there is no legal route (for example cancelled for a parcel already in transit) the shipment is left alone and flagged, never forced.
  3. Stores provider_status as received, writes a tracking event steadfast.{raw}, and on the first move to flagged dispatches SteadfastStatusNeedsReview after commit (listener AnnounceSteadfastReview tells staff once).

The webhook, the poll and "Check courier status now" are all this one path, so a status arriving by two routes produces one effect, one history row and one set of downstream actions.

Scheduled sync

SynchroniseSteadfastShipments does nothing while Steadfast is off. Otherwise it takes up to courier.steadfast.poll.batch (50) Steadfast shipments whose own status is not terminal and whose provider status is not final, ordered oldest check first (nulls first), and only those whose last check is older than interval (600 s) or, after a failed check, error_interval (1800 s). One parcel's failure does not stop the others, except authentication or not-configured errors, which would fail every parcel identically and stop the run. A parcel Steadfast says it never heard of is flagged (provider_sync_error = not_found).

Webhook handling

  1. SteadfastCourierDriver::verifyWebhookSignature() compares the full Authorization: Bearer <token> header to the stored token with hash_equals, before the body is read. No token configured, or none sent, fails closed: 401.
  2. Body over 16384 bytes: 413. Not JSON or not an object: 400.
  3. Validated fields: consignment_id (alphanumeric, underscore, hyphen, 1-64), invoice (string, max 64), status (string, max 64), updated_at (string, max 64), cod_amount (nullable, ignored). A failure returns the field names only.
  4. ReceiveSteadfastWebhook builds an event key sf: + SHA-256 of consignment, invoice, status and Steadfast's updated_at (Steadfast sends no event id), inserts the receipt and applies the status in one transaction. If processing fails the receipt rolls back, so Steadfast's retry is processed. A duplicate (unique index) and an unmatched invoice both return the same {"status":"success"}, so the endpoint cannot be used to probe which invoices exist.
  5. The shipment is found by the order whose reference equals the invoice and the latest Steadfast shipment on it. If the shipment already has an external_id that differs from the pushed consignment id, the push is treated as unmatched. A shipment recovered by invoice alone gets its external_id from the first push.

Money, ledger & audit effects

  • shipments.delivery_charge, cod_amount, return_charge and provider_charge are flat Taka (NUMERIC(19,2)). delivery_charge is the frozen Partner-facing decision; a staff-entered value is parsed with DecimalAmount::parse(), and a computed one freezes its breakdown in delivery_charge_rule_snapshot. The Steadfast balance is read from the raw JSON body so it never passes through a float.
  • Booking writes no ledger entry. Delivered, via the shared status action, runs the Order module's existing delivery pipeline (stock sold, supplier payable eligibility, Delivery Success Fee, proceeds "delivered" fact). Delivered is not cash collected: RecordCodCollection remains the only path that records collection, and the webhook's cod_amount is ignored.
  • Audit actions (module courier unless noted): courier.booking_requested, courier.booking_confirmed, courier.booking_failed, courier.booking_uncertain, courier.booking_reconciled_not_found, courier.booking_confirmed_not_booked, courier.steadfast_configured (sensitive; field names and host only), courier.steadfast_webhook_token_rotated (sensitive; the token is never in the row), courier.steadfast_connection_tested; and with module courier from the permission enum, shipment.created, shipment.status_advanced.

Rules, invariants & gotchas

One booking per order, never blind. A pending attempt is recorded under a row lock before the call; the partial unique index allows one live attempt per order. A timeout, dropped connection or unreadable answer is uncertain, and is reconciled by invoice before any retry.

Secrets never leave the server. Logs carry host, method, path and HTTP status only. Exceptions, audit rows and notices carry a fixed failure kind, never Steadfast's words, which could echo a key or customer data. Only a body hash is stored for webhooks.

Unverified against the live service (from requirements/06-steadfast-courier.md and code comments): that status_by_invoice returns HTTP 404 for an unknown invoice (anything else leaves a booking uncertain); the shape of a rejected key (401/403 read as authentication, 422 as validation); whether the merchant panel exposes webhook configuration for the account and which status values the webhook actually sends; any length or format limit on recipient_address or invoice (none are invented); and the package's own host discrepancy (README says portal.steadfast.com.bd, its config says portal.packzy.com; Banij uses the first and the second is not allow-listed).

Not implemented because the package has no such call: cancellation, return requests, pickup requests, partial-delivery quantities, a settlement signal, bulk booking, status by consignment id or tracking code, and a tracking-page link. SteadfastCourierDriver::cancelShipment() and requestPickup() throw UnsupportedCourierOperation: cancel in Steadfast's merchant panel and Banij learns of it from the reported status. fetchTrackingStatus() returns null; polling goes through the synchroniser.

  • Booking is Store Orders only. SteadfastOrderRequestBuilder refuses other sources, and requires the order to be already dispatched. Other orders use a manual shipment.
  • The driver does nothing on create. SteadfastCourierDriver::createShipment() is empty because booking happens before the shipment row exists. Do not move the network call into the shipment transaction.
  • Unknown or conflicting status is flagged, not guessed. Partial delivery moves nothing and touches no stock, COD or wallet.
  • Rolling back. Switch Steadfast off: booking and the scheduled poll stop, but the callback keeps applying statuses for parcels already booked. To refuse it too, generate a new token and do not give it to Steadfast. Shipments, attempts and receipts are kept; shipments are never deleted. Both additive migrations have working down() methods.
  • The provider-agnostic doc comments in CourierProviderCode, CourierManager and config/courier.php still say "only manual in this batch" and that Steadfast has no entry; the config now maps Steadfast. Trust the code.
  • ShipmentStatusChangeSource::Webhook comment says no provider sends webhooks yet; Steadfast now does.

How to...

Deploy Steadfast for the first time

  1. Run the migrations (the two 2026_11_17_* ones are additive). Make sure the scheduler runs.
  2. Grant courier.manage_integrations (Courier Manager has it). On admin.courier.steadfast.index, enter the API key and secret key, keep the default address, save, then Test connection (balance read only).
  3. Generate the token, and in Steadfast's merchant panel enter the callback URL shown and the token as the Bearer auth token. Whether the panel offers this is unconfirmed.
  4. Only then switch Steadfast on. Before the first real booking, do the read-only checks listed in section 5 of requirements/06-steadfast-courier.md, and get explicit approval.

Add a new courier provider

  1. Add a case to CourierProviderCode and a seeded row in courier_providers (new migration; precedent 2026_10_22_100000_create_courier_providers).
  2. Write a driver implementing App\Integrations\Courier\Contracts\CourierProvider (create, pickup, fetch status, cancel, verifyWebhookSignature, code); throw UnsupportedCourierOperation for what the API lacks. Register it in config/courier.php under drivers.
  3. Reuse CreateShipmentFromAllocations and route every status through RecordManualCourierStatusUpdate with source webhook or system. Never update shipment or order columns directly. Follow the Steadfast shape: attempt before call, call outside the transaction, uncertain on unknown outcome, receipts for idempotent pushes.
  4. Add its own credentials as encrypted settings, never .env; add tests with Http::fake.

Handle a new Steadfast status value

  1. Add the case to SteadfastStatus and set courierTarget(), isProviderFinal() and requiresReview(). finalValues() feeds the poller automatically.
  2. If it needs a new courier target, check the walk in ApplySteadfastStatus::path() still finds a legal route. Add cases to SteadfastStatusTest.

Unstick an uncertain booking

  1. On the order page use Reconcile. If the answer stays inconclusive, check Steadfast's merchant panel, then use "Mark not booked" with a reason. Do not book again before one of these.
