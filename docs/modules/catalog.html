Catalog module

The central product catalogue: products, variations, categories, brands, media, quantity price tiers, who may see each product, and the lifecycle that decides whether a partner can sell it. Feriwala staff author it; partners (business accounts) only read it through eligibility-scoped queries. This page is for developers touching app/Domain/Catalog.

Purpose

One central catalogue is shared by every wholesale buyer and every dropshipping/storefront partner. A product row is Feriwala's own record: its base cost, wholesale price, quantity tiers, lifecycle status, per-channel switches and eligibility rules live here, and stock lives in Inventory, never on the product (a copy would be a second answer to "how many are there").

  • Admin / catalogue staff create and edit products, variations, categories, brands, attributes, media, pricing, eligibility and publishing (spec §11, §12).
  • Business accounts (wholesale buyers and dropshipping partners) browse and buy from it, read-only, on the web (catalog.* routes) and on the mobile API (mobile.v1.catalog.*). They never see base_cost.
  • Partner storefronts read the catalogue through the frozen Storefront API; see Storefront API and Storefront app.

Implements §11 (catalogue, statuses, categories/brands), §12 (admin-only creation), §13 (partner browsing), §14 (order quantities, quantity pricing), §34.3 (SEO/schema fields); touches D4/D26 (flat Taka money) and D34 (what a partner has bought is what it may put on a website).

Rule (§12). Only platform staff create products, variations, categories, brands and attributes. A regular user is anybody who belongs to a business account: they are refused every write regardless of any permission or role (even Super Admin) they were given. This is enforced at the UI, controllers, form requests, actions, model policies, the Gate before hook and database triggers, with tests that assert rejection. Never add a catalogue write path that skips CatalogPolicy.

Key terms

BPC / SKU
The central product code. The column is products.sku; code and UI call it "BPC" interchangeably. Unique, stored upper-case (CHECK), nine upper-case letters and digits when auto-generated.
Central product
The single catalogue record a product has. A partner's website listing, a supplier offer and a stock item all point at it; none own it.
Variation / variant
A combination of attribute values (Size M + Colour Navy) with its own SKU, optional price overrides and logistics overrides. Code says ProductVariant; UI says variation.
Attribute / attribute value
Catalogue-wide shared vocabulary (Size, Colour; M, Navy). Variants are built from them.
Lifecycle status
The seven-state products.status (draft, pending_review, active, inactive, out_of_stock, discontinued, archived).
Sales channel
Dropshipping or wholesale (SalesChannel). Each has its own on/off column, its own package facility and its own browse screen. Called "Partner Selling" in some UI copy for dropshipping.
Eligibility
The rule set (active, category/brand on, account can transact, entitling package, package scope, account scope, channel) that decides if an account may see a product.
Price tier
A quantity band: from min_quantity units, this unit price. Belongs to a product or to one variant.
Wholesale pricing method
fixed (staff type the price) or percentage (price = base cost + markup %, calculated on the server).
Trash / force delete
Soft-delete of a product (reversible); permanent delete for an unused draft; Super Admin "force delete" for one with history.
Product content
A per-product update feed (title, body, at most one attachment) that admins publish; different from the Content Library, which releases one item to many products.

States & lifecycle

ProductStatus (implements TransitionableState) holds eleven cases on three independent axes, each in its own column. A state only moves to another state on its own axis; $product->transitionTo() is the only way to change one.

Channel axes toggle between their own two cases only. requiresReason() is true for discontinued and archived, so a written reason is mandatory for those moves.

Who may make which move (CatalogPolicy::canMoveProduct())

  • to active needs catalog.publish;
  • to archived needs catalog.archive;
  • away from active or out_of_stock needs catalog.unpublish;
  • everything else (submit for review, send back, discontinue an inactive product) needs catalog.edit.

Switching a channel on needs catalog.publish; off needs catalog.unpublish. Featuring a product needs catalog.publish.

Readiness to activate

TransitionProduct::assertReadyToActivate() refuses activation while the category (or its parent) is off, the brand is off, the wholesale price is not positive, or the product has variants and every one of them is inactive. published_at is stamped on the first activation and never changes (database trigger).

Stock-driven moves

After a product is activated, and after every stock change that touches sellable buckets, Inventory\Actions\RespondToStockChange runs SyncProductStockStatus: a tracked product with no sellable stock moves active to out_of_stock; it returns to active only if the system moved it there (a status someone set by hand stays). Those rows are written with no actor and an audit entry with actor_type = system. See Inventory.

Create and publish a product

  1. ProductController@store checks CatalogPolicy::canCreate() and validates through SaveProductRequest (which rejects any protected field via CentralProductFields).
  2. ManageProducts::create() authorises again, then in a transaction creates the product as draft with package_scope = all. Money is parsed with Money::fromDecimal() in the base currency. A blank SKU/barcode is generated.
  3. An audit row catalog.product_created is written. If the actor holds catalog.publish, both channels are switched on through SetSalesChannel (history and audit as for later toggles). The product is still a draft, so nothing reaches a partner.
  4. Staff add variants, media, tiers and eligibility, then call TransitionProduct (draft to active, or draft to pending_review for review).

Wholesale price resolution

  1. If the method is percentage, ResolveWholesalePricing ignores any wholesale_price in the request and computes base + base x pct / 100 with WholesalePriceCalculator (markup rounded half away from zero to the currency scale, bcmath, markup 0..1000 with at most two decimals). An update that omits a field keeps the stored one, so a percentage product recalculates whenever base cost changes.
  2. At purchase time WholesalePriceResolver::unitPrice($product, $variant, $qty) takes the variant's own tiers if it has any, else the product's tiers; picks the highest band whose min_quantity is reached; and never returns more than the base price (a tier above a later-cut base is ignored). Base = variant's effective wholesale price else the product's.
  3. SetPriceTiers enforces: at most MAX_TIERS = 10, min_quantity >= 2, no repeats, no band above max_order_quantity, and each unit price no higher than the band before (the first no higher than the base).

Trash and deletion ladder

  1. Trash (ManageProducts::trash, catalog.delete): allowed statuses depend on ProductDeletionRule; a reason is required; only the product row is soft-deleted, so it vanishes from every catalogue, cart, storefront and allocation lookup (they all read through Product::query()). Stock, offers, orders and history are untouched.
  2. Restore: clears deleted_by/deletion_reason.
  3. Permanent delete: only a trashed draft that nothing used (no movements, stock items, supplier listings/offers, sourcing, order lines, carts, website selections, source links, published updates). History rows become tombstones. Otherwise CatalogRefused::productHasBusinessHistory().
  4. Force delete (ForceDeleteProduct, CatalogPolicy::canForceDelete() = Super Admin role only, cannot be granted): reason of at least 10 characters plus typing the SKU or exact name; refused while an unfinished order, committed stock or active allocation exists. Unpublishes storefront selections, archives supplier listings, suspends offers, zeroes stock through AdjustStock, writes a sensitive audit entry, and releases the draft-only delete trigger for that product via the transaction setting feriwala.force_delete_product_id.

Business identities are refused first. CatalogPolicy::allows() returns false for anyone with an account membership (isBusinessIdentity()). The ordered Gate::before in AuthorizationServiceProvider does the same for every catalog.* ability and every model in CatalogPolicy::MODELS (and for inventory.*), before any permission or Super Admin check, so a partner handed a role by mistake still cannot author or read the catalogue admin. CatalogModelPolicy is registered for each catalogue model and only maps Laravel ability names to CatalogPolicy; the record never widens an answer.

Self-scoping for partners is the query, not the UI: every partner list goes through ProductEligibility::query($account, $channel); an account that cannot transact or has no entitling package gets whereRaw('1 = 0') (an empty catalogue, not an exception). ProductEligibility::refusals() (single product) and query() (SQL) state the same rules and are held to the same answers by tests. A product is visible when: status is active; category (and parent) available; brand, if any, on; account can transact; the account's package is entitling and, if package_scope = selected, listed; if account_scope = selected, the account is listed; and for a channel: the product's channel column is enabled and the package has that facility (PackageFeature::DropshippingEnabled / WholesaleEnabled). Reasons are string constants such as not_active, package_not_eligible, channel_disabled.

Money, ledger & audit effects

  • Money fields: base_cost, wholesale_price, the three selling-price bounds (partner guidance, §15.1), product_price_tiers.unit_price, variant wholesale_price/base_cost. All flat Taka decimal strings via Money; the percentage calculator uses bcmath and rounds half away from zero; the browser's wholesale-pricing-fields only previews through the server endpoint catalog.products.price-preview.
  • The catalogue itself writes no ledger entries; it is not a financial mutation. Orders snapshot prices at placement.
  • base_cost is never sent to a partner, storefront or mobile client (contract §5.1).
  • Audit actions (all module = catalog): catalog.product_created, .product_updated, .product_status_changed, .product_channel_changed, .product_eligibility_set, .price_tiers_set, .product_trashed, .product_restored, .product_permanently_deleted, .product_force_deleted, .product_featured, .product_unfeatured, .related_products_set, .product_category_assigned, .product_brand_assigned, .variant_created|updated|deleted, .media_added|updated|reordered|removed, .attribute_created|updated|deleted, .attribute_value_created|updated|deleted, .category_created|updated|enabled|disabled|deleted, .categories_reordered, .brand_created|updated|enabled|disabled|deleted|moved, .product_content_published|removed, .product_deletion_scope_changed (sensitive). Stock-driven status moves are audited as catalog.product_status_changed with module = inventory.

Rules, invariants & gotchas

Never assign status. Use TransitionProduct (lifecycle) or SetSalesChannel (channels). Both write product_status_history and an audit row; assigning the attribute skips the transition map, permission check and history.

  • Two statuses at once is normal. A product is Active and Dropshipping Enabled and Wholesale Disabled simultaneously. Only active products are ever offered, and a channel is also needed for that channel's screens.
  • Protected fields have exactly one owning endpoint (CentralProductFields): status, channel statuses, featured, scopes, currency_code, ids are rejected by the general edit; stock keys (anything matching /stock/i) are rejected everywhere; a list of products is only accepted by bulk actions. The rule is "missing", not "prohibited", so status: null is also refused.
  • Percentage pricing: a posted wholesale_price is ignored for percentage products. A variant that uses a percentage needs its own base cost.
  • Variant combinations are immutable. Add a new variant and switch the old one off. Variants can be deleted only while the product is a draft; their tiers go with them.
  • All variants of a product use the same attributes (a product offering Size and Colour cannot also have a Material-chosen variant), and one value per attribute.
  • Eligibility lists are retained when the scope no longer uses them, so toggling "all packages" and back loses nothing. package_scope is explicit rather than "no rows means everybody".
  • Trashed products still exist for stock. StockItem::product() uses withTrashed(); raw SQL reads (storefront inventory) must add deleted_at IS NULL themselves.
  • Hard delete is database-guarded. A non-draft product cannot be deleted by any code path (trigger); force delete releases the guard for one product inside one transaction.
  • A partner product the account may not see is a 404. Do not change it to 403.
  • Category depth 2 and the single-category-per-product design mean the "subcategory" of spec §11.1 is read from the tree, not stored on the product.
  • Brand and category is_active off removes their products from every partner without touching the products; switching back restores them.
  • Related products, SEO and logistics (ProductLogistics) are optional; a blank logistics figure clears the value instead of failing.

How to…

Add a field to a product

  1. Create a migration under database/migrations (money as NUMERIC(19,2), add CHECKs for bounds).
  2. Add the cast/@property in Product; add a snapshot key in ManageProducts::snapshot() if it should appear in the audit trail.
  3. Handle it in ManageProducts::fields() (parse money with Money::fromDecimal).
  4. Validate it in SaveProductRequest; if it is protected, add it to CentralProductFields and give it its own endpoint.
  5. Add form UI under resources/js/pages/admin/catalog/products/ and strings in lang/en/catalog.php and lang/bn/catalog.php.
  6. If storefronts need it, add it additively to the storefront payload (contract v1 is frozen; see requirements/05-storefront-api-contract.md).

Add a lifecycle status

  1. Add the case to ProductStatus with its axis, its transitionsTo() entry, tone and translation (catalog.products.status.*); say which axis it belongs to.
  2. Update the products_status_is_lifecycle CHECK in a new migration.
  3. Decide its permission in CatalogPolicy::canMoveProduct() and whether it requiresReason().
  4. Update isSellable() only if it should be offered to partners (today only active), and review SyncProductStockStatus.

Add a new eligibility rule

  1. Add a refusal constant and condition to ProductEligibility::refusals() and the matching SQL to query(). Both must give the same answer.
  2. Extend tests/Feature/Catalog/ProductEligibilityTest.php to hold the two forms equal.
  3. If an editor sets it, add it to SetProductEligibility (one locked write) and its audit snapshot.

Add a sales channel or change tier rules

  1. Tier rules live in SetPriceTiers (writes) and WholesalePriceResolver (reads); change both together and update WholesalePricingMethodTest/VariantTest-style coverage.
  2. A new channel needs a SalesChannel case, its enabled/disabled ProductStatus cases, a column and CHECK, a PackageFeature, and a browse route. This is architecture-sensitive; raise it for approval first.
