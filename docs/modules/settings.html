Settings module

Typed, admin-editable platform settings stored in one table behind a cached repository, plus the branding feature (logo, favicon and four colours) built on top of it.

Purpose

Much of the specification is "the admin can configure X": thresholds, toggles, deadlines. Those live in the settings table and are read through SettingsRepository. Anything with scope precedence, effective dates or history (commission, deposit, withdrawal and referral rules) does not belong here; it gets its own rule table resolved by App\Support\Rules\RuleResolver (the migration says so). Branding is the visual direction in CLAUDE.md: a neutral warm-grey surface, near-black actions, one admin-selectable accent from which every --brand-* token derives.

Key terms

Setting
A row with a unique dotted key (e.g. kyc.deadline_days), a group, a text value and a type.
Define
Introduce a setting (key, group, type, default, flags). Writing requires it to exist.
Public setting
is_public: a partner may read it (publicValues()).
Accent
The brand colour, stored as #rrggbb; null means the shipped #ca6330 (AccentColor::DEFAULT_HEX).

States & lifecycle

No status machine. A setting exists once defined; its value is set, overwritten or nulled.

Actions & workflows

SettingsRepository

MethodBehaviour
get($key, $default = null), has(), all()Reads. all() caches the entire table as one entry (rememberForever) under feriwala:settings:v2, then holds the typed result for the request.
set($key, $value, $updatedBy)The setting must already exist (firstOrFail); its type and encryption are schema, not something a caller invents. Flushes the cache.
define(...)Creates a setting with a default, or updates the definition of an existing one without touching its value. Flushes.
publicValues()Typed values of is_public rows (reads the database, not the cache).
flush()Clears the request copy and the cache entry.

The cache holds plain values with their type beside them, and types are applied after reading. Cache stores are configured to unserialize no classes (so a leaked app key cannot become a gadget chain), and a Money cached directly came back as an unusable half-object once. The whole entry is invalidated on every write, never one key: a missed partial invalidation leaves a stale fee in circulation.

ManageBranding

Methods: replace($actor, BrandingAsset, UploadedFile), restore(), setAccent(), setButton(), setNav(), setBackground(). All call BrandingPolicy::canManage (the system.manage_settings permission) and throw AuthorizationException otherwise.

  1. replace: store the file first (StoreManagedFile, public visibility, purpose branding/<asset>, MIME checked from the bytes, size capped), then define and set the setting; if saving fails the new file is deleted. The previous file is removed only after the new setting is saved.
  2. Colours are saved through define() then set(); a background darker than the dark text allows is refused (isReadableUnderDarkText); white background and the default accent are stored as null.
  3. Each change is audited with module: 'system': system.branding_replaced/_restored, system.branding_accent_changed/_restored, and the same pattern for button, nav and background.

Permissions & scoping

system.manage_settings guards the screen and every write (held by system_administrator and, via Gate::before, Super Admin). Settings are platform-wide and have no owner. A setting a partner may read must be marked is_public.

Money, ledger & audit effects

Money settings use the money type and surface as Money; nothing is multiplied or divided. Whether a given configuration action audits is up to that action: SettingsRepository::set() itself writes no audit entry, so configure-actions (for example ConfigureMobileVerificationRequirement) record their own.

Configuration

Branding setting keys: branding.accent_color, branding.button_color, branding.background_color, branding.nav_color (all #rrggbb strings), and branding.logo_path, branding.favicon_path (managed paths under branding/ on the public disk, or the active R2 equivalent through ManagedStorage). Shipped fallbacks: /logo.png, /favicon.svg. Logo: PNG/JPEG/WebP up to 2048 KB; favicon: PNG/WebP/ICO up to 512 KB; SVG is deliberately refused everywhere (scriptable, stored XSS).

Settings defined by other modules (not exhaustive): kyc.deadline_days, kyc.deadline_warning_days, account.mobile_verification_required, audit.log_retention_days, inventory.stock_blocks_orders, account.withdrawal_minimum/_maximum, supplier.withdrawal_minimum/_maximum, catalog.product_deletion_scope, sms.provider/sms.enabled, storage.r2.*. Several are defined by database/seeders/SafeSeeder.php or by their configure-Action.

Rules, invariants & gotchas

  • A colour never goes into a component directly. Every brand token derives from --brand-base; the shell writes --brand-* from the shared branding prop. accent is null while the shipped accent is in use, so the stylesheet's own value stands.
  • Branding fails safe. Every getter catches a throwing settings store and falls back to defaults; a malformed hex, a path outside branding/, or a missing file also falls back. A missing logo is an inconvenience; a page that fails to render is an outage. isManagedPath() accepts both branding/<asset>/<name>.<ext> and the older branding/<asset>-<name>.<ext> so an old upload keeps showing.
  • Accent text colour is computed from WCAG contrast (MINIMUM_TEXT_CONTRAST 4.5; light text #ffffff, dark #1d2630); the dark-mode accent is lifted (DARK_LIFT_PERCENT 25).
  • Button colour equal to the accent is still a choice (it keeps buttons put if the accent later changes), unlike the accent, where the default is stored as null.
  • set() on an undefined key throws; call define() first (the branding Actions define before every set).
  • Redefining never resets a configured value.

How to…

Add a setting

  1. Pick a dotted key and group; add a constant on the owning class (follow KycDeadlines or AuditRetention).
  2. Define it where it is first used: $settings->define($key, 'group', SettingType::X, $default, label: ...) in a seeder (SafeSeeder) or in the configure-Action, which also does set() and writes its own AuditEntry.
  3. Read it only through SettingsRepository::get() inside a small class that answers the question once; give a safe default.
  4. Use the right type: money for amounts, decimal for rates, never integer times 100.
  5. Add a test; SettingsCacheTest shows how the cache behaves.

Mark a setting readable by partners

  1. Pass isPublic: true to define(). Do not make credentials public; use isEncrypted: true for them.

Add another branding colour

  1. Add a constant and getters in Branding (fail safe), a setX in ManageBranding with an audit entry, a controller method and routes, and include it in Branding::toArray().
  2. Consume it in resources/css/app.css through a --brand-* token.

Testing

vendor/bin/pest tests/Feature/Settings (own schema, one suite at a time). BrandingTest covers uploads, colours and fallbacks; SettingsCacheTest the cache. In tests that read settings, remember the repository holds a per-request copy; call flush() after direct database edits.
