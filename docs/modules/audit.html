Audit module

The append-only record of who did what, why, and what changed. Every sensitive Action writes one entry through RecordAuditLog. Rows cannot be updated; the only deletion is the guarded purge, which the Super Admin alone may run and which always leaves a permanent record.

Purpose

Implements §36.2 (audit logging) and §42 (no secrets in logs), amended by D33 (the activity log can be cleared through one guarded path; recorded originally as D29 and still cited as "D29" in several code comments and route comments). Users: staff read it at Admin → Activity log; the Super Admin purges and sets retention; every module writes to it.

Rule. Audit logs are immutable: no update, ever, and no delete except PurgeAuditLogs (D33). Ledger entries have no exception at all. A correction is a new entry.

Key terms

Entry
AuditEntry: built where the action happens, because only there are the reason and the before/after state known.
Actor type
user by default, or system for scheduled jobs and gateway callbacks. A system action records no actor id: naming a person who did not act would be a lie an investigation could act on.
Sensitive flag
is_sensitive: marks decisions an investigation will want to find (suspensions, role changes, manual settlements, erasure). Filterable in the screen and counted on the dashboard.
Module
A short string (≤ 32 chars) such as account, access, kyc, system, audit; the screen's module filter accepts only [a-z_]{1,32}.
Purge
The guarded deletion of entries, recorded permanently as audit.logs_purged.

States & lifecycle

No statuses. A row is written once and lives until a purge removes it (never a row whose action is audit.logs_purged).

Actions & workflows

Flow: guarded purge (D33)

  1. Controller: activity-log.purge aborts 403 unless AuditLogAuthority::mayPurge; validates a current_password and the reason.
  2. PurgeAuditLogs::purge opens a transaction and runs SELECT set_config('feriwala.purge_audit_logs','on',true) (transaction-local). The database trigger permits DELETE only while that is on.
  3. Deletes matching rows, always excluding audit.logs_purged; sets the flag back to off.
  4. Writes the permanent audit.logs_purged entry: actor, reason, before = {deleted: N}, after = {scope, person, older_than}, sensitive. The trigger refuses to delete such a record under any circumstance.

UPDATE and TRUNCATE remain refused by the database (feriwala_audit_logs_immutable() with triggers audit_logs_no_update, and the delete trigger as amended by the purge migration).

How it is immutable (three layers)

  1. The model throws AuditLogIsImmutable on updating and deleting.
  2. The permission catalogue offers no audit.edit; audit.delete means the right to run the purge, not to delete a row.
  3. Database triggers refuse raw SQL.

Permissions & scoping

  • Catalogue: audit.view_audit_logs, audit.export, audit.delete, audit.manage_settings.
  • admin holds view_audit_logs only. system_administrator holds view_audit_logs and export. Super Admin holds all.
  • AuditLogAuthority: purge and retention need the Super Admin role and the corresponding permission, and the user must not be a business identity. A custom role given audit.delete is still refused. Controllers and Actions both ask it, so the rule cannot be met at the screen and missed in the Action.

Money, ledger & audit effects

Amounts never appear as floats in before/after; record decimal strings or Money::jsonSerialize() output like everywhere else. Audit is not a ledger and cannot stand in for one.

Rules, invariants & gotchas

  • Numbering: D33 is "D29" in code comments (ActivityLogController, routes). The decision text notes a pending cleanup.
  • Cost accepted by the owner: once cleared, wallet, withdrawal, payment and permission history cannot be recovered (D33).
  • The purge deletes audit.logs_purged neither by scope nor by retention; those records are permanent.
  • Never put secrets in before/after. Redaction is key-name based and defensive; a secret under an innocuous key name is written as is.
  • Audit from inside the Action, in the same transaction as the change, so a rolled-back change leaves no entry and a committed one cannot lack one. Send notifications after commit.
  • actor_id is a FK with nullOnDelete; an erased user's entries keep their rows with no actor. Account erasure does not touch the audit log.
  • Idempotent system callbacks should write once (see the "held back" check in ActivateAccountAutomatically) so the log is not flooded.
  • AuditEntry is a plain constructor with named arguments; roughly 225 files already use it.

How to…

Add an audit action

  1. Inside your Action's transaction, inject RecordAuditLog and call handle(new AuditEntry(action: 'module.thing_done', actorId: $actor->id, auditableType: Model::class, auditableId: $m->id, before: [...], after: [...], reason: $reason, accountId: $account->id, module: 'module', isSensitive: true)).
  2. Name the action <module>.<past_tense_event>; the module string is free text but keep it lowercase snake.
  3. Mark isSensitive for decisions about access, money, identity or trading ability. For a system actor use actorType: 'system' and no actor id.
  4. For a model change, AuditEntry::forModel($model, PermissionModule::X, PermissionAction::Y, $reason) builds before/after from the dirty attributes and sets the sensitive flag from the verb.
  5. Add a test that the row exists with the right action and fields.

Add request context

  1. In a controller path, $entry->withContext($request) returns a copy with actor, IP and user agent (truncated to 512).

Add a module filter value

  1. Nothing to register: the screen lists distinct non-null module values from the table.
