Access module

Who may do what on the platform. The module owns the closed permission catalogue, the 21 fixed platform roles, custom roles and permissions, platform-staff management, and the sensitive-action escalation rules. It is the vocabulary every policy in the codebase speaks.

Purpose

Feriwala's own staff (admins, KYC reviewers, finance, and so on) are governed by role-based access control built on spatie/laravel-permission (§32, D2). Permissions are named <module>.<action>, for example withdrawal.approve or kyc.view_kyc_documents. Roles are bundles of permissions held by a User who has no business account membership.

This module implements §32.1 (the roles), §32.2 (the verbs and the escalation for sensitive actions), §31.3 (one data-scope decision for pages, exports and APIs) and the Role and Permission management and Platform Staff management features. Business-side roles (owner, manager, staff) are a different scope and live in the Account module.

Users: Super Admin and holders of access.* manage roles and staff; every other module's policies read the catalogue.

Rule. The catalogue is closed. Nothing generates permissions at runtime. Adding a permission means adding a row to PermissionCatalogue::matrix() and re-running the seeder. A policy that asks for a name outside the catalogue fails loudly through PermissionCatalogue::name() instead of silently never matching.

Key terms

Permission
A string module.action. PermissionModule supplies the left part and PermissionAction the right. supplier.kyc is a module value that itself contains a dot, so supplier.kyc.view parses by longest-prefix match (moduleForOrNull()).
Module
A case of PermissionModule (account, kyc, kyc_batch, wallet, ledger, audit, return, damage, and so on).
Action (verb)
A case of PermissionAction. The list is closed so new modules inherit an understood vocabulary.
Platform role
One of the 21 PlatformRole cases, seeded as is_system = true, account_id = null.
Custom role / custom permission
A database-only role or permission created by an administrator (is_system = false). A custom permission is unbound: it protects nothing until code checks it.
Super Admin
The role that passes every check implicitly via Gate::before; it holds no permission rows itself in the enum, but PlatformRole::SuperAdmin->permissions() returns the whole catalogue.
Sensitive action
A verb for which PermissionAction::isSensitive() is true: holding the permission is necessary but not enough (password confirmation, reason, sometimes two-factor or a second approver).
Business identity
A User with an account membership (CatalogPolicy::isBusinessIdentity() is hasAccountMembership()). Refused several platform abilities whatever they hold.
Platform staff
A User with no membership. PlatformStaffDirectory lists them.

Roles are held against the user ($user->hasRole(), $user->syncRoles()). Public ids and slugs are not used: roles are addressed in URLs by their name or id as routed in roles/{role}, and permissions by name (permissions/{permission} is a name, never a database id).

States & lifecycle

No status enum. Two implicit lifecycles:

  • Custom role: created, updated (full permission sync), cloned, archived. Archived is permanent for that row.
  • Custom permission: created, description edited, archived. Name and system rows are not editable.

A staff member's ability to act is governed by their identity status (UserStatus, see Account), which the Platform Staff screen changes through ChangeIdentityAccess (staff.activate, staff.suspend, staff.deactivate).

How a permission is decided at runtime

One ordered hook, Gate::before in AuthorizationServiceProvider::boot(). config('permission.register_permission_check_method') is off so Spatie does not register its own check ahead of it. In order:

  1. The authenticatable must be a User. A Supplier session is on another guard and gets false outright.
  2. Catalogue and central stock abilities (CatalogPolicy::isCatalogueAbility, InventoryPolicy::isInventoryAbility) are refused to any business identity, even one handed the permission by mistake (§12, §19).
  3. Platform order administration (OrderPolicy::isOrderAdministrationAbility), return/exchange/damage administration (ReturnCasePolicy::isCaseAdministrationAbility) and website administration (WebsitePolicy::isWebsiteAdministrationAbility) are refused to a business identity the same way. A partner sees their own through the account-scoped policy.
  4. A permission the user holds (checkPermissionTo) returns true.
  5. A business identity otherwise gets null (fall through to the policy), never the Super Admin grant.
  6. A Super Admin gets true for everything else; anyone else gets null and the policy decides.

Returning null instead of false matters: false would short-circuit every other check and deny everyone.

Gotcha. A Super Admin actor never reaches a policy method, because Gate::before answers first. Rules that must bind a Super Admin (nobody locks themselves, the last Super Admin cannot be demoted, deleting oneself) are therefore enforced inside the Action, not the policy. The policy methods that refuse a Super Admin subject (UserPolicy::lock, assignRole, manageStaffAccess) work because the actor is a non-Super-Admin in that case.

Two-factor for sensitive roles

PlatformRole::requiresTwoFactor() is derived, not listed: a role needs it when any permission it actually holds has a sensitive verb. Super Admin always qualifies. A role gaining a sensitive verb gains the requirement in the same edit. User::requiresTwoFactorAuthentication() is true when the user holds any such role; RequireTwoFactorForSensitiveRoles (alias two-factor) is applied to the whole admin route group. On mobile the equivalents are mobile.two-factor, mobile.password and mobile.reason.

Permissions & scoping

  • The module's own catalogue entries: access.view, access.create, access.edit, access.delete, access.manage_settings. UserPolicy::assignRole and manageStaffAccess use access.edit; UserPolicy::lock (a business owner's login) uses account.edit. They are different jobs under different permissions, on purpose.
  • Held by default: system_administrator has access.* (view, create, edit, delete, export, manage_settings). Admin does not hold access.*.
  • Privilege ceilings: only a Super Admin grants or changes a Super Admin; nobody grants a custom role carrying a permission they lack; only a Super Admin deletes platform staff (DeletionAuthority); the platform always keeps at least one active Super Admin (AssignPlatformRole, EraseAccount).
  • Platform staff are users with no membership. AssignPlatformRole refuses anyone who has one, and PlatformStaffDirectory filters on whereDoesntHave('accountMembership'). Mixing the two scopes is how a partner's bookkeeper ends up approving withdrawals for everyone.
  • Data scope (§31.3): use DataScopeResolver for pages, exports, reports and APIs alike so the four routes to the same data stay closed together. Platform-wide visibility needs an explicit view permission; everything else is Own.

Rules, invariants & gotchas

  • Seeding is idempotent and never deletes a permission. A permission that disappeared would silently detach from every role. Roles use syncPermissions, so a grant removed from PlatformRole::grants() is revoked on the next seed. After changing the matrix or grants: run the seeder in every environment, and the seeder flushes Spatie's cache (stale cache hands people yesterday's access).
  • Custom permissions are inert. Creating one protects nothing; it still needs a policy or Gate check and a deploy. The catalogue screen labels it "unbound".
  • Verbs outside a module's row do not exist. PermissionCatalogue::name(Module::Audit, Action::Edit) throws. This is intended (it catches typos in policies); there is deliberately no audit.edit and no ledger.create/edit/delete.
  • audit.delete is not "delete a row". It is the right to run the guarded purge, and even then only a Super Admin may (AuditLogAuthority). The Admin role no longer holds it (D33 restriction, 2026-10-14).
  • The catalogue docblock figures are stale. PermissionCatalogue says "28 modules × 20 verbs = 560"; the enums now hold more modules and 36 verbs, and the role docblocks say "twenty" while there are 21 roles. Count from the enums, not the comments.
  • Roles are 21, not 20, because supplier_manager was added by D25.
  • Platform staff invitation reuses the ordinary password-reset broker and token table; there is no bespoke invitation token. A previous unused token is left to expire.

How to…

Add a permission for a new module

  1. Add a case to PermissionModule (app/Domain/Access/Enums/PermissionModule.php) and its label().
  2. Add a row to PermissionCatalogue::matrix() listing the verbs the module accepts. Add a new PermissionAction case (and its label()) only if no existing verb fits.
  3. If the new verb is sensitive, add it to PermissionAction::isSensitive(); roles holding it become two-factor roles automatically. Add it to SensitiveActionRequest::requiresTwoFactor() if it needs two-factor on the request.
  4. Grant it to roles in PlatformRole::grants().
  5. Check it in a policy via PermissionCatalogue::name(PermissionModule::X, PermissionAction::Y) and register the policy in AuthorizationServiceProvider.
  6. Run php artisan db:seed --class=RolesAndPermissionsSeeder (idempotent). Add tests under tests/Feature/Access or the module.

Add or change a platform role's grants

  1. Edit PlatformRole::grants() for the role. Use the local $read, $manage and $review bundles consistently.
  2. Re-seed. Check whether requiresTwoFactor() changed for that role.

Add a brand new fixed role

  1. Add the case, label() and a grants() arm to PlatformRole. The seeder creates it from PlatformRole::cases().
  2. Add translation keys if the UI lists it. Custom roles cannot reuse the new name (ManageCustomRole::guardName checks PlatformRole::tryFrom).

Gate an action behind password, reason and two-factor

  1. On the route: add RequirePassword::class and list the route name under required_for in config/reasons.php.
  2. In the Action, for money or credentials: build a SensitiveActionRequest and call SensitiveActionGuard::authorize(); follow SettlePaymentManually.

Testing

Run vendor/bin/pest tests/Feature/Access in its own schema, one suite at a time (Testing). PlatformGrantIsolationTest proves a business identity cannot use a platform grant. Tests that need permissions seed Database\Seeders\RolesAndPermissionsSeeder in beforeEach. There is also a permissions Pest group (tests/Feature/Permissions) for cross-module permission tests.
