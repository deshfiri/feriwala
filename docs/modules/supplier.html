Supplier module

Suppliers are businesses that supply goods to Feriwala. They are a wholly separate account domain from partners: their own model, login guard, KYC, portal, wallet and mobile API. A supplier proposes products, an administrator approves them as priced offers, orders are allocated to offers, and Feriwala pays the supplier through a payable, a wallet and withdrawals. This is the second-largest module (app/Domain/Supplier).

Purpose

Feriwala is merchant of record. Only Feriwala's central catalogue is ever sold to partners (§12); a supplier never writes to products. A supplier instead submits a listing request (a proposal), staff approve it and connect or create the central product, and the approval creates a supplier offer carrying two rates: the confidential Supplier Rate (what Feriwala pays the supplier) and the Platform Rate (what Feriwala charges). Orders for supplier-sourced products reserve the offer's stock, create a payable (a claim, not money), and when the order is delivered and paid the payable becomes eligible and staff settle it into the supplier's wallet. The supplier then requests a withdrawal.

Users: suppliers (portal at /supplier and the mobile API at /api/mobile/v1/supplier), staff (admin screens, permission-gated), and the system (order, delivery and return hooks, one scheduled sweep).

Authority: D25 — Separate Supplier Account domain (in requirements/04-decisions.md; it supersedes the single-account statements of §5 and §45 as applied to suppliers only), D26 (flat Taka), D30 (KYC batches, shared with partners), D12 (dropshipping money flow). The code comments also cite internal task labels (P13-1 … P13-28) and batch names (“Supplier Bulk Product Listing”, “Advanced Order Management”, “beta-critical batch”).

Rule (D25). A Supplier is not a role, permission or flag reachable from a User or BusinessAccount, and no conversion exists between the two. Never add a supplier check to the web guard, and never reuse Fortify controllers for suppliers. A supplier session must never gain access to partner or staff resources; this is enforced at the route/middleware boundary and by tests.

Rule (D25, Supplier Rate confidentiality). SupplierOffer.supplier_rate is visible only to that supplier and to staff holding supplier_pricing.view. It must never reach a partner Inertia prop, a storefront API response, an export, a log or a notification. Partners only ever see the Platform Rate.

Key terms

Supplier
App\Domain\Supplier\Models\Supplier, an Authenticatable on the supplier guard (provider suppliers). Reference prefix from ReferencePrefix::Supplier.
Operational
Only SupplierStatus::Approved (isOperational()). Every operational route and action asks this question server-side.
Listing (listing request)
A supplier's proposal for one product, with one or more items (variations). Never publishes anything.
Lot
A draft-then-submit-once batch of several listings (“product entries”). Its status is always rolled up from its listings.
Offer
SupplierOffer: a supplier's approved supply of one product (or variation), with Supplier Rate, Platform Rate, supply mode and stock.
Supplier Rate / Supplier Base Price
What is payable to the supplier per unit. supplier_offers.supplier_rate. Confidential.
Platform Rate
What Feriwala charges. Must not be below the base price (assignment refuses it). Written into the product or variant's wholesale_price when an offer is made preferred.
Preferred offer
The one offer per (product, variation) that orders use. Chosen by an administrator, never automatic and never “cheapest”.
Supply mode (SupplyMode)
ready_stock, on_demand, pre_order. Non-ready-stock modes need staff confirmation at allocation and a fulfilment commitment.
Supplier-sourced
A variation with any supplier offer (any status). From then on its stock is only from suppliers, never partly central.
Payable
What Feriwala owes a supplier for one allocated order line. A claim; it credits no wallet until settled.
Settlement
Crediting a payable's net amount into the supplier wallet (SettleSupplierPayable).
Recovery
The controlled debt on a supplier wallet when a reversal arrives after settlement and not enough is available; never a negative balance.
Platform credit
The part of a wallet's total spendable in the platform but never withdrawable. Converted to withdrawable only through ConvertSupplierWalletBalance.
Delivery success fee
A percentage of a payable's gross amount debited from the supplier's wallet when its order is delivered.
Fulfilment commitment
The capacity reservation for one allocated non-ready-stock line.

Data model

Money columns are cast with MoneyCast (exact decimal Taka plus currency_code). The original migrations name money columns *_minor; 2026_10_05_100000_convert_monetary_storage_to_flat_taka.php converted storage to flat Taka, and the models and constraints today speak flat Taka. Models marked “public id” use HasPublicId (ULID); “ref” use HasReference (human reference); “SM” use HasStateMachine; “hist” use RecordsStatusHistory.

Registration creates the supplier at draft and moves it to verification_pending in the same step. AdvanceSupplierPastVerification moves it to kyc_pending when email (always) and mobile (only while the admin's mobile-verification requirement is on) are verified; it is called from every place a verification can complete, and is a no-op for anyone not at verification_pending. draft → submitted → under_review → (approved | rejected | correction_required); correction_required → submitted. Editable while draft or correction_required (isEditable()). SubmitSupplierKyc performs submitted and under_review in one step (no separate “start review” click in this beta).

No listing status means “live on the catalogue”. Pending at order placement; eligible only when both delivery and payment settlement are recorded (EvaluateSupplierPayableEligibility; the second fact to arrive makes the move); settled by staff. Note SettleSupplierPayable settles only Eligible payables even though the state machine would also allow PartiallyReversed → Settled: a deliberately smaller scope (docblock).

SupplierWithdrawalStatus

requested → (under_review | rejected); under_review → (approved | rejected); approved → processing; processing → (paid | failed); rejected, failed, paid, reversed terminal (no code path reaches reversed; it exists for a later payout-channel reversal). holdsReservation() is true for requested, under_review, approved, processing.

FulfilmentCommitmentStatus

awaiting_confirmation → (confirmed | cancelled); confirmed → (preparing | failed | cancelled); preparing → (ready | failed | cancelled); ready, failed, cancelled terminal. Reaching any terminal status frees the capacity the commitment held (capacity counts only non-terminal rows). A supplier “declining” is cancel() recorded with the supplier source; there is no Declined status.

  • StockUpdateStatus: pending, approved, rejected.
  • SupplierLedgerEntryType: settlement_credit, payable_reversal_debit, withdrawal_reserved, withdrawal_reservation_released, withdrawal_paid_debit, manual_adjustment, delivery_success_fee_debit, balance_conversion_debit, balance_conversion_credit. direction() is null for reserve, release and manual adjustment. requiresReason() is true for reversal, release, manual adjustment and both conversions.
  • Change-source enums for histories: SupplierStatusChangeSource, PayableChangeSource (system, staff, scheduler, payment_gateway), SupplierWithdrawalChangeSource (supplier, staff, system, scheduler, payment_gateway).

Flow: order to payable to wallet

  1. Allocation (placement). AllocateSupplierOrderLine asks ResolvePreferredOffer which offer serves the line. A variation with no offer at all returns null and takes the unchanged central-stock path. A supplier-sourced variation must be served whole by its preferred offer: no fallback to another supplier, no split, no central top-up; otherwise SupplierAllocationRefused in words that name no supplier. On success it reserves via reserveFromSupplier() and returns a SupplierAllocation (the offer plus the exact price version in force). Audit supplier_offer.allocated.
  2. Accrual. AccrueSupplierPayable (same transaction as the order line) creates a pending payable: gross = snapshotted Supplier Rate × allocated quantity, key supplier-payable:<order item public id> (or supplier-payable:allocation:<allocation public id> for staff allocation). Idempotent; unique-violation races return the existing row. Audit supplier_payable.created.
  3. Fulfilment commitment (non-ready-stock only). RecordSupplierFulfilmentCommitment::forAllocation() locks the offer, sums non-terminal commitments, and throws FulfilmentCapacityExhausted if a bounded fulfilment_capacity would be exceeded (null capacity never refuses). due_at = the offer's expected availability, else now + lead time days, else null. confirmation_due_at = now + supplier.fulfilment_confirmation_deadline_hours (default 48). The supplier confirms, prepares, marks ready, fails or declines through AdvanceSupplierFulfilmentCommitment (source supplier, actor null, since a supplier has no users row).
  4. Unconfirmed commitments. The hourly ExpireOverdueFulfilmentCommitments sweep, per commitment under a lock: cancels it (freeing capacity), cancels its pending payable, marks the allocation Released, and returns the line to SourceAllocationPending for staff to choose again. All moves are system-sourced.
  5. Payment and delivery. Payment settlement calls QualifySupplierPayablePayment; delivery calls markDelivered. EvaluateSupplierPayableEligibility records each fact under a row lock, idempotently, and moves pending → eligible only when both exist. Audit supplier_payable.eligible. RecordSupplierPayableDelivery (needs order.edit) is the original manual stand-in for the delivery event, still present.
  6. Delivery success fee. On delivered, ApplyDeliverySuccessFee computes gross_amount × the configured percent (HalfAwayFromZero, via Money::percentage) and debits it with SupplierWalletService::debitFee(), independent of whether the payable has settled. A 0% rate (or a fee that rounds to zero) writes nothing. The rate is frozen on the delivery_success_fees row.
  7. Settlement. Staff run SettleSupplierPayable (single) or BulkSettleSupplierPayables (each payable in its own transaction so one failure does not roll back the rest). It locks the payable, returns it unchanged if settled_at is set, refuses non-eligible or not-earned payables, opens the wallet (OpenSupplierWallet, race-safe get-or-create), credits netAmount() with key supplier-payable-settlement:<public id> and source payable_settlement, sets settled_at/settlement_reference, transitions to settled, audits supplier_payable.settled and notifies the supplier.
  8. Returns. ReverseSupplierPayable never edits the payable: it appends a supplier_payable_reversals row (quantity × the payable's rate), moves the payable to partially_reversed or reversed, and if it had already been settled claws the amount back (debitForReversal: debit what is available, raise the rest as recovery). A line with no supplier payable is left alone. Audit supplier_payable.reversed.

Flow: wallet and withdrawal

  1. A supplier requests a withdrawal in the portal or mobile app with an idempotency key. RequestSupplierWithdrawal requires an operational supplier, a usable payout method owned by that supplier (PayoutOwnerType::Supplier, active), and an amount within SupplierWithdrawalLimits (supplier.withdrawal_minimum default 500.00, supplier.withdrawal_maximum default none; floor 1.00, ceiling 1000000000.00; per-supplier overrides win). The key is durable (a unique index on the row), not the 24-hour cache-based IdempotencyService.
  2. In one transaction: the payout destination is snapshotted into payout_snapshot; the wallet is locked and the amount reserved (reserve() writes a withdrawal_reserved ledger entry, drawing from withdrawable money only); the first history row is written; audit supplier_withdrawal.requested (module withdrawal); the supplier is notified; the staff queue is announced.
  3. Staff move it with AdvanceSupplierWithdrawalStatus (requested → under review → approved → processing); no money moves in these steps.
  4. RejectOrFailSupplierWithdrawal (reject from requested/under review, or mark a processing one failed) releases the reservation exactly once (release() entry withdrawal_reservation_released, reason required).
  5. PaySupplierWithdrawal pays a processing withdrawal: requires the external reference the payout channel returned, and consumes the reservation once (pay(): total and reserved fall together; entry withdrawal_paid_debit). Audit supplier_withdrawal.paid.

Other wallet operations: AdjustSupplierWallet (manual credit or debit; checked with WalletPolicy::canAdjust; a credit must state its balance type; idempotent on the caller's key; audit supplier_wallet.manual_adjustment, sensitive) and ConvertSupplierWalletBalance (WalletPolicy::canConvertBalance, reason, two entries balance_conversion_debit/_credit sharing a conversion_reference, no reverse; audit supplier_wallet.balance_converted). SetSupplierWithdrawalLimits (setDefault, setOverride) audits supplier.withdrawal_limits_default_set and supplier.withdrawal_limit_override_set.

Suppliers are never evaluated by a policy or Gate (a supplier is not a User). Money, ledger & audit effects

  • Money type. Supplier rates, platform rates, gross amounts, fees and wallet columns are Money (exact decimal Taka strings). Withdrawal limits are decimal strings parsed at the boundary. Platform rate vs base price comparison and the fee percentage use Money methods, never floats.
  • The ledger is supplier_ledger_entries. Every balance change goes through SupplierWalletService, which writes the immutable entry in the same transaction under lockForUpdate, idempotent by key. Never write a wallet column elsewhere. Methods: credit, debitForReversal, debitFee, reserve, release, pay, adjust, convertToWithdrawable.
  • Two kinds of money. Every entry carries a balance_type. A supplier's earnings (settlement) are withdrawable. A debit inside the platform (fee or reversal) spends platform credit first and, when it takes both kinds, writes one entry for each under keys carrying the command key as a prefix. A withdrawal's reservation is withdrawable money only.
  • Formulas (.ai/rules/wallet.md): Withdrawable Available = max(0, (total - platform_credit) - reserved_w - recovery); Available to Spend = max(0, total - reserved - recovery); recovery stands against withdrawable money. SupplierWallet::availableBalance() is total - reserved - recovery floored at zero. Never compute withdrawable as total - platform_credit: that is a holding.
  • Idempotency keys. supplier-payable:…, supplier-payable-settlement:<payable public id>, supplier-withdrawal-reserve:<withdrawal public id>, delivery-success-fee:<payable public id>, supplier-wallet-adjustment:<wallet public id>:<caller key>, supplier-reservation:<reference> (stock), plus the unique keys on payables, reversals, withdrawals and movements.
  • Immutability. Ledger entries, status histories, stock movements, price changes, reversals and delivery success fees are append-only (model guards and database triggers). Corrections are new rows (corrects_ledger_entry_id).
  • Audit actions (AuditEntry; module is a PermissionModule value): supplier.approved, supplier.rejected, supplier.suspended, supplier.reactivated, supplier.created_by_staff, supplier.withdrawal_limits_default_set, supplier.withdrawal_limit_override_set; supplier_kyc.submitted, .resubmitted, .correction_requested; supplier_listing.submitted, .resubmitted, .correction_requested, supplier_listing.<decided status>; supplier_listing_lot.submitted, .resubmitted, supplier_listing_lot.<status>; supplier_offer.allocated, .assigned, .rates_changed, .preferred_selected, .activated, .suspended; supplier_stock.adjusted, .approved, .rejected, .reserved, .committed, .released; supplier_payable.created, .eligible, .settled, .cancelled, .on_hold, .reversed; supplier_fulfilment_commitment.created; supplier_withdrawal.requested, supplier_withdrawal.<status>, .paid; supplier_wallet.manual_adjustment, .balance_converted. Supplier-initiated entries use actorType: 'supplier' with the business name as label and no actor id.

Rules, invariants & gotchas

  • Two separate identities. The supplier and web guards share the one Redis-backed session but namespace their logins separately. A browser can hold both logins; what is guaranteed is authorisation (D25 explicitly rejected a separate cookie for this batch). Never gate a supplier route with auth or a partner route with auth:supplier.
  • Suppliers are never deleted. suppliers_no_delete, listings, items, withdrawals and payout methods all have never-delete triggers. A supplier asks for erasure; staff with supplier.delete decide (deletions.* routes).
  • Supplier KYC is its own small engine (D25), but rounds can be placed on a shared KYC batch version (D30); evidence reviews, KycCompletion and KycApprovalReadiness are shared, with SupplierKycRound adapting. Approving a batch round is refused until groups are met and evidence is reviewed (KycReviewRefused::notReadyToApprove).
  • Immutability windows. Listing media, listing columns and items freeze when the listing leaves draft/correction_required (database triggers as well as isEditableBySupplier()). A rejected, approved or archived entry can no longer be edited away.
  • Lot submission is all-or-nothing; lot review is per-entry. This asymmetry is intentional.
  • Supplier-sourced is sticky. The moment a variation has any offer (even suspended), central stock is no longer used for it, and SupplierSourcedAvailability returns zero when the preferred offer is suspended, its supplier is not operational, or none is preferred. Suspending the only offer therefore makes the product unavailable rather than falling back to central stock.
  • Preferred offer is manual. There is no cheapest-supplier algorithm anywhere. Making one preferred writes the Platform Rate into wholesale_price; the supplier's rate and identity never reach the catalogue.
  • Price versions are what orders snapshot. Changing a rate afterwards does not restate any allocation or payable. A payable's amount is always the snapshotted rate × quantity.
  • Payable ≠ money. A payable credits no wallet. Reversing a settled payable can leave recovery on the wallet, which is never paid down explicitly; it is netted out of every later availability calculation.
  • Delivery success fee is charged at delivery regardless of settlement and is not reversed here when an order later returns (the decisions file notes a later return does not reverse a delivery-success fee on the supplier side; confirm in D35 before changing).
  • Withdrawal reservations are exactly-once. Release and pay both lock the wallet first and rely on the withdrawal's own state machine to refuse a repeat. Never add a path that changes reserved outside SupplierWalletService.
  • Settle needs a re-entered password (RequirePassword) in the admin, as do mark-paid, wallet adjustment and conversion.
  • The web supplier login has no throttle. AuthenticatedSupplierSessionController@store calls Auth::guard('supplier')->attempt() directly and its route has no throttle middleware, unlike the mobile login which uses LoginRateLimiter. See the report.
  • Mobile controllers without routes (see the callout above).
  • Pest helper prefix. Supplier test helpers are prefixed supplier*; keep new ones prefixed (global function namespace).

How to…

Add a field to a supplier's listing item

  1. Add a migration for supplier_product_listing_items (and a check constraint if it has a rule). If the column must be frozen after submission, extend the supplier_product_listing_items_locked_columns trigger.
  2. Add it to SupplierProductListingItem (docblock, cast).
  3. Accept it in SaveSupplierListingDraft and the validators of Supplier\ListingController / ListingLotItemController and their mobile twins; show it in ValidateSupplierListingLotForSubmission if it affects submittability.
  4. Show it on the supplier pages (pages/supplier/listings/form.tsx, listing-lots/entry-dialog.tsx) and the admin review page; copy it to the offer in DecideSupplierListing::approveItem() if it should live on the offer.
  5. Add strings to lang/{en,bn}/supplier.php. Never expose supplier_rate to a partner prop.

Add a new supply mode

  1. Add the case to SupplyMode with label(), buyerFacingLabel(), and decide requiresStaffConfirmationAtAllocation().
  2. Update the check constraints on supplier_product_listing_items, supplier_offers (supply_mode_known and the mode-specific requirements).
  3. Review DecideSupplierListing (stock opened only for ReadyStock), RecordSupplierFulfilmentCommitment and SupplierSourcedAvailability.

Add a new ledger entry type to the supplier wallet

  1. Add the case to SupplierLedgerEntryType and fill direction(), creditBalanceType(), requiresReason(), requiresActor(), label().
  2. Add a method (or extend one) in SupplierWalletService; never write wallet columns from an action.
  3. Widen any database check on the type or source column in a new migration, and add an idempotency key.
  4. Wrap the caller in a transaction with the locked source row, and write an audit entry.

Add a status transition

  1. Edit the enum's transitionsTo() (and its status_known check in the migration for new cases); move through transitionTo() or transitionWithHistory().
  2. Update the matching *_status_history source/consistency checks if you add a change source.

Add a new supplier notification

  1. Create the class under app/Notifications/Supplier/ (extend SupplierLifecycleNotification where it fits) and send it with $supplier->notify((new X)->locale($supplier->locale)) from the action, after the transaction commits where possible. Do not include rates.

Expose a new supplier screen on mobile

  1. Add the controller under Api/Mobile/V1/Supplier/<Area>, a route file routes/mobile/supplier/<area>.php (auto-loaded by the glob) inside Route::middleware('mobile.operational') if it is operational-only, and scope queries through the authenticated supplier.
  2. Add a test with mobile.v1.supplier.<area>.<action> route names and update the API docs.
