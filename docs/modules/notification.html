Notification module

How Feriwala tells people things: the header bell (database notifications, pushed live), staff work-queue alerts, case and courier announcements, and SMS as a Laravel notification channel with a queued, deduplicated delivery log. Read it before adding any notification or text message.

Purpose

The platform uses Laravel's own notification system rather than a parallel one (§30: SMS is a delivery channel for notifications the platform already sends). This module supplies what Laravel does not: the sms channel, the SMS log (sms_messages), the global/provider/per-event SMS switches (§30, §30.2), the bell presentation (§33.2, D20), live updates over Reverb, and the helper actions that find the right recipients and write idempotent notifications.

Audiences: any signed-in person (their own bell), platform staff (queue alerts, SMS settings), Partners (outcomes of their cases and parcels), Suppliers (a separate notifiable with its own channel and routes), and customers (SMS only, e.g. a COD confirmation code).

Key terms

Event
A dotted name such as account.activated. Stored in a database notification's event key, and used as the SMS event for switches and dedupe. The two vocabularies overlap but are separate: bell events are lang keys under notification.events; SMS events are the SmsEvent enum.
Bell
The header notification centre: the latest 10 database notifications for the signed-in user (RecentNotifications::LIMIT).
Staff queue
A StaffQueue case: a kind of work arriving from outside the team that waits for staff (KYC, supplier listings, withdrawals, returns, exchanges, damages, refunds, website requests, deletion requests).
Dedupe key
SHA-256 of an SMS's key plus recipient; unique, so a retried notification adds no second text.
Suppressed
An SMS the platform deliberately did not send because a setting said so. Not a failure.
One-time-code event
mobile_verification, supplier_mobile_verification, cod_confirmation. Switching them off blocks the flow that waits for the code.

States & lifecycle

suppressedNot sentDeliberately not sent (global switch, event switch, or no usable provider).
 
queued --> sent         (provider accepted)
queued --> suppressed   (SMS off globally or for this event, or no provider can send)
queued --> failed       (refused, last attempt, or the queue gave up)
queued --> queued       (retryable result: released with backoff)

DeliverSmsMessage acts only on a row still queued; anything else returns without sending, which is what prevents a double send. tries = 3, backoff = [60, 300] seconds. A thrown exception records the error and rethrows (the queue retries, and recordExhaustion() marks failed on the last attempt, which also covers the sync connection where failed() is never called); a provider result that is not accepted and not retryable is final. failed() writes the failure onto the record when the queue gives up.

Flow: an SMS from a notification

  1. A notification class lists 'sms' in via() and implements toSms($notifiable): SmsMessage with event set to a SmsEvent value and the locale from the recipient (Locale::parse($notifiable->locale)). The three that do today: PaymentReceived, WalletBalanceLow, AccountActivated. It may define smsDedupeKey() when the event alone is not unique (e.g. payment.received:{reference}).
  2. The notification is queued (they implement ShouldQueue), the channel runs, a queued row is inserted, DeliverSmsMessage is dispatched on the queue named by config('sms.queue') (default sms).
  3. The job re-reads the switches. Off: suppressed. Otherwise it resolves the active SmsProvider (bound to SmsProviderManager::driver(), not a singleton, so an admin switching provider takes effect without restarting workers), increments attempts, sends, and records sent (with provider reference and cost) or the failure.

Some SMS are not notifications: one-time codes (mobile verification, COD confirmation) are sent directly by their own senders and are governed by the same event switches; a switched-off code event raises SmsEventSwitchedOff so the screen can say no code is coming.

Flow: a case or courier event reaches the bell

  1. The model's moveTo() (or the courier action) calls the announcer. It captures plain values, then registers a closure with DB::afterCommit, so a rolled-back step announces nothing. A failure inside is reported and swallowed.
  2. For each recipient it builds the notification, sets id to Uuid::uuid5(NAMESPACE_URL, "feriwala:{event}:{subject}:{recipient public_id}") and calls Notification::send(). The notification's shouldSend() (on CourierPartnerUpdate) skips a database row whose id already exists, so a repeat writes one entry.
  3. The framework's NotificationSent event for the database channel reaches BroadcastStoredNotification, which fires NotificationsChanged (ShouldBroadcastNow) on the private channel notifications.user.{public_id} (or notifications.supplier.{public_id}). It carries only reason and unread, never text; the browser refetches what it is allowed to see.
  4. When the person opens the bell, RecentNotifications turns each row into a title, description and link. Case links are computed at read time in caseHref (permission and ownership checked) and never stored.

Permissions & scoping

  • The bell is self-scoped by construction. Every read and mark-read starts from $user->notifications(); there is no account or user parameter to tamper with (§31.3). A notification id belonging to someone else resolves to nothing.
  • SMS settings: SmsSettingsPolicy::canView = sms.view, canManage = sms.manage_settings (held by the SMS Manager). Turning messaging off or switching provider decides whether customers hear about their own payments, so it is its own permission. The sms permission module has CRUD plus export, manage_settings and manage_integrations. ToggleSmsEvent checks the policy itself.
  • Staff queue recipients are the holders of the queue's view permission (delete for the two deletion queues), plus Super Admins, platform access only. A business account's own staff and Suppliers are never told what is waiting in the platform's queues.
  • Partner case and courier notices go to the account owner only.
  • Content rule: a notification carries an outcome, kind, reference and public id; never a customer's name, number or address, an evidence name or path, a staff note, or an error body.

Money, ledger & audit effects

No ledger effect. PaymentReceived and WalletBalanceLow format a Money into the text ($amount->format()) and store toDecimal() plus the currency in the bell data; nothing is computed from a float.

Audit actions (module sms): sms.settings_changed (sensitive; before/after of enabled and provider), sms.event_enabled / sms.event_disabled (sensitive), sms.test_sent (provider, masked recipient, accepted, error code; never the message). The credentials action also audits; read ConfigureSmsCredentials for the exact name (not read for this page).

Rules, invariants & gotchas

Event names contain dots: index the lang array, do not path into it. __('notification.events.account.activated.title') does NOT work: the translator splits on dots, looks for a nested account array and silently returns the key. Fetch __('notification.events') and index it with the raw event string (RecentNotifications::line(), SmsEvent::describe()). A missing line falls back to the raw event name on purpose: a visible wallet.topped_up in the bell is a bug someone fixes; a dropped row is one nobody notices (.ai/rules/notification.md).

Case notifications come from the models' moveTo(), after commit. Return, exchange and damage notifications are sent by AnnounceCaseEvent, called from OrderReturn::moveTo, OrderDamage::moveTo, a few actions and Order::moveTo (exchange shipped). Never add a second sender in an action. Ids are uuid5 of event + case + recipient so repeats write one row; sending is wrapped in DB::afterCommit. Bell links for case events are computed at read time in RecentNotifications::caseHref, never stored.

  • A failure to notify never undoes the change it announces. Announcers catch, report() and continue; the SMS channel returns quietly for a missing number.
  • Send after commit, never inside the transaction. Otherwise a rolled-back step announces something that did not happen.
  • Retry the text, not the notification. SMS delivery is its own job precisely so a provider timeout does not re-send the email and bell entry.
  • Dedupe at the database. The unique dedupe_key index decides, not an application check, because two concurrent dispatches would pass an application check. Provide smsDedupeKey() when two legitimate messages share an event and recipient.
  • Switches are read at delivery, so turning an event off stops messages already queued.
  • No-provider and not-configured are suppressed, not failed, keeping the failed-SMS log for real breakages.
  • Case notifications are in-app only (D35): no email, SMS or push.
  • Queue name mismatch to check. compose.yaml runs a worker with --queue=payments,sync,notifications,sms,reports,maintenance. The ShouldQueue notification classes read (e.g. CourierPartnerUpdate, PaymentReceived) set no queue, so they use the connection's default queue, which that list does not name. Verify the production worker command covers the default queue before relying on it. This is observation only, not a confirmed defect.
  • Real SMS provider scope: only GenNet has a live-capable driver; the others are placeholders. Whether the GenNet integration has been run against the live service was not verified.

How to...

Add a bell notification

  1. Create the class in app/Notifications/{Area}/ extending Illuminate\Notifications\Notification, implements ShouldQueue, use Queueable, via() returning ['database'], and toArray() returning at least event (a dotted name) plus the fields it needs (a reference, a public id). No personal data.
  2. Add events.{event}.title and .description under notification.events in lang/en/notification.php and lang/bn/notification.php. Remember the dotted-key trap; keep the array keyed by the full event name.
  3. If the link depends on who is reading, extend RecentNotifications::href/caseHref rather than storing a URL.
  4. Send it after commit with a deterministic id (copy the idFor() pattern in AnnounceCourierEvent) so repeats write one row, and swallow-and-report failures.

Add an SMS notification

  1. Add a case to SmsEvent (decide isOneTimeCode()) and its title/description under sms.events in lang/en/sms.php and bn. Add the template under sms.templates.*.
  2. In the notification, add 'sms' to via() and implement toSms() returning new SmsMessage(to: '', body: __('sms.templates...'), locale: Locale::parse($notifiable->locale ?? null), event: SmsEvent::X->value); the channel fills in the recipient from routeNotificationFor('sms').
  3. Add smsDedupeKey() if one event can legitimately occur twice for a recipient.
  4. Run the guard test in SmsEventSwitchesTest; add a case to QueuedSmsTest.

Notify staff that a new kind of work arrived

  1. Add a case to StaffQueue and fill every match: module(), cardKey(), route(), model(), waitingStatuses() (and the dashboard lang card key). One definition drives who is told, what the dashboard counts and where the bell links.
  2. Add notification.events.queue.{value} lines. After the submission commits, call $queue->announce($submission).

Add an SMS provider

  1. Write a driver extending SmsGateway (implements SmsProvider: send, balance, name, isConfigured, required/missing configuration) with a SmsCredentials subclass. A provider-side rejection returns an SmsResult, it does not throw.
  2. Set its driver in config/sms.php. No change to the code that sends messages.
