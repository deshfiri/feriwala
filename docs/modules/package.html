Package module

Packages are the plans Feriwala sells to partner (business) accounts. A package carries a price, a term, wallet requirements and a set of typed entitlements; an account's subscription to it decides which modules the account may use and how much of each. This page explains the model, the subscription lifecycle, and how a feature flag gates code.

Purpose

Partners cannot trade until they hold an entitling package (§5.4 activation funnel). The package decides which business methods they get (wholesale, dropshipping), how many products they can publish, how many staff and websites they may have, whether they get a dedicated website with domain and hosting, external-store access and so on (§8.1). Administrators create, edit, take off sale and archive any number of packages (§8). Accounts choose, renew, upgrade, downgrade and cancel (§8.2, §8.3, §8.4). Decision D16 governs downgrades: nothing is auto-removed, and an over-limit downgrade is blocked unless an authorised administrator overrides it with a recorded reason.

Users: partners (own subscription screens), administrators (catalogue, assignment, override), and the system (the daily lifecycle sweep, payment settlement).

Rule. Entitlements are read from the subscription's captured terms, never from the live package row (§8.3). Editing a package changes what future buyers get, not what existing subscribers already agreed to. Every feature gate must go through App\Domain\Package\Entitlements.

Key terms

Package
A sellable plan row in packages. Soft-deleted ("archived"), never hard-deleted.
Feature
One entry of the closed PackageFeature enum. The enum names which feature; a package_features row holds what a package sets it to.
Subscription / term
A UserPackage row: one account's hold on a package for one period. Renewals, upgrades and downgrades are new rows, chained by renews_user_package_id.
Terms (snapshot)
SubscriptionTerms, stored as JSON in user_packages.terms at creation: name, fees, validity, grace, deposit, minimum balance, charges and every feature value.
Source
How the subscription came about (SubscriptionSource); never changes after write.
Entitling
Statuses that grant features: active, renewal_due, grace_period.
Current pointer
business_accounts.current_user_package_id (relation currentPackage). A cheap hint; Entitlements verifies it rather than trusting it.

PackageFeatureType::cast() turns the stored string into a bool, int or string; serialise() does the reverse. A limit stored as null means unlimited; zero is a real answer ("none allowed"). That is why "unlimited" and "zero" must never be conflated.

States & lifecycle

UserPackageStatus implements TransitionableState. Legal moves (transitionsTo()):

FromToEntitles?
pending_paymentactive, superseded, cancelledNo (unpaid grants nothing, §5.1)
activerenewal_due, cancelled, expiredYes
renewal_dueactive, grace_period, cancelled, expiredYes
grace_periodactive, expired, cancelledYes
expired, cancelled, supersedednone (terminal)No

Terminal means a new term is a new subscription row, never the old one revived. UserPackage::entitlesNow() additionally checks started_at (a future-dated downgrade or grant does not entitle yet) and grace_ends_at ?? expires_at (an entitling status past its effective end does not entitle).

SubscriptionSource: purchase, renewal, upgrade, downgrade, manual, promotional. isPaid() is false only for manual and promotional, so revenue reports can tell a grant from a sale.

Choosing and paying (first purchase)

  1. SelectPackage::handle() (requires Package::isAvailable()) in one transaction supersedes the account's other pending_payment rows and writes the new row with paid_fee = package fee and the captured terms.
  2. The partner pays through the activation checkout (Billing module). Activation itself is outside this module.

Renewal

  1. SubscriptionPolicy::isRenewable() allows renewal_due, grace_period and expired always, and active only inside the renewal window (expires_at - renewalWindowDays). A term with no expiry never enters the window. Pending, cancelled and superseded terms are not renewable.
  2. OpenRenewal (row-locks the current term, checks ownership) captures the package's current terms; paid_fee is renewal_fee ?? fee. The renewal page (Erp\RenewalController::show) opens it, so the quote and the record agree. pay re-quotes server-side and hands off to the gateway.
  3. Billing\Actions\SettlePayment routes PaymentPurpose::PackageRenewal to ActivateRenewal. The new term starts where the old one ends (or now if the old one is over); validity and grace come from the renewal's snapshot. The previous term is moved to expired only if it has actually ended; otherwise the sweep closes it later.
  4. The account's current_user_package_id is repointed immediately; Entitlements falls back to whichever term really entitles today. Audit action package.renewed (system actor), notification SubscriptionRenewed.

Upgrade and downgrade

PackageChangePlanner::plan() decides direction by fee: a higher target fee is an upgrade, equal or lower is a downgrade.

UpgradeDowngrade
EffectiveImmediatelyAt the end of the current term
ExpirySame as the current term (cycle kept)A full new term from the effective date
Gross feeTarget feeTarget renewalFee ?? fee
CreditUnused share of paid_fee, floored, only if package.prorate_upgrades is on (default true)Zero

OpenPackageChange refuses a non-entitling current term, the same package, an unavailable target, or a blocked plan. It supersedes any other pending upgrade/downgrade (one change in flight) and stores the quoted dates so activation does not recompute them. If the quote is not payable (free change) the controller redirects to the subscription page with an info message rather than activating silently.

Lifecycle sweep

SweepSubscriptionLifecycle::handle() returns {due, grace, expired} and does three passes in order, chunked by 200:

  1. Renewal due: active terms with expires_at within the renewal window move to renewal_due and the owner gets SubscriptionExpiring.
  2. Grace: renewal_due terms past expires_at with grace_ends_at in the future move to grace_period (SubscriptionExpiring with inGracePeriod: true).
  3. Expire: entitling terms past grace_ends_at (or past expires_at where there is no grace) move to expired; the account pointer is moved to a still-entitling successor if one exists; SubscriptionExpired is sent.

Each move happens under lockForUpdate() and only if canTransitionTo(), so a repeat run (or a second server) does nothing and the notification is sent once. A term whose end passed during an outage goes straight from active to expired.

Assignment, cancellation, archive

  • AssignPackage: reason required, expiresAt must be after startsAt. Creates the row pending_payment then transitions to active, paid_fee zero. If it starts now, other entitling terms are cancelled; a future-dated grant leaves the current term running. Audit package.manual_assigned or package.promotional_assigned, sensitive. Notification PackageAssigned.
  • CancelSubscription: transitions to cancelled now (no access until expiry), clears or repoints current_user_package_id, audit package.cancelled (sensitive; actor null means the account holder). No refund: refunds are a separate workflow (§27, RefundabilityPolicy).
  • ManagePackages::archive: refuses with PackageInUse while a live (non-archived) KYC requirement's scope rule names the package (kyc_document_type_scopes.package_public_id) or while any entitling subscription exists. blockers() returns the same list so the screen can show it before the button is pressed. setActive(false) (take off sale) is unguarded: existing subscribers keep entitlements.
  • ManagePackages::update replaces features and charges wholesale: an absent feature means "not granted; default applies", so a facility can be withdrawn through the same form that granted it.

How a feature gate works

There are four layers; use the right one.

  1. Route gate — middleware entitled:<feature_value> (EnsureAccountIsEntitled). Boolean features pass if allowed; limit features pass if the limit is not exactly 0 (null = unlimited passes); text features throw InvalidArgumentException (a service level is not an access question). An unknown feature string also throws, so a typo cannot fail open. Accounts with no business account (platform staff) are passed through. Used today as entitled:staff_limit on the settings staff routes and the mobile staff routes. It aborts 403 "Your package does not include this."
  2. Capacity check — Entitlements::hasCapacityFor($account, $feature, $currentCount, $adding = 1). The caller supplies the count because only it knows what it is counting. Example: Website\Actions\SetWebsiteProductPublication publishes inside a lock keyed website:publish:<account>, counts the account's other published website products, and throws WebsiteRefused::publishLimitReached when ProductPublishLimit has no room. The same limit is shown as limit/used/remaining on the website product screens.
  3. Channel gate — SalesChannel::facility() maps Dropshipping to PackageFeature::DropshippingEnabled and Wholesale to WholesaleEnabled. Catalog\ProductEligibility adds the refusal PACKAGE_WITHOUT_CHANNEL when the account's package lacks the facility, and returns an empty query (whereRaw('1 = 0')) for an account with no active package. AccountContext uses the same flags to decide which workspaces an account sees.
  4. Snapshot read during allocation — Website\Actions\AllocatePackageWebsite reads DedicatedWebsite, WebsiteLimit and the validity-months features straight from the subscription's SubscriptionTerms when a subscription activates.

Behaviour of Entitlements with no entitling package: allows() is false, limit() is 0 and hasCapacityFor() is false — unlimited is never inferred from absence. With a package and a null limit, hasCapacityFor() is true and remaining() is null.

activePackage() checks the account's current_user_package_id pointer, verifies it with entitlesNow(), and otherwise falls back to the newest entitling subscription. The result is cached on the account instance as the resolvedActivePackage relation for the request; $account->refresh() drops it.

Money, ledger & audit effects

  • All money is Money (exact decimal Taka). PackageChangePlanner::flooredShare() computes the proration with bcmath at scale 20 and floors to the currency scale, so a credit is never larger than owed and no float is involved.
  • This module does not post ledger entries itself. Charging is the Billing module's job (quotes from CalculatePackageChangeQuote, CalculateRenewalQuote, payments via RecordPaymentFromQuote); activation here is reached only from payment settlement, so an unpaid change never moves an account.
  • SubscriptionTerms::toArray() stores fees as decimal strings (toDecimal()), restored by Money::fromDecimal.
  • Audit actions (module package): package.created, package.updated, package.archived, package.renewed, package.upgrade / package.downgrade (action is 'package.'.$source), package.manual_assigned, package.promotional_assigned, package.cancelled, package.downgrade_limit_overridden. Cancel, assign and override are flagged sensitive.

Rules, invariants & gotchas

Rule. Never assign UserPackage::status; use transitionTo() / canTransitionTo(). SelectPackage does contain one bulk update(['status' => Superseded]) on pending rows; follow the transition-based pattern in OpenPackageChange::supersedePending for new code.

  • Snapshot vs live row. Anything that answers "what may this account do" reads UserPackage::terms(). A package that edits a limit does not affect existing subscriptions until they renew (renewal captures fresh terms, §8.3). Rows older than the snapshot migration have terms = null and fall back to the live package.
  • The pointer is a hint. Cancelling or expiring does not always clear current_user_package_id (CancelSubscription and the sweep repoint, but older code paths and tests should not assume it). Use Entitlements::activePackage().
  • Defaults. Missing features default off or zero, except WholesaleEnabled and DropshippingEnabled, which default on.
  • Downgrades are never destructive (D16). Exceeding a limit after an override leaves the account's existing data alone; only new publishing is refused.
  • Equal fee is a downgrade. It waits until the term ends.
  • KYC rules key on package_public_id (ULID), not the slug, so renaming a slug cannot orphan a rule.
  • Archived packages stay readable (withTrashed in the admin index); subscriptions, payments and invoices reference them (restrictOnDelete).
  • AccountHoldings::counts() still returns 0 for ProductPublishLimit and WebsiteLimit (only staff is counted) even though the code comment says those modules "do not exist yet" and they now do. The downgrade guard therefore cannot currently block on products or websites. See the report; this is an observed gap, not a documented decision.

How to…

Add a new package feature

  1. Add a case to PackageFeature and extend type(), label() and default() (all are exhaustive matches).
  2. Surface it in the admin form: Admin\PackageController builds its feature list from PackageFeature::cases(); update resources/js/pages/admin/packages/package-dialog.tsx and lang/{en,bn}/package.php as needed. SavePackageRequest rejects unknown keys.
  3. Gate the code: route middleware entitled:<value>, or Entitlements::allows() / hasCapacityFor() with a count you supply.
  4. Existing subscriptions get the new feature's default (SubscriptionTerms::feature() falls back when the key is missing from the snapshot).
  5. If the limit holds existing things (like published products), add it to DowngradeGuard::guardedFeatures() and to AccountHoldings::counts().

Gate a new route or module behind a package facility

  1. Boolean or limit feature only. Add ->middleware('entitled:your_feature') to the route group (see routes/settings.php staff routes).
  2. Remember the gate does not run for accounts with no business account.
  3. Keep funnel and subscription routes out of the gate and named under packages. / subscription..

Change the term or grace behaviour

  1. Term length comes from validity_days; grace from grace_period_days, both captured into SubscriptionTerms.
  2. Date arithmetic lives in ActivateRenewal (renewals), PackageChangePlanner::plan() / OpenPackageChange (changes) and AssignPackage (grants). Change all relevant places and the sweep predicates together.

Add a new subscription status

  1. Add the case and its transitionsTo() row; update entitling() if it should grant access, tone(), and the translation group user_package.
  2. Check SubscriptionPolicy::isRenewable() (an exhaustive match) and the sweep queries.

Add a new notification for a lifecycle event

  1. Create the class under app/Notifications/Package/ and send it from the action next to the transition (the sweep uses tell() after a successful move(), so it is sent once).
