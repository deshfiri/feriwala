Account module

The business account is the commercial workspace: it owns KYC, the package, payments, the wallet, orders and websites, and its status decides whether the business may trade. This module also owns the activation funnel, staff inside an account, staff-created accounts, closure and erasure. It is separate from the login identity (users.identity_status) and from Feriwala's own platform staff.

Purpose

Feriwala has a single account structure (§5, §44, D1). There is no customer account, no partner account and no conversion between them: a "partner" is simply a business account that trades through wholesale, dropshipping or both. Everything that looks like a type is either a BusinessAccount status, a package entitlement, an AccountRole, or the wholesale AccountType flag.

The module implements:

  • §5.1 – §5.4 registration, verification, activation funnel and the pre-activation allow-list (EnsureBusinessAccountIsActivated).
  • §5.3 the twenty-two account statuses, status history, suspension and reactivation.
  • §6 identity status (lock, suspend, close a login) as a separate question from business status.
  • §8.1 / D1 staff inside an account: one owner, owner and managers invite staff, staff limit comes from the package.
  • D18 closed accounts are preserved, never reopened; D23 identity versus business account; D27 automatic activation once conditions are met, with a manual hold as the exception; D22 activation readiness.
  • Account deletion requests and erasure (an account is anonymised into a tombstone, not deleted).

Who uses it: the partner (owner, manager, staff) works inside the account; platform staff review, activate, suspend and create accounts from /admin; the system activates accounts automatically when payment settles or KYC is approved.

Rule. The account status moves only through transitionTo(), and the only code that does it for commercial status is ChangeAccountStatus, which also writes the history row. Never assign $account->status directly. A login's UserStatus is a different enum with a different action (ChangeIdentityAccess).

The model class is BusinessAccount, not Account, on purpose: Account alone reads as "the thing I log into", which is the confusion the identity/account split ended. The UI still says "Account".

Key terms

Business account
BusinessAccount: the commercial workspace. One owner (owner_id is unique), soft-deleted, public id is a ULID.
Identity
The login, a User. Its identity_status (UserStatus) answers "may this person use the platform at all". It outranks every permission and every account status.
Platform staff
A User with no business_account_members row, holding a PlatformRole. See Access. They never complete KYC or pay an activation fee.
Owner / Manager / Staff
AccountRole: the account-side roles. The UI vocabulary is Account, Staff and Permissions; the starter kit's "team" must not appear in routes, labels or messages.
Funnel / onboarding
Register, verify, KYC, package, payment, approval. The six-step stepper is OnboardingStep; the 22 statuses drive the system, the six steps drive what a person sees (§33.4).
Approval gate
The approval_pending status. Reaching it means all three activation conditions are met.
Activation hold
A named staff member's recorded decision (reason, time, who) to take one account off the automatic activation path (D27). It does not block manual activation.
Waived activation payment
An administrator's recorded decision that no activation payment is owed. No payment row and no ledger entry is created; the account stores who, when and why.
Account type
Conditional or NonConditional: whether a wholesale order's product cost is funded upfront or recovered from the collected COD amount. Not a lifecycle, and not what the single-account rule forbids.
Partner number
partner_number: BJ followed by eleven random digits (first digit never zero), 13 characters, unique, never reused (soft-deleted rows are checked too).
Managed account
An account opened by staff on someone's behalf (CreateManagedAccount); the owner sets their own password through a setup link.
Tombstone
What an erased user or account becomes: ERASED-XXXXXXXX (last eight characters of the public id uppercased) in tombstone_reference, personal fields replaced, erased_at set.
Dossier
AccountDossier: the administrator's full read of one business, including internal notes. Authorised by viewDossier, never view.

Who triggers the moves, as far as this module is concerned:

  • Verification statuses to kyc_pending: VerifyMobile, SkipMobileVerificationIfNotRequired, AdvanceAccountPastVerification (also used after staff confirm a contact by hand).
  • KYC statuses: the KYC module (SubmitKyc, ReviewKyc, RequestKycResubmission). Approval then also moves the account on to package_selection_pending.
  • payment_pending onward: the Billing and Package modules; AdvanceToApprovalGate takes the intermediate payment_verification_pending step so the history shows the payment being received.
  • approval_pending: EvaluateActivationReadiness. active: ActivateAccount.
  • suspended: SuspendAccount; back to active: ReactivateAccount.
  • temporarily_restricted: the KYC deadline sweep (EnforceKycDeadline), when enabled.
  • package_renewal_due, package_expired, low_wallet_balance, wallet_topup_required: set by the Package and Wallet modules (the scheduler has SweepSubscriptionLifecycle; the wallet has EnforceBalanceRules and RestoreWalletServices). Not traced in detail here.
  • closed: EraseAccount (through ChangeAccountStatus, only when the machine allows it from the current status).

Flow: registration to activation

  1. Registration (app/Actions/Fortify/CreateNewUser.php) creates the user (identity_status active), a BusinessAccount at registered, and an owner membership, and attaches a referrer when a code was typed.
  2. Email, and mobile while MobileVerificationRequirement::isRequired(), are verified; the account moves to kyc_pending. Verification is read from the owner (ActivationRequirements::ownerVerified), never from whoever is signed in.
  3. KYC is submitted, reviewed and approved (KYC module); the account reaches kyc_approved then package_selection_pending.
  4. The owner picks a package and pays the combined activation checkout (payment_pending, then the payment is verified server-side).
  5. Each trigger (payment settlement from the IPN, the browser return, the reconciliation sweep, a KYC decision) calls ActivateAccountAutomatically. Three callers may race; the per-account lock plus the "already activated" check make that harmless.
  6. If ActivationRequirements::unmet() is empty and the account is not held, ActivateAccount runs; otherwise the account waits at approval_pending for a reviewer at /admin/activations.

The three conditions (§5.1, §44) are: a KYC submission with status approved; an activation payment that is settled (or a recorded waiver); the owner's email verified and mobile verified when required. Closed and suspended accounts, and already activated ones, return a single explanatory reason.

Flow: reviewer actions on the approval queue

  • activations.approve: manual activation (works on a held account; this is the point of a hold).
  • activations.request-resubmission: RequestKycResubmission.
  • activations.suspend: declines an applicant at the gate (uses account.reject, see Permissions).
  • activations.hold: HoldAccountActivation::hold or release. Not a fourth outcome; it decides nothing, it moves the decision back to a person.

Flow: staff inside an account

  1. An owner or manager with the permission calls InviteStaff. It refuses role owner, self-invitation, existing members; locks the account row; checks StaffAllowance::hasRoom(); creates the invitation (14 days, InviteStaff::EXPIRES_AFTER_DAYS); audits account.staff_invited; and sends the email after commit.
  2. StaffAllowance: limit is PackageFeature::StaffLimit through Entitlements (null means unlimited, zero means no staff at all). A live invitation occupies a seat, so ten invitations cannot be sent against two seats. The owner does not consume a seat.
  3. The invitee opens staff/invitation/{token} signed in. AcceptStaffInvitation locks the invitation, checks it is live, addressed to this user, that the user has no membership yet (D1), and re-checks room (the package may have been downgraded since). It creates the membership, stamps accepted_at/accepted_by and audits account.staff_joined.
  4. ManageStaff revokes invitations (account.staff_invitation_revoked), removes staff (account.staff_removed) and changes roles (account.staff_role_changed). It refuses on the owner and refuses granting owner.

Flow: deletion and erasure

  1. A person (or a Supplier) asks: RequestAccountDeletion (reason of at least 5 characters, idempotent) writes the request, audits account.deletion_requested and announces it to the staff queue (StaffQueue::AccountDeletion, or SupplierDeletion). They may withdraw while pending.
  2. Staff with account.delete (or supplier.delete) decide at /admin/deletions. DeletionAuthority: nobody deletes their own account; platform staff can only be deleted by a Super Admin.
  3. EraseAccount::handle needs a reason (5+ characters) and a typed confirmation (the user's email, or the Supplier's reference), refuses to erase the last active Super Admin, and runs in one transaction under a row lock. Files are collected first and deleted after commit through ManagedStorage; a file that cannot be removed is reported, never allowed to undo the erasure.
  4. What goes: sessions, passkeys, tokens, notifications, saved addresses, invitations, carts, SMS logs, API credentials and webhook secrets, KYC typed values and files, payout methods and shared addresses. What is replaced: names and contact details inside records that must stay (orders, withdrawals, websites). What stays untouched: amounts, identifiers, statuses and their history, ledger, payments, refunds, stock movements and the audit log. Where the database refuses a change (guard triggers) the table is reported as retained with the reason.
  5. The login becomes a tombstone (identity_status closed, erased_at, tombstone_reference, email erased-…@deleted.invalid), websites are closed through their own machine, and the business account is moved to closed through ChangeAccountStatus. One audit entry, account.erased (sensitive), records counts and table names with no personal data. preview() reports what would happen inside a rolled-back transaction.

Scheduled and queued

This module owns no scheduled task. Neither does it prune expired invitations (deliberate; see the comment in routes/console.php). The KYC deadline sweep that can restrict an account is in KYC. AccountActivated, AccountSuspended, AccountReactivated, StaffInvitation and the Identity* notifications live in app/Notifications/Account.

Self-scoping

  • Partner routes carry no account identifier: the account is resolved from the signed-in user's membership. Staff are addressed by public id and looked up inside the caller's account.
  • EnsureBusinessAccountIsActivated is an allow-list of route-name prefixes (onboarding., profile., kyc., packages., subscription., checkout., security., user-password., well-known., staff.invitation., locale., notifications., logout, password., verification., and a placeholder support.). A new ERP route is closed by default. An unactivated member is redirected to onboarding.status (a 403 would blame someone who has steps left); a user with no account at all (invitee or platform staff) is sent to their home route instead.
  • Administration never uses business.activated. It is identity plus permission plus a policy on each action, so platform staff need no business.

Gotcha. HandleInertiaRequests shares an account prop: the viewer's own account. A page prop with the same name silently overwrites it for the whole shell. The admin account screen returns its subject as business for this reason. Check share() before naming a page prop. Also gate "my business" navigation on account being present, not only on permissions (.ai/rules/account-access.md).

Money, ledger & audit effects

  • Money: the account stores two optional decimal override columns, withdrawal_minimum_override and withdrawal_maximum_override, read by the Withdrawal module. This module does no money arithmetic. The deposit obligation captured on activation is a Wallet concern (CaptureDepositObligation).
  • Ledger: activation opens the wallet (OpenWallet, idempotent, empty: every balance starts at zero and moves only through the ledger) inside the activation transaction. A waived activation payment writes no payment row and no ledger entry because no money moved. Erasure keeps every ledger, payment, refund, withdrawal and stock record.
  • Idempotency: activation is idempotent by construction (lock, re-check, "already active" short-circuit); the settlement callbacks that trigger it are retried by design.
  • Audit actions written here: account.activated, account.activation_held, account.activation_hold_released, account.activation_held_back (system), account.completed_manually, account.suspended, account.reactivated, account.account_type_changed, account.created_by_staff, account.staff_invited, account.staff_joined, account.staff_invitation_revoked, account.staff_removed, account.staff_role_changed, account.deletion_requested, account.erased, account.mobile_verification_requirement_changed, identity.locked and the other identity.* moves. Most of the staff-decision ones are marked sensitive. Status moves also leave their own history row, which is not a substitute for the audit entry.

Rules, invariants & gotchas

  • One owner, one account, one membership per person (D1), enforced by unique indexes on owner_id and on business_account_members.user_id. An invitee who already works somewhere is refused; there is no account switcher.
  • Solo accounts see no staff concept (BusinessAccount::isSolo()): no switcher, no members list, no "team".
  • Identity versus business (D23): UserStatus gates everything including admin; AccountStatus gates trading only. A closed login's business is not automatically closed by ChangeIdentityAccess (only EraseAccount moves both).
  • closed is terminal (D18). Suspension is reversible and must not be used as a quiet substitute for closure.
  • Reactivation is not activation. ReactivateAccount only returns a suspended account to active; it opens no wallet, starts no subscription, calculates no commission. It refuses any account that is not suspended.
  • Manual activation still works on a held account; a hold stops only the automatic path (D27).
  • The subscription term comes from what was bought ($subscription->terms()), not from the live package row, so editing validity_days between purchase and approval cannot shorten a paid year. The term starts at activation, not purchase.
  • Notifications are sent after the transaction commits (activation, suspension, invitation). A queued mail for a change that rolled back is worse than a late one.
  • Nobody changes their own identity status; the refusal is in the action because Gate::before would pass a Super Admin straight over a policy.
  • Erasure is anonymisation. The audit log and ledger cannot be changed by it. Tables where a database guard refuses an update are reported as retained.
  • Partner numbers are never reissued and are not a route key; the URL identifier is the ULID public id (non-negotiable 8).

How to…

Add an AccountStatus

  1. Add the case in app/Domain/Account/Enums/AccountStatus.php, its transitionsTo() row, and every other row that should lead to it. Decide tone(), and whether it belongs in isActivated(), canTransact() or neither.
  2. Map it in OnboardingStep::forStatus() if it is part of the funnel (otherwise it falls into Approval).
  3. Add the label under the account group in lang/en/status.php and lang/bn/status.php (HasTranslatedLabel). Check the column width: status is a 40-character string.
  4. Make the move through ChangeAccountStatus; add a test in tests/Feature/Account/. Update the allow-list implications if the new status should be restricted to onboarding.

Add an account-level permission

  1. Add a case to AccountPermission.
  2. Grant it in AccountRole::permissions() (owner gets all automatically).
  3. Check it through User::hasAccountPermission() in a policy (see AccountMembershipPolicy::allows or SharedAddressPolicy). Platform permissions are different: see Access.

Add a new admin action on an account

  1. Write an Action that locks the account row, changes state through ChangeAccountStatus where status changes, and writes an AuditEntry with module: 'account' and accountId.
  2. Add a method to BusinessAccountPolicy that treats membership as a refusal and asks a catalogue permission via PermissionCatalogue::name().
  3. Add the route in the admin. group of routes/web.php (before accounts/{account} if it is a literal segment). If the reason must be required, add the route name to required_for in config/reasons.php. Add RequirePassword for destructive actions.
  4. Use Gate::authorize('viewDossier', …) for any screen that shows reviewer-written material, never view.

Add a staff-limited feature to a package

  1. Seat logic is in StaffAllowance; the limit itself is a package feature (PackageFeature::StaffLimit). Change package data in the Package module, not here.
  2. Gate new routes with entitled:staff_limit inside business.activated, never on an admin route.

Change what is erased

  1. Edit EraseAccount::userSteps, accountSteps, caseSteps or supplierSteps using $run->purge(), blank(), update(), collectFiles(), retain().
  2. Collect file paths before deleting the rows that name them.
  3. Extend tests/Feature/Account/AccountErasureTest.php.
